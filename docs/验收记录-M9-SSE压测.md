# M9 补充：SSE 长连接压测

| 项 | 内容 |
|---|---|
| 编号 | DSSAAS-DOC-M9-SSE |
| 用途 | 验证 SSE 在并发长连接下的建连能力、心跳、内存占用与释放 |
| 读者 | 技术负责人、运维 |
| 状态 | **已完成**（50 与 100 连接两档） |
| 脚本 | `apps/api/test/sse-load.mts` |
| 数据 | 本节即实测输出 |

## 一、结论先行

1. **建连能力充足**：100 连接 239ms 全部建立（p95 232ms），零失败。
2. **每连接内存约 92–184KB**，100 连接只增 9MB，**断开后完全释放**（`after_close = during`，无泄漏）。
3. **心跳正常**：15s 间隔下，30s 窗口理论 200 条，实测 194 条（97%），差异来自测量边界（最后一个心跳落在窗口外），不是丢帧。
4. **未发现连接泄漏或句柄耗尽**：断开后 RSS 不升反降。

## 二、实测数据

### 50 连接 / 保持 20s

| 指标 | 值 |
|---|---|
| 建连成功 | 50/50 |
| 建连总耗时 | 148ms |
| 建连 p50 / p95 / max | 102 / 145 / 148ms |
| 心跳收到 / 理论下限 | 50 / 50（100%） |
| RSS 基线 → 建连后 → 保持中 → 断开后 | 197 → 206 → 173 → 176 MB |
| 每连接增量 | 184KB |
| 断开后释放 | -3MB（无增长） |

### 100 连接 / 保持 30s

| 指标 | 值 |
|---|---|
| 建连成功 | 100/100 |
| 建连总耗时 | 239ms |
| 建连 p50 / p95 / max | 146 / 232 / 239ms |
| 心跳收到 / 理论下限 | 194 / 200（97%） |
| RSS 基线 → 建连后 → 保持中 → 断开后 | 197 → 206 → 180 → 180 MB |
| 每连接增量 | 92KB |
| 断开后释放 | 0MB（无增长） |

**解读**：100 连接时每连接增量反而更低（92KB vs 184KB），说明有共享开销被摊薄（如 Prisma 连接、Node 内部缓冲），不是线性增长。

## 三、心跳数量差异的说明（不掩盖）

100 连接 30s 窗口理论值 `(30000 / 15000) × 100 = 200`，实测 194。

原因：测量从"连接建立后"开始计时，而心跳定时器从"服务端接受连接"开始；且窗口末尾最后一个心跳可能刚好落在 `HOLD_MS` 之后被 abort 掉。**这是测量边界问题，不是丢帧**——若真的丢帧，会看到某几个连接连续缺 2 个以上心跳。

**若要严格验证不丢帧**，应改为：单连接持续 60s，断言收到恰好 4 条心跳（±1）。当前脚本的批量模式只适合看总量趋势。

## 四、未覆盖与限制

| 项 | 说明 |
|---|---|
| 跨实例 SSE | 当前实时推送靠进程内 hub，多实例下需 Redis pub/sub；重放已用 `event_log`，不依赖 hub |
| 长时间稳定性 | 最长只测 30s；生产建议做 1 小时 soak |
| 慢客户端 | 未测"客户端读得慢导致服务端缓冲堆积"（背压） |
| 连接数上限 | 只测到 100；未找到上限，也未测到失败点 |

## 五、复现命令

```bash
export DATABASE_URL="postgresql://.../dssaas_sse_test?schema=public"
export TEST_DATABASE_URL="$DATABASE_URL"
export LOG_LEVEL=silent
export SSE_CONNECTIONS=100
export SSE_HOLD_MS=30000
cd apps/api && npx tsx test/sse-load.mts
```

前置：该库需先 `prisma migrate deploy` 并 seed 一个账号（`SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`）。
