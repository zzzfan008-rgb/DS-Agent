# 0003 · 用 Postgres + pgvector（而非独立向量库）

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-20 |
| 决策类型 | 数据架构（影响检索与备份，改造成本中） |
| 关联 | `docs/00` §11 §19；`docs/06`（`kb_chunk`）；`docs/09`；ADR-0010 |

## 背景

1. **DSH 没有 embedding / vector / RAG 包**（`docs/00` 附录 A 已核实，311 个包中无对等能力）→ 向量能力必须自建，问题只是「放哪」。
2. **检索要求带版本与引用**：`docs/00` §11 要求混合召回（向量 + 关键词）→ top-k → 可选重排 → 输出必须带 `document_id + chunk + version`；`kb_query_log` 要记命中。引用与版本都住在 Postgres，跨库就是跨一次网络 + 一次可能的「引用指向已删除切片」。
3. **一致性是硬约束**：尺码表既是知识（客服口径）又是结构化数据（平台上传），必须**同源同版本**；知识库过期比没有知识更危险（`docs/00` §18「知识库过期」风险项）。跨库双写在「主数据变更 → 切片 → 嵌入」链路上必然出现窗口。
4. **规模明确且不大**：单租户、自有货品、SKU 级文档。切片量级预估 10^4–10^5，QPS 个位数到几十。这个量级离 pgvector 的上限很远。
5. **运维能力有限**：每多一个有状态服务，就多一套备份、恢复、升级、监控与故障演练（本文档 `docs/20` 的备份矩阵已覆盖 Postgres，加一套向量库等于备份矩阵再翻一页）。

## 决策

- **一个库**：Postgres 16 + `pgvector` 扩展；`kb_chunk.embedding vector(1024)`，HNSW 索引（`vector_cosine_ops`），`maintenance_work_mem` 与 `hnsw.ef_search` 按 `docs/09` 调参。
- **混合召回同库完成**：向量列 + `tsvector`（中文分词/`pg_bigm` 方案在 `docs/09` 定稿）在同一张表、同一条 SQL 或同一事务内的两条查询里融合；不使用跨服务聚合。
- **一致性与版本**：`kb_document` 版本 + `kb_chunk.status ∈ {active, superseded, disabled}`；重切片 = 新行 + 旧行标 `superseded`（不 UPDATE 内容）。主数据变更走同一事务或同一 outbox 事件，避免「DB 已更新、向量未更新」。
- **降级可用**：向量不可用（扩展缺失/索引重建）→ 纯关键词检索 + 标注「低置信」→ 判断层升级人工（`docs/00` §11、`docs/18` §0.3）。这条只有在「同一个库」时才可能是一个开关而不是一次架构改造。
- **维度锁定**：`vector(1024)` 固定。换嵌入模型导致维度变化 = 新列（`embedding_v2`）+ 后台重嵌入 + 双读窗口 + 切换，不原地改列。

## 备选方案与放弃理由

| 方案 | 放弃理由 |
|---|---|
| Milvus / Qdrant 自托管 | 多一个有状态服务：独立备份、独立恢复演练、独立版本升级；且引入**双写漂移**（主数据已改、向量未改），直接违反 ADR-0010 与 `docs/20` §8 的零容忍指标 |
| Elasticsearch / OpenSearch | JVM + 堆内存运维成本高；BM25 强但向量能力是后加的；同样是跨库双写，且审计与引用仍要回查 PG |
| 云托管向量库（Pinecone 等） | 数据出境与驻留问题；平台消息、商品资料属经营数据，自用系统没有上云的必要收益 |
| Postgres 内自建倒排/暴力扫描 | 10^5 级还可接受，但召回质量与延迟不可控；既然装了 pgvector，没有理由自研 |
| 单一向量库替代 Postgres 存切片 | 引用、版本、权限、审计、事务全在 PG；把切片搬走等于把知识库的元数据与内容分家 |

## 影响

| 面向 | 内容 |
|---|---|
| 正面 | 一套备份/恢复/PITR 覆盖知识库与业务数据；引用、版本、权限、审计同库同事务；降级只是查询改写 |
| 正面 | HNSW 索引与 `kb_chunk` 同表，重建索引可在线 `REINDEX INDEX CONCURRENTLY`，不需要数据迁移 |
| 代价 | HNSW 占用内存与磁盘随切片线性增长，需监控 `pg_relation_size` 与缓存命中 |
| 代价 | 向量检索与业务查询共享连接池与 CPU：检索变慢会拖慢写入门 → 必须分连接池/分只读副本（读检索走副本，写入门只走主库） |
| 代价 | 中文关键词侧不如专用搜索引擎：分词质量与同义词需在应用层补（`docs/09`） |
| 缓解 | `kb_chunk` 按月/按域分区可控；索引重建放低峰；`statement_timeout` 限制检索；预算内 top-k 上限 + 重排可选 |

## 复审触发条件

- `kb_chunk` 活跃行 > 5×10^6，或检索 P99 > 200ms 且已排除索引参数问题。
- 检索 QPS 持续 > 50，与交易路径争抢主库资源，只读副本仍无法隔离。
- 需要跨组织/跨租户的向量隔离（本方案明确不做多租户，此项仅在企业化立项时触发）。
- 需要专用 ANN 硬件（GPU 索引）或向量库特有的能力（多向量、稀疏向量混合、内置重排）。
- 嵌入模型强制要求维度/度量变化 > 1 次/年，改造窗口成本超过引入独立服务。
