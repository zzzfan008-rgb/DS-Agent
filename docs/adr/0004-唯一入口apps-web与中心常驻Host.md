# 0004 · 唯一入口 apps/web + 中心常驻 Host（不把 dsh-headless 当交互通道）

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-20 |
| 决策类型 | 架构（入口与运行时拓扑） |
| 关联 | `docs/00` §5.1 §5.2；`docs/14` §5.3；`docs/17`；`docs/18` §0.3；ADR-0002、ADR-0007 |

## 背景

1. **运营与客服不装 DSH**：他们在浏览器里点按钮或提诉求，需要的是结果，不是对话。DSH 原生 Web/Desktop 界面只给管理员调 preset/skill。
2. **`dsh-headless` 是一次性任务模式**（`docs/00` 附录 A：跑完即退出、无 GUI、不常驻，支持 `--json` 事件流与 `--session-id` 续接）。它**没有**面向浏览器的流式通道，每次调用有冷启动成本。
3. **实时/交互要求**：客服消息 5s 内草稿可用或降级（`docs/18` §0.2），且过程要能中途取消（用户关掉面板、换问题）。这要求常驻进程 + 流式 + `AbortSignal`。
4. **权限必须在 Host 侧再判一次**：`dsh-api-remote-access` 用 peer principal 决定 role × resource；如果浏览器直连 Host，这一层就没有可信的 principal。
5. **审计要求**：每个业务动作要有 `request_id` 贯穿 api → Host → 模型调用（`docs/00` §19.3）。一次性进程难以维持贯穿的会话与流。

## 决策

- **唯一业务入口 = `apps/web`**（Next.js，12 个页面）。运营/客服的账号、权限、审批、页面状态都以它为准；不暴露任何 DSH 原生界面给业务角色。
- **`apps/api` 是 Host 的唯一客户端**：按请求构造业务信封（`user_id`、`role`、`purpose`、`request_id`、`org_id`），以 Client 身份调用 Host 暴露的**一个** Typert Remote service（`@Remote({ mode:'stream' })`）。
- **Host 常驻单实例**（Compose 服务 `dsh-host`，随栈启动），对外只在 `internal` 网络暴露 RPC 端口；不发布宿主机端口。多副本不在本期范围（需先解决会话粘性与并发上限）。
- **流式与取消**：api 将 Host 的流透传为 SSE（`text/event-stream`，带 `Last-Event-ID` 补偿，`docs/18` §1.5）；浏览器断开或用户取消 → api 触发 `AbortSignal` → Host 侧工具调用中止 → 释放额度。
- **`dsh-headless` 的使用白名单**（仅三类）：批量任务（`worker` 调用）、定时任务、CI 回归。调用必须带 `--json` 与 `--session-id`，禁止在 HTTP 请求路径内同步阻塞调用。
- **原生界面**：管理员通过本机回环 + 一次性启动 token 使用（`docs/14` §5），用完即关；不作为任何业务流程的一环。
- **降级**：Host 不可用 → 按 `docs/18` §0.3 走 L2/L3（话术模板 → 人工手写），业务**不停摆**，但绝不绕过写入门与审计。

## 备选方案与放弃理由

| 方案 | 放弃理由 |
|---|---|
| 每次请求 `dsh-headless` 跑一次 | 冷启动吃掉 5s 预算；无面向浏览器的流式；进程退出即丢上下文，多轮追问要反复重建；并发下进程数不可控 |
| 浏览器直连 Host（跳过 api） | 失去可信 principal 与二次鉴权；业务审批、写入门、审计全部旁路；CORS 与内网暴露面扩大 |
| 用 DSH 原生 Web 当业务界面 | 没有 12 个业务页、没有审批模型、没有 A/B/C 分级；且与「管理员调试工具」定位冲突，权限无法分档 |
| 自研 agent 循环（不用 DSH） | 放弃 agent 内核复用（多步工具调用、长上下文、skill/MCP 编排），等于重写一个 DSH（ADR-0007 复审项） |
| Host 多副本前置负载均衡 | 会话与工具上下文有状态；本期单机房单实例足够，过早分布式化只会引入粘性会话与一致性难题 |

## 影响

| 面向 | 内容 |
|---|---|
| 正面 | 一个入口、一套权限、一条 `request_id` 链路；Host 可用作连接池与限流点（并发上限、队列、背压） |
| 正面 | Headless 的用途被收窄到「无交互」场景，避免两套语义混淆 |
| 代价 | Host 成为单点：挂了以后所有 agent 类功能降级（但业务数据与网页仍可用） |
| 代价 | 流式透传 + 取消语义需要 api 侧正确实现，否则会留下孤儿调用与计费（必须落 `model_call_log.status=cancelled`） |
| 缓解 | `/health` 与 `/ready` 探针；Host 重启即换桥接令牌（`docs/14` §5.4）；SSE 心跳 15s；孤儿调用由 `media_job`/`model_call_log` 对账任务清理 |
| 观测 | 指标：Host 并发数、排队时长、流首字节时延、取消率、孤儿调用数 |

## 复审触发条件

- Host 需承载的并发持续逼近单实例上限（排队时长 > 2s 成为常态），需要水平扩展时。
- 浏览器侧出现**直接**需要 agent 流式能力、且 api 透传成为瓶颈的场景（如双向多模态）。
- `dsh-headless` 支持常驻 + 流式 + 会话恢复，且经回归验证可替代 Host 常驻进程。
- 需要多租户/对外 SaaS 化（本方案非目标，触发即意味着方案基线变化）。
- Host 相关故障连续两次以上影响业务可用性，且根因在进程内（需重新评估是否拆分 agent 能力边界）。
