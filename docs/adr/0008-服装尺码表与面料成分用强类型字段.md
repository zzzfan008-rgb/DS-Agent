# 0008 · 服装尺码表与面料成分用强类型字段（而非自由文本）

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-20 |
| 决策类型 | 领域建模（数据契约，改动需迁移） |
| 关联 | `docs/00` §13.2 §18；`docs/06` §2（枚举）§3.1；`docs/10` §2.1 M3；`docs/19`；ADR-0010 |

## 背景

1. **服装是 SKU 最复杂的类目**：尺码表、面料成分既是**知识**（客服口径、详情页话术）又是**结构化数据**（平台属性、资质申报、尺码表图渲染）。同一份事实的三个出口必须同源同版本。
2. **成分是合规字段**：百分比合计必须 100，平台资质与职业索赔都盯这一项；一个「62% 聚酯纤维 + 33% 棉」的自由文本既无法校验也无法申报。
3. **尺码表图要机器渲染**：`docs/10` §2.1 M3 要求由 `size_chart` + 模板渲染 PNG，且与数据同版本（`data_version`）；自由文本渲染不出图，只能人手画，必然图文不一致。
4. **平台属性映射必须按值入库**：拼多多标准色卡 ID、1688 的尺码与建议体重区间（`docs/00` §13.2），靠字符串匹配会随平台字典变化而静默错配。
5. **模型不得生成事实**（ADR-0010）：如果字段是自由文本，模型「改写措辞」时就会顺手改掉数值，且无法检测。

## 决策

- **尺码表**：`size_chart` 一尺码一行，多版本（`version_no` + `effective_from` + `status ∈ {draft, effective, superseded}`，同商品仅一条 `effective`）。`measurements` 用 **JSONB + JSON Schema 固定键**：`衣长/胸围/肩宽/袖长/腰围/臀围/下摆`，单位 cm，`numeric(12,3)` 语义；`recommend_height_min/max`、`recommend_weight_min/max` 为独立列并加 `CHECK (min < max)`。`size_system ∈ {alpha, numeric, height_weight, one_size}`。
- **面料成分**：`fabric_composition.materials` 为数组 `[{material, percent, note}]`；DB 层 `CONSTRAINT` 校验「每项 percent 为整数 1–100 且合计 = 100」，`role ∈ {main, lining, trim, accessory}`；`material` 受词表约束（`docs/19`）。
- **来源受限**：`ck_source_kind ∈ {import, erp, manual, platform_sync, supplier}`，**刻意不含任何模型取值**——让「模型产生事实」在物理层不可表示（`docs/06` §2）。
- **版本与失效联动**：任何触碰尺码/成分的变更 → `product.fact_version + 1`，并使所有 `pending` 审批 `invalidated`（`docs/06` §3.1）。尺码表图携带 `data_version`，渲染入参哈希不一致即拒绝发布。
- **平台属性映射**：`platform_attribute_mapping(platform, attr_path, internal_value, platform_value_id, extra)`，`attr_type ∈ {enum, text, number, bool, range, multi_enum}`；`status='stale'` 表示平台字典已变，禁止用 `stale` 映射上架。
- **导入强制校验**：CSV 导入走同一 JSON Schema + 业务校验器；非法尺码/成分**入库即拒**（`422 invalid_fact`），不做「先存后修」。

## 备选方案与放弃理由

| 方案 | 放弃理由 |
|---|---|
| 自由文本/富文本存尺码与成分 | 无法校验、无法渲染、无法申报；图文不一致；模型改写会篡改数值；`docs/00` §16 事实错误率 0 容忍直接不可达 |
| 全部塞进一个 `product.attributes jsonb` | 无法按尺码查询/唯一约束/区间比较；索引不可用；平台映射无处安放；迁移与审计粒度太粗 |
| 只存平台侧属性值（不存内部标准） | 换平台/平台改字典即失去唯一真相；内部尺码体系（`color_id + size_code + fabric_id`）无法与展示名解耦 |
| 用 Excel 母表当事实源 | 版本、并发、审计全无；多人编辑冲突；无法与审批流绑定 |
| 用 LLM 从图片/描述里抽取成分与尺码 | 事实错误率不可控；抽取结果仍需人工复核，等于多一道且无收益（ADR-0010） |

## 影响

| 面向 | 内容 |
|---|---|
| 正面 | 平台驳回中「属性/成分/尺码不符」类问题从根上减少；尺码表图与数据同版本；客服口径与平台申报同源 |
| 正面 | 强类型字段让 L1 规则与判断层可以机械校验（`docs/08`），也是「事实零错误」验收的可执行基础 |
| 代价 | 主数据导入门槛提高：必须按模板填全，历史脏数据需要清洗迁移 |
| 代价 | 新增维度（如「袖型」「厚薄」）需要迁移 + 词表 + 平台映射，不能靠文案临时补 |
| 缓解 | 提供导入模板与校验器（带逐行错误定位）；`draft` 状态允许不完整，`active`（提交上架）时必须全量合法；历史数据用一次性清洗脚本 + 人工抽检 |
| 观测 | 指标：非法尺码/成分入库拒绝数、`size_chart` 版本覆盖率、平台属性驳回率、渲染入参哈希不一致次数 |

## 复审触发条件

- 平台新增必填属性或改变尺码标准（如统一码/国标码切换），需扩字段与词表（`docs/19` 同步更新）。
- 出现新的服装子类目（如鞋、配饰）需要不同测量维度集合，JSON Schema 需分型而非加宽。
- 成分申报从百分比改为分级制或需要检测报告绑定，字段模型需扩展。
- 非法值入库（任一）发生，说明校验被绕过，需评估是否把校验下沉到 DB 触发器。
- 平台属性字典版本化接口可用，可把 `platform_value_id` 的维护从人工改为同步。
