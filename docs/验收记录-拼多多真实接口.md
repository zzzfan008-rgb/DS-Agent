## 一、结论先行

1. **原实现不是按官方文档开发的**，是明确的占位实现（`placeholder-hmac-sha256-v0`），因此**无论填多正确的凭据都连不上**。
2. **现已按官方文档重做**，签名算法用官方示例逐字节验证通过：`E4DE3ED21002510DED352819E7AE6775`。
3. **真实网关已打通**：用无效凭据调用 `https://gw-api.pinduoduo.com/api/router`，227ms 拿到平台真实响应 `error_code=10016 client下线或者clientId不正确`，含平台侧 `request_id`。
4. 这意味着**协议层（网关地址、请求格式、签名结构）是正确的**，只差有效凭据。

## 三、官方签名算法（原文摘录）

来源：基础文档 → 开发文档 → API调用详解
`https://open.pinduoduo.com/application/document/browse?idStr=8EC06C399636041E`

1. 所有请求参数（公共+业务）按**参数名首字母 ASCII 升序**排列
2. 按 `key`+`value` 次序**无缝拼接**（不含任何分隔符）
3. 拼成长串后，**头部和尾部各拼接 `client_secret`**
4. 对该字符串做 **MD5**，密文**转大写**

**官方示例（已做成单测断言）**：
```
client_secret = testSecret
参数: access_token=asd78172s8ds9a921j9qqwda12312w1w21211
      client_id=1, data_type=XML, order_status=1,
      page=1, page_size=10, timestamp=1480411125,
      type=pdd.order.number.list.get
期望 sign = E4DE3ED21002510DED352819E7AE6775
```

## 四、实现与验证

### 4.1 签名（`pdd-signer.ts`）

- `computePddSign(params, clientSecret)`：严格按上述四步
- `buildPddRequestBody(apiType, business, options)`：自动注入公共参数并算 sign
- 空值（`null`/`undefined`/空串）不参与签名
- 数字按十进制原样拼接（与官方示例一致）

### 4.2 单元测试（22/22 通过）

| 测试 | 断言 |
|---|---|
| **官方示例逐字节一致** | `computePddSign(官方参数, 'testSecret') === 'E4DE3ED21002510DED352819E7AE6775'` |
| 参数乱序不影响结果 | 打乱传入顺序，结果相同 |
| sign 格式 | `/^[0-9A-F]{32}$/` |
| 空值不参与 | 带空值与不带空值结果相同 |
| 数字/字符串等价 | `client_id: 1` 与 `'1'` 同签名 |
| secret 首尾拼接 | 不同 secret 产生不同签名 |
| 请求体注入公共参数 | `type/client_id/timestamp/data_type/sign` 齐全 |
| 无 token 时不注入 | `access_token` 不出现 |
| 网关地址 | 与官方一致 |

### 4.3 探针（`pdd-probe.ts`）

把平台响应映射为 7 种可诊断结果，每种带明确处置建议：

| outcome | connectivity | 用户看到 |
|---|---|---|
| `ok` | `ok` | 连接成功 |
| `credential_invalid` | `auth_invalid` | clientId 不正确或应用已下线 |
| `signature_invalid` | `auth_invalid` | 签名校验失败，检查 client_secret |
| `token_invalid` | `auth_invalid` | access_token 无效或过期（24h） |
| `permission_denied` | `auth_invalid` | 应用无此接口权限 |
| `unreachable` | `unreachable` | 网络不通/超时（含网关地址） |
| `unknown_error` | `unknown` | 未分类错误，保留原始码 |

**探针不重试**（重试会掩盖真实问题）、**响应截断 2000 字符**、**失败绝不返回 ok=true**（有专门测试）。

## 六、还差什么才能「配对了就连上」

| 需要 | 说明 |
|---|---|
| **有效的 client_id** | 当前用无效值测试，平台返回 10016。填入真实 client_id 后此错误消失 |
| **有效的 client_secret** | 用于签名。填错会返回签名类错误码 |
| **access_token**（可选） | `pdd.time.get` 可能不需要；若需要授权接口则必须有，有效期 24 小时 |

**填好这三项后，点「测试连接」应当返回 `ok`。** 如果仍失败，探针会明确告诉你是哪一类问题（clientId / 签名 / token / 权限 / 网络），不会含糊。

## 七、接口注册表状态（重要）

`registry/pdd-interfaces.ts` 里 **30 个接口的 `method` 仍是 `null`**，`verification` 仍是 `unverified`。

- 这**不影响**「测试连接」（探针走独立路径，直接用 `pdd.time.get`）
- 但**影响**真实业务调用（上架、改价、订单同步）：`PddClient` 仍会拒绝未核验接口的真实调用

要放开业务调用，需要逐接口把 method/version/path 填实。**建议顺序**：
1. `pdd.time.get`（已用于探针）
2. `pdd.goods.list.get`（只读，验证商品同步）
3. `pdd.mall.info.get`（只读，店铺信息）
4. 订单类（`pdd.order.list.get` 等，注意收件人信息已加密，需走多多云解密）
