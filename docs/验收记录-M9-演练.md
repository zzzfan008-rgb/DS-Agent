## 一、结论先行

1. **kill switch 能止住**：27/27 项通过，其中 8 项是真实 HTTP 写请求被 `503 kill_switch_on` 挡住（不是只验服务对象返回值）。fail-closed 已验证——DB 查询抛错时**阻断**而非放行。

## 三、凭据轮换演练（docs/20 §7、docs/14 §5.4）

### 3.1 方法

起一个**本地 HTTPS 上游**（自签证书，SAN=127.0.0.1）扮演 OpenAI-compatible 供应商，它只接受"当前有效 Key 集合"内的 `Authorization: Bearer`，其余返回 401。然后用真实 API + 真实 registry 代码路径走完整轮换：

1. `provider.credential_ref = m9_cred_v1` → `POST /api/providers/:id/test` 探活成功；
2. `PATCH /api/providers/:id`（带 `If-Match: <version>`）把 `credential_ref` 改成 `m9_cred_v2`；
3. 再探活 → 上游收到的就是新 Key（**下一次请求生效**）；
4. 上游撤销旧 Key → 仍指向 v1 的对照 provider 立刻 401（**旧凭据立即失效**）；
5. 查审计 + 全库扫明文 + 校验审计哈希链。

脚本：`apps/api/test/credential-rotation-drill.mts`。

### 3.4 模拟边界（必须如实登记）

1. **上游是本地 mock**，不是真实 DeepSeek/火山。验的是"凭据选择与传递链路"（选哪个 ref → 解析出哪个 secret → 放进哪个 header），**不是厂商鉴权细节**。
2. **凭据真值存储是进程内 Map**（`DSSAAS_MODEL_CREDENTIALS` 环境变量，`MapCredentialResolver`）。**改这个环境变量本身需要重启**；本次证明的是"切 `provider.credential_ref` 指向新名"这条免重启路径——与 docs/14 §5.4 平台 appSecret 的"`external_key` 指向新键名"同构。
3. **没有真实 Vault / DSH 凭据文件**，也没有真实"双 secret 窗口"。双活窗口用"上游同时接受两个 Key"模拟。
4. 未验证：真实厂商侧的旧 Key 撤销生效时延、24h 错误率观察（`docs/20 §7.2` 第 4 步）、加密导出件与 `recipient_fingerprint`。

### 3.5 演练暴露的缺口（不影响"能轮换"的结论，但上线前应补）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| R1 | **无专用 `credential.rotate` / `credential.revoke` 审计动作**，只有通用的 `provider.update` | 审计检索无法直接筛出"轮换"事件；不满足 docs/20 §7.3 字段要求（旧/新 `fingerprint`） | 补 `credential.rotate` 动作，记录 SHA-256 前 16 位 fingerprint |
| R2 | `credential_ref.last_rotated_at` 代码从不写入（实测 `null`） | 无法做"90 天到期提醒"，轮换周期只能靠人工日历 | 轮换成功时写入该字段 |
| R3 | 生产凭据解析器未接入（当前是环境变量 Map） | 真实部署需 DSH 凭据/Vault，改 Key 的运维步骤与本次不同 | 接入后重跑本演练 |

## 四、性能补测

### 4.1 测量口径（避免与旧数据误比）

| 口径 | 含义 | 与旧数据关系 |
|---|---|---|
| **服务级** | 直接调 `listProducts()`，重复 20 次取分位 | **与 t28 的 44.5ms 同口径**（t28 是单次测量，本次是 20 次 p95） |
| **HTTP 级** | 真实 Fastify + 登录会话 + 网络栈 | 用户实际感受，含鉴权/序列化开销 |

两档数据量在**同一进程、同一参数**下测，只有行数不同。每档测量前脚本会清空自己灌的数据并回填到目标行数——**这一步是必须的**：本脚本首次运行时因未清理，"1,000 条"那轮实际测的是上一轮残留的 10,000 条，两档数字几乎一样（718ms vs 704ms），结论完全错误。修正后才是下面的数据。

数据形态：不只是空商品行——每个商品都挂了 1 条 SKU、1 条 effective 尺码表、1 条 effective 面料、1 条 published listing（10,000 档即 4 万条子行），与真实聚合负载一致。

### 4.2 商品列表：1,000 vs 10,000 条

**两轮独立运行**（每轮都从 0 行重新造数，避免残留污染）。本机波动约 ±10%，故给区间而非单点：

| 数据量 | 子行 | 口径 | p50 | **p95** | p99 | 吞吐 |
|---:|---|---|---:|---:|---:|---:|
| 1,000 | 4,000 | 服务级 | 70.6–74.1ms | **94.0–99.2ms** | 97.0–114.5ms | — |
| 10,000 | 40,000 | 服务级 | 734.7–862.5ms | **885.7–991.5ms** | 922.8–1,097.3ms | — |
| 10,000 | 40,000 | 服务级（无 missing_fields） | 621.3–727.7ms | **728.1–786.3ms** | 748.3–940.1ms | — |
| 1,000 | 4,000 | HTTP 并发 5 | 202.5–208.0ms | **244.3–293.6ms** | 246.6–294.8ms | 22.8–24.1 rps |
| 1,000 | 4,000 | HTTP 并发 20 | 738.2–873.9ms | **878.4–905.8ms** | 947.4–1,158.0ms | 22.5–25.7 rps |
| 10,000 | 40,000 | HTTP 并发 5 | 1,850.2–2,125.1ms | **2,453.6–2,455.3ms** | 2,455.3–2,545.2ms | 2.3–2.5 rps |
| 10,000 | 40,000 | HTTP 并发 20 | 6,311.0–7,547.1ms | **7,012.9–7,629.3ms** | 7,013.0–7,780.2ms | 2.6–3.0 rps |

**与清单项 37 的 44.5ms 对比**：同口径服务级，本次 1,000 条 p95 = **94.0–99.2ms**（44.5ms 是 t28 的单次测量；本次是 20 次 p95，含冷启动与 GC 抖动，量级一致，慢约 2 倍属正常）。**10,000 条 p95 = 885.7–991.5ms，是 1,000 条的 9.4–10.0 倍，而行数正好 10.0 倍——线性关系稳定，不是偶发抖动。**

### 4.3 根因（已定位到具体代码）

`apps/api/src/services/products.ts` 的 `listProducts()`：

```ts
const rows = await deps.prisma.product.findMany({ where, orderBy: { spuCode: 'asc' } });
// ↑ 无 take/skip：把当前筛选下的【全部】商品拉进内存
// 之后 4 条 productId IN (全部 ids) 的批量查询，再在内存里聚合、过滤、slice(limit)
```

`limit` 只在最后 `slice` 时生效，**完全不参与 SQL**。所以 10,000 条就是 10,000 行全表扫 + 4 次 10,000 元素的 `IN` 查询 + 内存聚合。

**逐段实测（10,000 行，单次）**：

| 步骤 | 耗时 | 占比 |
|---|---:|---:|
| `product.findMany`（全字段，10,000 行） | 485.6ms | ~49% |
| `productSku.findMany`（10,000 ids IN） | 64.5ms | ~7% |
| `sizeChart.findMany`（10,000 ids IN） | ~69ms | ~7% |
| `fabricComposition.findMany`（10,000 ids IN） | ~66ms | ~7% |
| `listing.findMany`（10,000 ids IN） | 92.6ms | ~9% |
| 内存聚合 / 序列化 / 其余 | ~200ms | ~20% |

对照实验说明**大头是"取全量行 + 全字段"**：

- 同样 10,000 行，只取列表需要的列（slim select）：217.6ms（降 55%）；
- 走 `$queryRaw` 取 slim 列：95.1ms（降 80%）。

即：**先把 SQL 分页做掉（`LIMIT/OFFSET` 或游标），比换 ORM 或加索引收益大得多**。现有索引已覆盖 `product.spu_code` 唯一索引（`uq_product_spu`），慢的不是索引缺失，是**取数策略**。

### 4.4 影响与建议

| 影响 | 说明 |
|---|---|
| 10,000 条时列表页 p95 约 1s（服务级）/ 2.5s（HTTP 并发 5） | 超过 1s 的用户可感知阈值；并发 20 时 7s，已属不可用 |
| 吞吐从 24 rps 掉到 2.5 rps | 单实例可支撑的并发用户数下降一个数量级 |
| 内存放大 | 每次请求构造 10,000 个对象的聚合 map，是堆外/堆内内存高位（见 `docs/验收记录-M9-压测.md` 第三节 2GB 基线）的诱因之一 |

**建议（按收益排序，均需改业务代码，本次未做）**：

1. **把 `limit` 下推到 SQL**：先按 `spu_code` 游标取 `limit+1` 行，再对这 N 行做 4 条 `IN` 查询聚合。复杂度从 O(全表) 降到 O(page)，10,000 条与 1,000 条将回到同一量级。
2. **`missing_fields` 过滤下推**：当前是"先取全量、内存过滤、再分页"，下推后才能真正走索引。
3. **slim select**：只取列表需要的列（实测降 55%）。
4. 商品量超过 5 万后，考虑 `product_list_view` 物化视图或冗余聚合列。

> 注：以上是**容量风险**，不是当前功能缺陷。当前 1,000 条下 p95 99ms 可接受；但清单项 38 要求 10,000 条数据，按 991ms 判定**不达标**。

### 4.5 DB 连接池压测

**连接池参数**：

| 参数 | 值 | 来源 |
|---|---|---|
| Prisma `connection_limit` | 未显式设置 → 默认 `num_physical_cpus * 2 + 1` = **33**（本机 16 vCPU） | Prisma 默认 |
| Prisma `pool_timeout` | **10s** | Prisma 默认 |
| Postgres `max_connections` | **100** | `pg_settings` 实测 |
| Postgres `superuser_reserved_connections` | 3 | `pg_settings` 实测 |

> 注意：`apps/api` 未在任何地方显式配置连接池（全仓库 `grep connection_limit` 只命中压测脚本），**生产必须显式设置**，否则实例数 × 33 会瞬间打爆 `max_connections=100`（3 个实例就 99）。

**压测结果**（每场景 120 请求，重查询 `/api/products?limit=20&missing_fields=1`，两轮独立运行）：

| 场景 | connection_limit | pool_timeout | 并发 | 成功 | 失败 | 连接峰值 | p50 | p95 | 首个失败点 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 极小池（run1） | 2 | 5s | 40 | 62 | **58** | 2 | 10,035ms | 11,380ms | **5.43s 时 HTTP 500 `internal_error`**（第 101 个请求） |
| 极小池（run2） | 2 | 5s | 40 | 38 | **82** | 2 | 9,250ms | 11,472ms | **5.03s 时 HTTP 500 `internal_error`**（第 106 个请求） |
| 小池 | 5 | 10s | 60 | 120 | 0 | 5 | 16,983–20,850ms | 17,129–20,929ms | 无（全部成功但极慢） |
| 默认池 | 17 | 10s | 60 | 120 | 0 | 17 | 19,004–20,335ms | 19,966–21,128ms | 无（全部成功但极慢） |

> run1/run2 的失败数不同（58 vs 82），但**首个失败点始终落在 5.0–5.4s**，即 `pool_timeout=5s`。失败数量受调度波动影响，失败**时机**由配置决定——这是可复现的结论。

**关键发现**：

1. **第一个失败点 = `pool_timeout` 到期**。两轮都在 **5.0–5.4s** 处首次失败，正好是 `pool_timeout=5s` 加少量调度开销。**失败阈值由 `pool_timeout` 决定，不是由 `max_connections` 决定**——调大 `max_connections` 不会推迟失败，只有调大 `pool_timeout`（或降低单请求耗时）才会。
2. **对外暴露成 HTTP 500 `internal_error`，而不是 503/504**。Prisma 抛 `P2024`（"Timed out fetching a new connection from the connection pool"），`toApiError` 没有对应分支，落到兜底 `internal_error`。已单独复现确认：

   ```text
   HTTP_STATUS 500
   BODY {"error":{"code":"internal_error","message":"服务内部错误","retryable":false,"next_action":"contact_admin"}}
   ```

   **后果**：① 客户端看到 `retryable=false` 不会重试，实际是瞬时可恢复的；② 值班按 500 排查会当成代码 bug，而不是容量问题；③ `next_action=contact_admin` 把容量问题导向人工。
3. **`limit=5` / `limit=17` 都没失败，但慢到不可用**（p50 17–21s）。原因是"排队"而非"拒绝"——池越大排队越长（因为 10,000 条时每个请求本身要 ~1–2s）。**这说明：在当前列表查询复杂度下，调大连接池不解决问题，只会把失败推迟并放大延迟。**
4. **连接峰值精确等于 `connection_limit`**（2/5/17），证明池确实被打满，采样没有失真（用 `application_name` 隔离了被测池与采样连接）。
