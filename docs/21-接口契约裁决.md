## 0. 为什么需要这份文件

文档 06/07/08 与 11/12 由不同执行者并行产出，出现了字段名、枚举值、金额单位、接口入参、作用域建模五类不一致。若不裁决，t8/t9 实现时会出现"数据库一套、接口一套、文档两套"的三方打架，返工成本远高于现在改文档。

**规则**：本文件每一条裁决，都指定"采纳方"与"需修改方"。需修改方必须改到与采纳方一致；不得反向兼容两套写法。

## 1. 金额单位（全局）

| 项 | 裁决 |
|---|---|
| 单位 | **整数分（cent）**，字段后缀统一 `_cents` |
| 废止 | `_micro_cny`（1e-6 元）一律废止，包括 06/07 中 `%10000=0` 的约束说明 |
| 理由 | 平台侧价格以分计；计费以分计；分是人民币最小流通单位，无需再缩放，避免多一层换算错误 |
| 需修改 | 06、07 把 `*_micro_cny` 全部改为 `*_cents` 并删掉 `%10000` 约束；12 统一用 `_cents` |

**模型价格结构**（采纳 07 的嵌套形态，12 改为一致）：

```json
{
  "text":  { "input_per_1k_cents": 1, "output_per_1k_cents": 2 },
  "image": { "per_image_cents": 80, "per_megapixel_cents": 10 },
  "video": { "per_second_cents": 300 },
  "embed": { "per_1k_tokens_cents": 1 }
}
```

调用时把当时的价目快照写入 `model_call_log.price_snapshot`（jsonb），事后调价不影响历史账单。

## 12. 并发与排队语义（补裁决）

`docs/12` §8.3 原文同时出现"全局 8、超出 409"与"全局满则 queued(≤30)"，字面矛盾。裁决如下（以此为准）：

| 情形 | 行为 | HTTP |
|---|---|---|
| 全局并发未满 | 立即执行 | 202（异步）/ 200（同步） |
| 全局并发已满，队列未满（≤30） | 入队，返回排队位置与预计等待 | 202 + `queue_position` |
| 单用户第 3 个并发请求 | 拒绝 | 409 `concurrency_user_limit` |
| 单会话第 2 个并发请求 | 拒绝 | 409 `concurrency_session_limit` |
| 队列已满（>30） | 拒绝 | 429 `queue_full` + `Retry-After` |
| 同一 `Idempotency-Key` 重复提交 | 返回首次结果 | 与原请求一致 |

即：**全局满是排队，不是 409；409 只用于用户/会话级超限；队列满才 429。** 需修改：12 §8.3。

## 13. Peer 身份与 `/connect` 禁用（安全裁决）

| 项 | 裁决 |
|---|---|
| 禁止 | **禁止用 `/connect` 建立业务侧（BFF）Peer**。该入口创建的 API Peer principal 恒为 `owner`，而 owner 调用会跳过 `remoteAccess` 判定，方法级授权被静默绕过 |
| 必须 | 走 Host 内精确路由 + `createPeer({ kind: 'business-api' })` + `typertGateway.stream({ peer, signal })`，且每请求 dispose Peer |
| 理由 | 一旦用 owner Peer，`viewer`/`operator` 的越权保护形同虚设，且审计里看不到真实主体 |
| 验证 | 安全用例 SEC：以 `operator` 身份调用 admin-only 方法必须返回 `remote-access/denied`；日志中 principal 必须为 `business-api` 而非 `owner` |
| 落地 | docs/17 §3.3 已写明；docs/14 的越权用例需覆盖此条；agent-host 实现时必须遵守 |

## 17. 遗留冲突裁决（终局）

| # | 冲突 | 裁决 | 需修改 |
|---|---|---|---|
| 17-1 | `product.pdd_category_id` / `ali_category_id`（06）vs "平台类目走映射表" | **从 `product` 删除这两列**。内部类目用 `product.category_code`；平台类目按 listing 维度记在 `listing.platform_category_id`（同一商品在两个平台类目可以不同）。`platform_category` 表仍是类目字典与资质来源 | 06（§4 字段、§3 上架守则、索引清单） |
| 17-2 | `size_chart` 列名 `size_code`（06）vs `sku_size_code`（21/12/DB） | 统一为 **`sku_size_code`**（数据库已是此名）。语义说明：这一列存的是"这个尺码行对应的尺码编码"，用 `sku_` 前缀是为了和 `product_sku.size_code` 对齐，不代表行属于某个 SKU | 06（唯一约束、索引、规则引用） |
| 17-3 | 图片主图：`product.main_asset_id`（06）vs `listing.main_image_id`（12） | **两个都保留，语义不同**：`product.main_asset_id` 是"商品默认主图"，`listing.main_image_id` 是"这个平台链接当前使用的主图"（PDD 与 1688 可用不同主图）。后者可空，回落到前者 | DB 增列（t12）；06 增补字段；12 保持 |
| 17-4 | 金额类型 `bigint`（06）vs `Int`（DB）vs `int`（21 §10） | **统一 int4（数据库 `Int`）**。理由：Prisma 的 `BigInt` 映射到 JS `BigInt`，`JSON.stringify` 会直接抛错，每个 DTO 都要手写序列化；而 int4 上限 21.47 亿分 = 2147 万元，单条价格/单笔费用远不会触及。**聚合金额（月成本、余额汇总）在 SQL 里 `SUM(...)::numeric` 计算，不落 int8 列** | 06（§1 类型表、§1 金额说明、示例 DDL）；21 §10 |
| 17-5 | 应急开关 `mode(block|drain)`（11）vs `action` 枚举（06/DB） | **两者是正交轴，都要**：`action ∈ {block_writes, block_replies, block_media, block_model, readonly}` 决定"停什么"；`mode ∈ {block, drain}` 决定"怎么停"（立即中断 / 等在途完成）。DB 增 `mode` 列，默认 `block`；`readonly` 与 `drain` 互斥由 CHECK 约束 | DB 增列（t12）；06 增补；11 保持 |
| 17-6 | 8 张支撑表（12 §9.2，含 `listing_write_log` P0）未建 | **建**。`listing_write_log` 是写入门与审计的对账依据，属于 P0，不能等到 M4 再补 | DB 迁移（t12） |

**关于 17-4 的补充**：`video_seconds` 一类度量用 `numeric(10,3)` 不受影响；只有 `*_cents` 走 int4。

**关于 17-1 的补充**：`platform_category` 仍保留 `qualification_requirements` 等资质字段；上架前校验"品类资质是否满足"应查 `listing.platform_category_id` 指向的那一行，而不是商品。
