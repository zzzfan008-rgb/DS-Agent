## 0. 结论先行

1. 三套环境：本地（开发）、预发（staging，平台测试店）、生产（prod）。**预发是生产的同构缩配，不是另一套架构。**
2. 发布只走「构建一次镜像 → 预发验证 → 生产滚动」；禁止在生产机器上 `git pull` 后构建。
3. 回滚以**镜像 tag + 数据库前向兼容**为前提；破坏性迁移必须拆成「扩展 → 双写/回填 → 收缩」三步跨版本发布。
4. 健康检查分两层：`/health` 只证明进程活着（不查依赖），`/ready` 证明能接流量（查 PG/Redis/MinIO/Host/队列）。探针接错会导致「假活」或「雪崩重启」。
5. 告警必须带「阈值来源」：压测基线、平台限流文档、历史 P95、SLA。拍脑袋的阈值等于没有阈值。
6. 备份的价值只在恢复演练里体现；**没有演练记录的备份视为不存在**。
7. DSH 预发布通道（`0.2.1-rc.2`）升级必须月度窗口 + 预发回归 + 卷快照，不允许「顺手升一下」。
8. 交接不是给账号密码，是给「谁能做什么、东西在哪、坏了找谁、还有哪些坑」。

## 2. 部署步骤

### 2.1 首次部署（从零）

```bash
# 1) 准备
git clone <repo> /opt/dssaas && cd /opt/dssaas
cp infra/.env.example infra/.env.prod && chmod 600 infra/.env.prod
# 填写 .env.prod（见第 3 节），生成 KEK：
openssl rand -base64 32   # 写入 DSSAAS_KEK，并离线备份

# 2) 证书与域名（Caddy 自动申请；内网则放自签证书到 infra/tls/）
# 3) 起基础依赖
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml up -d postgres redis minio vault
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml ps
# 3.1) 初始化 Vault：init（5 份 unseal key 离线分持）、unseal、启用 kv-v2、建 AppRole 与最小策略
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml exec vault vault operator init

# 4) 迁移（只由 migrator 角色执行）
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml run --rm api \
  pnpm --filter @dssaas/db migrate:deploy

# 5) 首次初始化：管理员账号、TOTP、模型供应商、平台凭据引用
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml run --rm api pnpm seed:admin
# 按提示在网页完成 TOTP 绑定；平台凭据在「平台连接」页录入（落 credential_ref，backend=vault）

# 6) 起全量
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml up -d
# 7) 验收
curl -fsS https://<domain>/health
curl -fsS https://<domain>/ready | jq .
```

### 2.2 常规发布（镜像不变更配置）

```bash
# 0) 前置：发布单（变更内容、影响面、回滚方案、审批人）
export TAG=$(git rev-parse --short HEAD)
# 1) CI 构建并推送镜像（只在 CI 做）
# 2) 预发部署同一 tag
docker compose -f infra/docker-compose.staging.yml pull
docker compose -f infra/docker-compose.staging.yml up -d --no-deps web api worker
# 3) 预发冒烟（必须绿）
scripts/ci/smoke.sh https://staging.<domain>
# 4) 生产：先迁移（前向兼容），再滚动
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml pull
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml run --rm api \
  pnpm --filter @dssaas/db migrate:deploy
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml up -d --no-deps api worker
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml up -d --no-deps web
# 5) 验证
scripts/ci/smoke.sh https://<domain>
scripts/ops/watch-errors.sh 10m      # 观察 10 分钟错误率/队列/延迟
```

发布窗口与冻结：
- 默认周二/周四 10:00–12:00；大促、平台活动期、月末对账日冻结（除 P0 修复）；
- 冻结期发布需负责人 + 运维双签，并在发布单注明理由。

### 2.3 迁移纪律

| 规则 | 说明 |
|---|---|
| 只增不改 | 已合并迁移禁止编辑；修正用新迁移 |
| 前向兼容 | 新代码必须兼容旧 schema 至少一个版本；破坏性变更拆三步 |
| 三步法 | ① 扩展（加列/表，双写）→ ② 回填（后台任务）→ ③ 收缩（下个版本删旧列） |
| 大表 | 加索引用 `CREATE INDEX CONCURRENTLY`；加列用 `NULL` 默认或分步 |
| 迁移前 | 必须有一次可恢复备份（`scripts/ops/backup.sh --kind pre-migrate`） |
| 迁移后 | 跑 `pnpm db:verify`（行数/约束/索引存在性） |

### 2.4 回滚

| 场景 | 动作 | 注意 |
|---|---|---|
| 应用逻辑问题 | 回滚镜像到上一个 tag：`docker compose ... up -d --no-deps api@sha256:<prev>` | 迁移必须前向兼容，否则不能只回滚镜像 |
| 配置错误 | 回滚 `.env.prod` 到上一版（Git 管理非密钥部分）并重启受影响服务 | 密钥改动走轮换流程，不回滚明文 |
| 迁移破坏 | 用备份恢复到新库 → 切换连接串 → 旧库保留只读 | 必须走变更单；禁止 `migrate down` 在生产 |
| DSH 升级问题 | 回滚镜像 + 恢复 `dsh-data` 卷快照 | 见第 9 节 |
| 平台侧事故 | 开 kill switch，不回滚代码 | 先止血再定位 |

回滚后必须：跑冒烟、核对关键计数（订单/商品/审批）、发通知、写复盘。

### 2.5 启停与常见操作

```bash
# 停止（保留数据）
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml stop
# 启动
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml start
# 重启单服务
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml restart api
# 看日志（最近 200 行，带时间戳）
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml logs -f --tail=200 api worker
# 进容器排查（只读优先）
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml exec api sh
# 清理（危险：会删卷，禁止在生产无确认执行）
# docker compose ... down -v
```

#### 连接池必须显式配置（t51 / M9 P1）

Prisma 未在连接串里写 `connection_limit` 时，默认约为 `num_physical_cpus × 2 + 1`/实例。
常见 16 核机器上就是 **33/实例**：3 实例 = 99 连接，直接顶到 `max_connections=100` —— 到顶后所有请求开始 `P2024`。

**按实例数反推公式**：`connection_limit = floor(max_connections × 0.8 ÷ 实例数)`
（留 20% 给运维连接、迁移任务、监控采集）

| 实例数 | max_connections=100 时建议 connection_limit |
|---|---|
| 1 | 80 |
| 3 | 20 |
| 5 | 16 |

写法（连接串参数，不是独立环境变量）：

```bash
DATABASE_URL="postgresql://dssaas:...@postgres:5432/dssaas?schema=public&connection_limit=20&pool_timeout=10"
API_INSTANCE_COUNT=3
PG_MAX_CONNECTIONS=100
```

启动时 `checkPoolCapacity()` 会校验 `connection_limit × API_INSTANCE_COUNT` 是否超过
`PG_MAX_CONNECTIONS` 的 80%：
- 超了 → 启动日志打 `[pool] WARNING`（**不阻断启动**：池子多大是部署决策，代码不该让服务起不来）；
- 未显式配置 → 同样打 WARNING（提醒默认值不能上线）；
- 实际值写入启动日志的 `pool{connection_limit,instances,effective,pg_max_connections}`，便于事后复盘。

池子耗尽时的对外表现（t51 起）：**HTTP 503 `db_pool_exhausted` + `retryable:true` + `Retry-After: 2`**，
并计入 `dssaas_errors_total{code="db_pool_exhausted"}`。这条指标持续增长 = 该调池子或加实例，
而不是"代码有 bug"（修复前是 500 `internal_error`，正是这个混淆最要命）。

## 4. 健康检查与就绪探针

### 4.1 端点

| 端点 | 检查内容 | 成功 | 失败 | 用途 |
|---|---|---|---|---|
| `GET /health` | 进程事件循环可用（不查依赖） | 200 `{status:"ok",version}` | 5xx | liveness；失败才重启 |
| `GET /ready` | PG `SELECT 1`、Redis `PING`、MinIO `HEAD bucket`、Host 桥接探活、队列 worker 心跳、迁移版本匹配 | 200 明细 | 503 | readiness；失败摘流量 |
| `GET /metrics` | Prometheus 文本 | 200 | — | 监控抓取 |
| Host `GET /internal/health` | Host 存活、preset 目录可读、MCP 工具数、版本 | 200 | 503 | 由 `/ready` 聚合 |
| `GET /version` | 构建版本、commit、DSH 版本 | 200 | — | 排障核对 |

`/ready` 返回示例：

```json
{ "status": "ok", "checks": {
  "postgres": {"ok": true, "latencyMs": 3},
  "redis": {"ok": true, "latencyMs": 1},
  "minio": {"ok": true, "latencyMs": 8},
  "dshHost": {"ok": true, "version": "0.2.1-rc.2", "presetCatalogHash": "ab12…"},
  "queue": {"ok": true, "workers": 2, "oldestJobAgeSec": 4},
  "migration": {"ok": true, "current": "20261020_add_audit_chain"}
}}
```

### 4.2 Compose healthcheck

```yaml
services:
  api:
    healthcheck:
      test: ["CMD", "node", "scripts/healthcheck.mjs", "http://127.0.0.1:4000/ready"]
      interval: 15s
      timeout: 5s
      retries: 4
      start_period: 40s
  dsh-host:
    healthcheck:
      test: ["CMD", "node", "scripts/healthcheck.mjs", "http://127.0.0.1:43180/internal/health"]
      interval: 15s
      timeout: 5s
      retries: 6
      start_period: 90s
```

### 4.3 探针纪律

- liveness 绝不能查数据库：DB 抖动会导致全部容器重启，雪崩；
- readiness 失败只摘流量，不重启；
- 启动期 `start_period` 要覆盖 DSH 插件加载（首次可达 60–90s）；
- 探活请求不写审计、不打业务日志，避免噪声；
- 探活超时统一 5s，失败重试 4 次才判死，避免瞬时抖动误杀。

### 7.2 RPO / RTO

| 场景 | RPO | RTO | 说明 |
|---|---|---|---|
| 单容器故障 | 0 | 5 分钟 | 重启/重建 |
| 数据库损坏 | ≤5 分钟（WAL） | ≤60 分钟 | 恢复到最近可用点 |
| 主机整体故障 | ≤5 分钟 | ≤2 小时 | 新机 + 备份 + DNS 切换 |
| 误删数据 | ≤24 小时 | ≤2 小时 | 依赖全量备份；可配合逻辑导出 |
| 机房级灾难 | ≤24 小时 | ≤8 小时 | 异地备份 + 重建 |

### 7.3 备份脚本（`scripts/ops/backup.sh`）

前置：备份容器已装 `pg_dump`/`age`/`mc`，`mc alias set minio …` 已配置；`BACKUP_AGE_RECIPIENT` 为离线私钥对应的公钥。本脚本是**最小骨架**；生产以 `docs/20` §9 的规格为准（`pg_basebackup` + WAL + manifest + 校验和 + 试恢复）。

```bash
#!/usr/bin/env bash
set -euo pipefail
: "${BACKUP_DIR:?}"; : "${DATABASE_URL:?}"; : "${BACKUP_AGE_RECIPIENT:?}"; : "${DSH_HOME:?}"
ts=$(date +%Y%m%dT%H%M%S)
mkdir -p "$BACKUP_DIR/daily" "$BACKUP_DIR/state"

# 1) Postgres 全量
pg_dump -Fc --no-owner --no-acl "$DATABASE_URL" \
  | age -r "$BACKUP_AGE_RECIPIENT" > "$BACKUP_DIR/daily/db-$ts.dump.age"

# 2) dsh-data（排除密钥）
tar -C "$DSH_HOME" \
  --exclude='secrets' --exclude='.credentials.yaml' \
  -czf - . | age -r "$BACKUP_AGE_RECIPIENT" > "$BACKUP_DIR/daily/dsh-$ts.tar.gz.age"

# 3) MinIO 镜像（mc 已配置别名）
mc mirror --overwrite --remove minio/media backup/media >/dev/null

# 4) 校验与记录
sha256sum "$BACKUP_DIR/daily/db-$ts.dump.age" "$BACKUP_DIR/daily/dsh-$ts.tar.gz.age" \
  > "$BACKUP_DIR/daily/SHA256SUMS-$ts"
date +%s > "$BACKUP_DIR/state/last_success"
# 5) 清理：日备 14 天
find "$BACKUP_DIR/daily" -type f -mtime +14 -delete
echo "backup ok: $ts"
```

要求：
- 脚本失败必须非零退出并触发 A21；
- 每次执行写审计 `ops.backup`（只记时间、大小、校验和，不记内容）；
- 备份件上传到异机/异地后再标成功（`BACKUP_OFFSITE=1` 时）。

### 7.4 恢复步骤

> 恢复是**变更**：必须带 `CHANGE_ID` 与审批记录，脚本缺此项拒绝执行（`docs/14` §2.4）。完整 PITR（基备 + WAL 到目标时间）见 `docs/20` §6；本节是**逻辑恢复**的快速路径（单表/误删）。

```bash
# 1) 宣布事件，冻结写入（开 kill switch 或停 api/worker）
docker compose --env-file infra/.env.prod -f infra/docker-compose.prod.yml stop api worker dsh-host

# 2) 恢复到新库（不要覆盖原库，先并存）
docker compose ... up -d postgres
createdb dssaas_restore
age -d -i ~/.age/backup.key daily/db-<ts>.dump.age | pg_restore -d dssaas_restore --no-owner

# 3) 校验
pnpm db:verify --url postgres://.../dssaas_restore
# 行数、关键约束、迁移版本、审计链、最近订单/商品

# 4) 切换
# 更新 DATABASE_URL 指向恢复库 → 起 api/worker → 冒烟 → 观察 30 分钟
# 5) 保留原库只读 7 天，确认无误后删除
```

### 7.5 恢复演练脚本（`scripts/drills/restore-drill.sh`）

```bash
#!/usr/bin/env bash
set -euo pipefail
# 目标：在隔离 compose 项目中恢复最近备份并验证，不影响生产
PROJECT=dssaas-drill
docker compose -p "$PROJECT" -f infra/docker-compose.restore.yml up -d postgres
# 1) 恢复最新备份到 drill 库
# 2) 跑 db:verify（表数量、关键表行数、外键、审计链）
# 3) 抽样 20 条业务记录与生产只读对比（金额/状态/时间）
# 4) 记录 RTO（从开始到校验通过）
# 5) 通过则写 docs/drills/<date>-restore.md；失败退出 1
```

验收：RTO ≤60 分钟、RPO ≤5 分钟、抽样差异为 0（或全部可解释）；连续两次失败升级为 P0 整改。


回滚后必须：验证 R1–R7、通知使用方、记录「升级失败原因 + 版本差异」。

### 8.5 停更兜底

若 DSH 上游停更或连续两个版本回归失败：
1. 冻结当前可用版本，不再升级；
2. 核心链路不依赖 agent loop：文案/判断/客服草稿可切「直调模型 + 自建工具」降级实现（`docs/17` 第 10 节）；
3. 桥接层保持稳定，前端无感；
4. 在 `docs/04` 登记「版本冻结」与后续替代计划。

## 9. 故障处置 SOP

### 9.1 通用流程

```text
发现 → 定级 → 止血（≤15min）→ 定位 → 恢复 → 观察 30min → 复盘（24h 内）→ 整改（有 owner/期限）
```

| 级别 | 定义 | 响应 | 通报 |
|---|---|---|---|
| P0 | 安全事件、数据丢失、错误写平台 | 立即 | 全员 + 负责人 |
| P1 | 核心功能不可用、批量失败、Host 全挂 | 15 分钟 | 值班群 + 负责人 |
| P2 | 部分功能降级、积压、成本异常 | 1 小时 | 值班群 |
| P3 | 体验问题 | 次日 | 工单 |

止血优先手段：kill switch、暂停队列、切只读、回滚镜像、断开出网。**先停止伤害，再找原因。**

### 9.2 平台限流（429 / 频率超限）

| 阶段 | 动作 |
|---|---|
| 识别 | A5 告警；`platform_calls_total{code="429"}` 上升；adapter 日志有 `Retry-After` |
| 止血 | 暂停该平台写队列；读同步降频到 1/2；必要时开该平台 kill switch |
| 定位 | 查是否批量任务/重试风暴/多实例叠加；核对平台公告的限流变更 |
| 恢复 | 按 `Retry-After` 与令牌桶恢复；从最小并发爬坡（10%→50%→100%） |
| 复盘 | 更新限速配置与批量上限；把平台限流写进 adapter 常量并加测试 |

关键：**不要用加大重试对抗限流**；重试必须带抖动并受全局限速器约束。

### 9.3 平台变更（字段/接口/规则）

| 阶段 | 动作 |
|---|---|
| 识别 | 契约沙箱/夜间任务漂移报告；驳回率突增；错误码从 `platform_reject` 变成解析错误 |
| 止血 | 停用受影响接口（kill switch 按任务类型）；切「导入包 + 人工」兜底路径 |
| 定位 | 对照平台公告与 fixture diff；确认是新增字段、改名、还是规则变化 |
| 恢复 | 更新 adapter + fixture + schema；回放测试；灰度 1 个 SKU→1 个类目→全量 |
| 复盘 | 登记漂移事件；24h 内修复；补回归用例；评估是否需平台侧申诉 |

### 9.4 模型故障（超时/5xx/限流/涨价）

| 阶段 | 动作 |
|---|---|
| 识别 | A11/A12/A13；`model_call_log` 错误率；首 token 延迟上升 |
| 止血 | 按 `model_route.fallback_ids` 切备用模型；关非必要用途（如场景图批量）；草稿走 5 秒降级模板 |
| 定位 | 区分供应商全挂 / 单模型限流 / 密钥失效 / 网络；看供应商状态页 |
| 恢复 | 主模型恢复后按 10%→50%→100% 回切；核对成本 |
| 复盘 | 更新降级链与配额；评估是否需要第二供应商常备 |

### 9.5 队列积压

| 阶段 | 动作 |
|---|---|
| 识别 | A3/A4；最老任务年龄上升；worker 心跳缺失 |
| 止血 | 暂停非关键队列入队（媒体、批量）；优先审批/消息队列；扩容 worker（≤CPU 核数×2） |
| 定位 | 是下游慢（平台/模型）、还是 worker 卡死、还是任务风暴（重复入队） |
| 恢复 | 清理死信、修复 poison message、按优先级重放；观察 30 分钟 |
| 复盘 | 加并发上限、入队去重、批量拆分；补压测场景 |

### 9.6 数据库故障

| 阶段 | 动作 |
|---|---|
| 识别 | A14/A15/A16；`/ready` 的 postgres 失败；连接超时 |
| 止血 | 切只读模式（页面提示）；停 worker 写入；保留连接给健康检查 |
| 定位 | 磁盘满 / 连接耗尽 / 长事务 / 锁等待 / 主库崩溃 |
| 恢复 | 杀长事务 → 扩连接 → 重启 PG → 必要时按 7.4 恢复 |
| 复盘 | 加连接池上限、慢查询告警、长事务自动终止；评估读副本 |

### 9.7 Host / Agent 故障

| 现象 | 动作 |
|---|---|
| Host 进程挂 | 重启容器；`/ready` 失败时网页自动降级（`docs/17` 第 10 节） |
| 流式中断 | 前端显示「生成中断，可重试」；重试幂等，不重复写 |
| MCP 工具全失效 | 检查 server 进程/网络；业务降级为「仅文案生成 + 知识库关键词」 |
| 模型密钥失效 | 按 9.4；管理页显示「未配置/探活失败」 |
| 会话串话 | 立即停 Host、保全日志、按 P0 处理（数据泄露） |

## 11. 变更与发布纪律

| 规则 | 说明 |
|---|---|
| 一切变更留痕 | 代码走 PR，配置走 PR/变更单，数据修复走脚本 + 审计 |
| 生产禁手改 | 禁止直接改数据库、禁止 `docker exec` 改配置；紧急情况先记录再执行 |
| 发布单 | 内容、影响面、回滚方案、验证步骤、审批人，缺一不发 |
| 观察期 | 发布后 30 分钟内值班不离线；P1 以上问题立即回滚 |
| 复盘 | P0/P1 24h 内出复盘；P2 一周内 |
| 文档同步 | 变更涉及运维步骤的，同 PR 更新本文档 |
