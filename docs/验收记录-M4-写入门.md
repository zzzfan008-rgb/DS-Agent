## 3. 写入门时序（代码固定，不可由调用方重排）

```
S1 身份/角色（viewer 拒绝）
S1.5 kill switch 廉价预检（DB，fail-closed）
S2 approval：存在 → action/platform/subject → status → 过期 → 预约窗口
             → target_hash 重算比对 → level 比对 → 四眼（decided_by ≠ requested_by/executor）
             → C 级 confirm_token 存在性
S3 快照：listing_snapshot（snapshot_hash, source=pre_write, fields 本地镜像），失败即停
S4 幂等：L3 write_key（platform+action+target_hash+mode）
         succeeded → 响应回放；in_flight → 409；同键异 hash → 409；failed → 重置重试
S5 kill switch 权威回源 + 滑动窗口限流（120/min）+ listing 并发锁
S6 adapter：PDD PddClient（强制 dry_run）/ 1688 plan()；携带 request_id + write_key
S7 结果分类：retryable/uncertain/manual/permanent/guard → DB 三分类映射
S8 同一 DB 事务：listing_write_log + compensating_ticket（B/C）+ listing 回写 + approval executed
   + idempotency succeeded（缓存响应）+ workflow_run succeeded；事务后写 audit_log
S9 返回 write_id/level/result/platform_response/snapshot_ref/ticket_id/workflow_run_id
```

- 平台写只从 `WriteGate` 发出；adapter 只被 `write-gate/platform-port.ts` import；
- `target_hash` 由服务端用 `canonicalHash` 计算，前端传的 level 一律忽略；
- 幂等键按 docs/11 §5.2 规范化：键排序、去 volatile、NFC/trim、整数、去空值；
- 写前快照失败 → 抛 `upstream_5xx`，不调 adapter；`listing_write_log.restored_from_snapshot` 永远 false。

## 4. A/B/C 分级与审批

- 注册表 26 动作（docs/11 §6.2）映射到 DB `approval.action` 9 个枚举值；级别只由 `computeLevel()` 产生。
- 升级规则：在售 ≥B；活动/主图/类目或关键属性/价格变动>20%/不可逆字段 → C；影响 SKU >20 → ≥B，>200 → C；首次发布且未上线无活动可 C→B（不低于 B）。
- C 级审批：申请人 ≠ 决策人（四眼），决策需 admin；执行人 ≠ 决策人；执行需 confirm_token（5 分钟、一次性、绑定 approval/user/action/target_hash）。
- `timing_advice`：C 级返回 Asia/Shanghai 下一个 02:00–06:00 低峰窗口，提示避开活动/客服高峰。
- SLA：C 60 分钟、B 4 小时、A 8 小时（`sla_due_at`），`GET /approvals?overdue=1` 可查；有效期 C 24h / B 48h / A 72h。
- 审批 `target_hash` 与当前写请求不一致 → `approval_stale`；内容变即失效。

## 5. 工作流、死信与重放

- 7 态：`pending → running → waiting_human/succeeded/failed_retryable/failed_permanent/cancelled`；终态只读，重放新建 run。
- 失败分类：网络/5xx/429→retryable；提交后无回执→uncertain；平台可修复驳回/事实冲突→manual；参数/权限/未核验→permanent；审批/幂等/kill switch/越权→guard。
- DB `error_class` 只有 retryable/manual/permanent（t1 CHECK）；uncertain/guard 保留在 `result.failure_class`。
- 死信：`workflow_dead_letter` 记录 reason/payload/replayable；重放 P1–P6：失败分类/修复、kill switch、审批有效、对账确认、幂等键未被 succeeded、admin+reason。C 级、已产生不可逆副作用、已重放均拒绝。
- 重放方式：新建 `pending` run，`parent_run_id` 指向旧 run，旧 run 终态不变；死信写 `replayed_at`。

## 6. 止损与禁用伪回滚

- 补偿工单：B 级 medium / C 级 high，source=`irreversible_action`，绑定 approval/listing/platform，status `open`；可 claim→`in_progress`→resolve/waive。M4 的 dry-run 工单关闭要求 admin 复核。
- kill switch：global / platform / task_type / category；`block` 优先 `drain`；DB 读取失败 fail-closed；关闭需 admin + `confirm=true`。命中时写入门在 S1.5 即返回 `503 kill_switch_on`，不产生 snapshot/写留痕。
- 伪回滚三层：
  1) `assertReversible(action)`：B/C 动作直接 `IrreversibleActionError`；
  2) 路由先看 `listing_write_log.level`：B/C → `409 irreversible` + `next_action=create_compensation`，并写 `listing.rollback_rejected` 审计（`irreversible=true`）；
  3) rollback body `.strict()`：带 `force` → 422 validation_failed；DB `ck_restore_a_only` 仍兜底。
- 不提供“覆盖写回旧值并声称恢复”的 API；B/C 结果文案只允许“已登记不可逆，正在止损”。

## 7. adapter dry-run 全链路

- PDD：`PddClient` 强制 `dryRun`（`PDD_DRY_RUN=1`），调用 `product.publish` / `price.sku_update` / `stock.update` 等注册表接口，返回 `request_preview`（method/path 仍为 null）与 warnings；`NullArchiver` 避免测试落盘。
- 1688：`Alibaba1688Client.plan('item.publish'|'item.update_price'|...)`，返回 blocked=true、gaps、todoIds，不发网络。
- 写入门响应 `platform_response.status=dry_run`、`adapter`、`interface_key`、`blocked`、`payload_hash`、`contract_unverified=true`；**不把 dry-run 当平台成功**，`mode=full` 仍保留该标记。
- `t9` 用例分别断言 PDD 与 1688 两条通道。

## 10. DB 契约缺口与偏差

| # | 项 | 现状/处理 |
|---|---|---|
| D1 | approval 无 `second_confirm_by` / `payload_patch` / `batch_id` 列 | C 级二次确认改为 `confirm_token`（内存，绑定 approval+user+target_hash）；审批详情不返回 payload_patch/batch |
| D2 | `workflow_run.error_class` 仅 retryable/manual/permanent | `uncertain`/`guard` 映射到 DB 三值，原分类保留在 `result.failure_class` |
| D3 | `kill_switch.scope_type` 仅 global/platform/category/task_type | docs 的 listing/provider 作用域无承载列；用 platform+task_type 近似，缺口待 docs/06 补列 |
| D4 | `compensating_ticket.status` 仅 open/in_progress/resolved/wontfix/escalated | docs 的 assigned/mitigating/verified/closed 8 态未落地；当前 open→in_progress→resolved/wontfix |
| D5 | `audit_log` 无 `compensating_ticket_id` 列 | 工单 id 写 `audit_log.meta.ticket_id` + `compensating_ticket.audit_log_id` 不存在时留空；DB 触发器兜底待补 |
| D6 | audit `irreversible=true` 要求 `after` 含 `operation_level` | 已按 DB CHECK 写入 `operation_level`；非文档字段，登记 |
| D7 | `listing_write_log.action` 是 DB approval 枚举，不是 docs 业务动作码 | 写留痕存 `meta.approvalAction`（publish/update_price/...）；业务动作码在响应/工单/审计 meta 保留 |
| D8 | S8 审计不在平台写同一事务 | audit 走 t2 哈希链独立事务，平台调用后写；事务后 audit 失败无法回滚已发生的平台写 → 需 outbox（docs/11 §7.3）后续补 |
| D9 | 写前快照是本地镜像（无平台 GET） | adapter 只读接口未核验，`capture_source=local_mirror`；接入核验后换平台现值 |
| D10 | batch 只做级别/混批/C 级≤10 校验与 dry-run 计划 | 逐项写与逐项 confirm_token 待 M5 |
| D11 | confirm token/kill switch 缓存为进程内 | 多实例需 Redis（docs/11 §9.2）；当前 fail-closed 语义不受影响 |
| D12 | SLA 只到 `sla_due_at` + overdue 查询 | 无定时升级 worker（100%/200% 升级、值班通知待 worker） |
| D13 | dry-run 工单也会创建 | 为验收工单生命周期；impact.dry_run=true，关闭要求 admin；真实模式只应在平台写成功后建 |
