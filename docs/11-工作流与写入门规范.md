## 1. 不变量（违反即 P0 缺陷）

| # | 不变量 | 校验点 |
|---|---|---|
| I1 | 平台写调用只能从写入门发出，`packages/adapters-*` 不得被其他模块直接 import | 依赖边界 lint（§11.7） |
| I2 | 每次平台写必须携带有效 `approval_id`，且审批对象与目标资源 `payload_hash` 绑定 | 写入门 S2 |
| I3 | 每次平台写必须有幂等键，重复提交不产生第二次外部副作用 | 写入门 S4 |
| I4 | 写前必须有快照；快照失败 → 不写 | 写入门 S3 |
| I5 | 不可逆动作必须有补偿工单，且审计标 `irreversible=true` | DB 触发器 + 写入门 S8 |
| I6 | B/C 级动作不得走"覆盖写回旧值"并声称恢复 | 回滚处理器 + 文案 lint（§11） |
| I7 | 任何写操作 100% 落审计，`request_id` 贯穿 api → worker → adapter → 平台 | 审计抽样对账 |
| I8 | kill switch 命中即停写，fail-closed（守护读取不可用也停写） | 写入门 S5 |

## 2. 三个正交轴（先分清，再看状态机）

| 轴 | 字段 | 取值来源 | 谁改 |
|---|---|---|---|
| 执行状态 | `workflow_run.status` | 引擎内部 | worker / 调度器 / admin |
| 业务相位 | `workflow_run.phase` | 业务定义（按 `workflow_type`） | 写入门与业务步骤 |
| 写操作级别 | `listing_write_log.level` / `approval.level` | 动作注册表 + 判定规则（§5） | 写入门计算，不接受前端传入 |

> 总纲 §9.1 的 `draft → fact_checked → ... → archived` 是**业务相位**；本规范用 `phase` 承载它，用 `status` 承载调度与失败语义。两轴独立演进，映射见 §3.3。

## 3. `workflow_run` 状态机

### 3.1 `status` 全集（14 个）

| 状态 | 含义 | 终态 | 可转移出 | 超时/告警 |
|---|---|---|---|---|
| `pending` | 已创建，未入队（等前置数据） | 否 | `queued`、`cancelled` | 5 分钟未入队告警 |
| `queued` | 已入队待执行 | 否 | `running`、`cancelled`、`paused` | 队列深度告警 |
| `running` | 正在执行某步骤 | 否 | 任意等待态、`retry_wait`、`failed_manual`、`dead_letter`、`succeeded` | 单步超时见 §4.2 |
| `waiting_approval` | 等 L3 人工审批 | 否 | `running`、`cancelled`、`queued`（审批被拒后重来） | SLA 见 §6.3 |
| `waiting_media` | 等素材就绪（`media_job`） | 否 | `running`、`failed_manual`、`cancelled` | 24h |
| `waiting_external` | 等平台回执/异步回调 | 否 | `running`、`retry_wait`、`failed_manual` | 30 分钟无回执 → 对账 |
| `retry_wait` | 可重试失败，等待退避 | 否 | `queued`、`dead_letter`、`cancelled` | 见 §4.2 |
| `paused` | kill switch 或人工暂停 | 否 | `queued`、`cancelled` | 暂停 > 24h 告警 |
| `failed_manual` | 需人工处置（可恢复） | 否 | `queued`（修复后）、`cancelled`、`dead_letter`（转永久） | 4h 未处置升级 |
| `dead_letter` | 超重试上限/毒消息，只读待重放 | **是**（可重放出新 attempt） | `queued`（重放） | 立即告警 |
| `succeeded` | 全部步骤完成 | **是** | — | — |
| `cancelled` | 人工或 kill switch 取消 | **是** | — | — |
| `compensating` | 已发生不可逆写，止损/补偿进行中 | 否 | `compensated`、`failed_manual` | 见 §7 SLA |
| `compensated` | 补偿完成（**不是回滚**） | **是** | — | — |

终态集合：`{succeeded, cancelled, dead_letter, compensated}`。`dead_letter` 允许"重放"生成**新 attempt**（同 `run_id` 下 `attempt_seq+1`），不修改原行的终态结论。

### 3.2 `status` 转移表

| # | from | 事件 | 守卫 | 动作 | to |
|---|---|---|---|---|---|
| S01 | — | 创建 run | 幂等键无冲突（§5）；`workflow_type` 已注册 | 写 `workflow_run`、写 `idempotency_key`（`status=in_flight`） | `pending` |
| S02 | `pending` | 前置数据齐备 | 无阻塞依赖 | 入队 BullMQ（`jobId=run_id`） | `queued` |
| S03 | `queued` | worker 取到 | kill switch 未阻断该 `task_type` | 取运行锁 `wf:lock:{run_id}`（TTL 120s，续租） | `running` |
| S04 | `running` | 步骤要求审批 | 判定级别需要审批（§5.3）且无有效 approval | 建 `approval`（`payload_hash` 绑定）、置 `sla_due_at` | `waiting_approval` |
| S05 | `waiting_approval` | 审批通过 | approval 未过期、`payload_hash` 与当前一致、四眼通过 | 写 `approved_at`、继续下一步 | `running` |
| S06 | `waiting_approval` | 审批被拒 | — | 记拒绝原因、回写修复项 | `failed_manual`（除非策略为直接终止） |
| S07 | `waiting_approval` | 审批过期 | `now > expires_at` | 作废 approval、通知申请人 | `failed_manual` |
| S08 | `running` | 步骤要求素材 | 必需 asset 未齐 | 建/复用 `media_job`，记 `waiting_ref` | `waiting_media` |
| S09 | `waiting_media` | 素材齐备且抽检通过 | `media_ready` 校验通过（10 §10.3） | 清 `waiting_ref` | `running` |
| S10 | `running` | 调用平台异步接口 | 已提交，未得最终回执 | 记 `external_ref`、`reconcile_due_at` | `waiting_external` |
| S11 | `waiting_external` | 回调/轮询确认成功 | 回执与 `external_ref` 匹配 | 清 `reconcile_due_at` | `running` |
| S12 | `waiting_external` | 回执超时 | 30 分钟无回执 | 触发对账（查询平台现值） | `retry_wait`（分类为不确定） |
| S13 | `running` | 步骤失败（可重试） | 分类=retryable（§4.1） | `attempt++`、算退避、记 `last_error_code` | `retry_wait` |
| S14 | `retry_wait` | 退避到期 | `attempt < max_attempt`；kill switch 未阻断 | 重新入队 | `queued` |
| S15 | `retry_wait` | 退避到期 | `attempt >= max_attempt` | 写死信原因、生成重放包 | `dead_letter` |
| S16 | `running` | 步骤失败（需人工） | 分类=manual（平台驳回可修复/事实冲突） | 写 `repair_hints[]`、通知责任人 | `failed_manual` |
| S17 | `running` | 步骤失败（永久） | 分类=permanent（参数非法/资质缺失/明确拒绝） | 释放审批占用、写修复项 | `failed_manual`（标记 `permanent=true`）→ 由人决定是否 `cancelled` |
| S18 | `failed_manual` | 人工修复后重试 | 修复项全部关闭；`payload_hash` 可能变化 → 重新审批 | 新 attempt，重走 S04 | `queued` |
| S19 | 任意非终态 | 用户取消 | 无不可逆写已发生 | 释放锁、置 `cancelled` | `cancelled` |
| S20 | 任意非终态 | kill switch 命中 | 作用域匹配（§9） | 停止调度、保留现场、记 `kill_switch_id` | `paused` |
| S21 | `paused` | kill switch 解除 | 作用域全部解除且人工确认 | 重新入队 | `queued` |
| S22 | 任意非终态 | 不可逆写已发生且需止损 | `level ∈ {B,C}` 且已有 `irreversible=true` 审计 | 建 `compensating_ticket`、通知值班 | `compensating` |
| S23 | `compensating` | 补偿完成并验证 | 工单 `verified` 或 `waived`（admin 签署） | 关闭工单、写复盘链接 | `compensated` |
| S24 | `running` | 全部步骤完成 | 输出齐全 | `idempotency_key.status=succeeded` 并缓存响应 | `succeeded` |
| S25 | `dead_letter` | 重放 | 重放前置条件全满足（§4.5） | 新 attempt、`attempt=0`、保留历史 | `queued` |

### 3.3 `phase`（业务相位，`workflow_type=listing_publish`）

| phase | 含义 | 进入条件 | 出向 |
|---|---|---|---|
| `draft` | 草稿，可编辑 | 创建 | `fact_checked`、`cancelled` |
| `fact_checked` | L1 事实校验通过 | 价格/库存/成分/尺码/政策/资质来源可追溯且一致 | `judged`、`failed_manual` |
| `judged` | L1+L2 判断通过 | 无 blocker；L2 有证据引用 | `media_ready`、`failed_manual` |
| `media_ready` | 素材齐备（含尺码表图同版本） | 10 §10.3 全项通过 | `approved`、`failed_manual` |
| `approved` | 审批通过且未过期 | approval `approved` + 哈希一致 | `publishing`、`failed_manual`（过期） |
| `publishing` | 写入门执行中 | S02–S06 完成 | `published`、`publish_unknown`、`rejected`、`failed_manual` |
| `published` | 平台确认成功 | 回执成功 + 写后核对 | `stop_loss`（后者按需）、`archived` |
| `publish_unknown` | 提交后无回执/超时 | 不确定态 | `published`（对账确认）、`rejected`、`publishing`（重试） |
| `rejected` | 平台驳回 | 平台明确拒绝 | `draft`（修复后重走）、`stop_loss` |
| `stop_loss` | 止损中（不可逆已发生） | B/C 级事故或需先下架再改 | `archived` |
| `archived` | 收尾归档 | 终态 | — |

**相位与状态组合**：`published` 允许 `status=succeeded`；`stop_loss` 期间 `status=compensating`；`publish_unknown` 对应 `status=waiting_external` 或 `retry_wait`。禁止出现"相位 `approved` + `status=succeeded`"这类组合（校验触发器，见 §11.3）。

## 4. 失败分类、重试与死信

### 4.1 失败分类判定

| 分类 | 判定规则（按顺序匹配，先命中先定） | 典型错误码 | 归属 |
|---|---|---|---|
| **retryable** | 网络层错误（`ECONNRESET/ETIMEDOUT/EAI_AGAIN`）、HTTP 5xx、429、平台"系统繁忙"、供应商超时 | `upstream_5xx`、`rate_limited` | 自动重试 |
| **uncertain** | 提交后无回执/连接中断在读响应时/平台返回"处理中"但超期 | `conflict`（sub=unknown） | 先对账再决定（不直接重试写） |
| **manual** | 平台业务驳回且可修复（缺资质、属性不合法、图片不合规、标题违规）、事实冲突（价格/成分与主数据不一致） | `platform_reject`、`invalid_fact` | 人工修 + 重提 |
| **permanent** | 参数结构性错误、类目不存在、账号无权限、商品已删除、动作本身被平台禁止、内容严重违规 | `platform_reject`（sub=fatal）、`forbidden` | 不重试，终止或重开需求 |
| **guard** | 审批失效、幂等冲突、kill switch、配额超限、越权 | `approval_required`、`approval_stale`、`irreversible`、`quota`、`kill_switch_on` | 不重试，回前端给可执行下一步 |

`uncertain` 的处理是**硬要求**：任何"可能已生效"的写必须先查平台现值（`GET` 类只读接口或 `POST /listings/:id/reconcile`），确认未生效才允许重试；确认已生效则按成功处理并补审计。

### 4.2 重试策略

| 操作类型 | 最大尝试 | 退避（第 n 次） | 单次超时 | 说明 |
|---|---|---|---|---|
| 平台写（发布/改价/库存） | 4 | 10s、30s、90s（+抖动 ±20%） | 15s | 仅 retryable；`uncertain` 不计入尝试，先对账 |
| 平台写（批量） | 3 | 30s、120s | 60s | 批量失败按子项重试，成功的子项不重试 |
| 客服消息发送 | 3 | 2s、5s | 8s | 发送前必须先去重占位（§5.5） |
| 素材生成/取回 | 8 | 见 10 §5.3/§5.5 | 见 10 §5.4 | 素材域自治 |
| 同步/对账任务 | 6 | 30s→15min | 120s | 幂等读为主 |
| 审批通知/告警 | 5 | 5s→5min | 5s | 失败不影响主流程 |

**禁止重试清单**（命中即 `permanent` 或 `guard`，不得自动重试）：审批相关、不可逆动作的"补偿类"写、kill switch 相关、删除类操作、C 级操作、平台"重复请求"明确报错、`429` 超过 `Retry-After` 上限（30 分钟）。

### 4.3 超时与看门狗

| 看门狗 | 阈值 | 动作 |
|---|---|---|
| 单步执行 | 步骤定义 `timeout_ms`（默认 60s，平台写 15s，批量 60s） | 中断 → retryable |
| 运行锁续租 | 30s 未续租 | 视为 worker 崩溃，锁过期后由其他 worker 接管（幂等保证安全） |
| `waiting_external` | 30 分钟 | 触发对账 |
| `waiting_approval` | SLA 到期（§6.3） | 升级 + 告警 |
| 整 run | 24h | 置 `failed_manual` 并告警（不自动删） |
| 队列积压 | 同类型 > 100 且最老 > 10 分钟 | 告警 + 降并发 |

### 4.4 死信

`workflow_run.status=dead_letter` 时固定写 `dead_letter` 视图（同一张表的索引视图或独立表 `workflow_dead_letter`）：

| 字段 | 说明 |
|---|---|
| `run_id` / `attempt_seq` | 关联运行与尝试序号 |
| `workflow_type` / `step_name` | 失败位置 |
| `failure_class` / `last_error_code` / `detail` | 机器可读原因 |
| `attempts` / `first_failed_at` / `dead_at` | 时间线 |
| `replay_pack` (jsonb) | 重放所需的最小上下文：`payload_hash`、`approval_id`、`snapshot_ref`、`external_ref`、`idempotency_key` |
| `replayable` (bool) / `blocked_reason` | 是否允许重放 |
| `replayed_by` / `replayed_at` / `replay_run_id` | 重放留痕 |

### 4.5 重放前置条件（全部满足才允许）

| # | 条件 | 校验方式 |
|---|---|---|
| P1 | 失败分类为 `retryable`/`uncertain`，或 `manual` 且修复项已关闭 | `failure_class` + `repair_hints` 全绿 |
| P2 | kill switch 未阻断该 `platform × task_type` | 实时查询 |
| P3 | 审批仍有效（未过期、`payload_hash` 与当前一致） | 重算哈希比对 |
| P4 | 外部状态已对账且确认"未生效"或"已生效但可安全重放" | 强制调用 reconcile |
| P5 | 幂等键可复用（同 key 无 `succeeded` 记录，或已有记录则走响应回放） | `idempotency_key` 表 |
| P6 | 重放操作人角色 = `admin`，且填写 `replay_reason` | 鉴权 + 审计 |

**重放禁止**：C 级写、已产生不可逆副作用的写（必须先走补偿工单，不允许"重放式假装成功"）、平台明确永久拒绝的写、审批已过期且无法重新获取的写。

**重放方式**：`POST /workflow-runs/:id/replay`（治理组，admin），同步返回新 `attempt_seq` 与 `run_id`；底层只是把 `dead_letter` 置回 `queued` 并递增 attempt，不复制业务数据。

## 5. 幂等键构造

### 5.1 四层键

| 层 | 名称 | 构造 | 作用域 | TTL |
|---|---|---|---|---|
| L1 | 业务幂等键 `biz_key` | `sha256("wf\|v1\|" + org_id + "\|" + workflow_type + "\|" + business_key)` | 一次业务诉求（如"上架 SKU X 到 PDD"） | 7 天 |
| L2 | 步骤幂等键 `step_key` | `sha256("step\|v1\|" + run_id + "\|" + step_name + "\|" + step_input_hash)` | 一次步骤执行 | 7 天 |
| L3 | 写幂等键 `write_key` | `sha256("write\|v1\|" + platform + "\|" + action + "\|" + canonical_json(payload))`（**即总纲 §9.2 的 `hash(platform+action+payload)`**） | 一次平台写 | 24 小时（平台侧最长建议 72h） |
| L4 | 消息幂等键 `msg_key` | `sha256("msg\|v1\|" + platform + "\|" + conversation_id + "\|" + outbound_business_key)` | 一条外发消息 | 7 天 |

`business_key` 由调用方给出且必须稳定：商品发布 = `sku_id + ":" + platform`；改价 = `listing_id + ":" + new_price_fen + ":" + effective_at`；批量 = `batch_id + ":" + 子项序号`；素材生成 = 10 §5.7 的 `dedupe_key`。

### 5.2 规范化（canonicalization）规则

| 规则 | 说明 | 反例 |
|---|---|---|
| 键排序 | 所有对象键按 UTF-8 码点升序 | 顺序依赖导致同 payload 两键 |
| 剔除易变字段 | `timestamp`、`nonce`、`sign`、`request_id`、`trace_id`、`retry_count`、`attempt` 不参与哈希 | 每次重试换键 = 重复写 |
| 金额 | 一律整数分，字段名以 `_fen` 结尾 | `"99.00"` 与 `"99"` 不一致 |
| 字符串 | `trim`、NFC 归一化、内部连续空白压成一个空格 | 中文全角空格导致差异 |
| 空值 | `null`、`undefined`、空字符串统一删除该键 | 有无空字段导致键漂移 |
| 时间 | UTC ISO8601 到秒（`2026-10-20T02:00:00Z`） | 本地时区偏移 |
| 数组 | 默认保序；仅对"集合语义"字段显式排序（`sku_ids`、`image_ids` 之外的属性组） | 主图顺序有语义，不得排序 |
| 数值 | 整数不带小数点；浮点禁止出现在业务 payload | `1.0` vs `1` |

实现：`packages/core/src/idempotency/canonical.ts`，单测必须覆盖上表每一行。

### 5.3 存储与冲突

`idempotency_key` 表：

| 字段 | 说明 |
|---|---|
| `key` (PK, char(64)) | 上述哈希 |
| `layer` | `biz` / `step` / `write` / `msg` |
| `scope` | 作用域串（org/run/conversation） |
| `request_hash` | 原始 payload 的规范化哈希（与 key 分开存，便于识别"同键异载荷"） |
| `status` | `in_flight` / `succeeded` / `failed` |
| `response_code` / `response_body` (jsonb) | 响应回放副本（仅 `succeeded`） |
| `resource_type` / `resource_id` | 关联资源 |
| `created_at` / `expires_at` | 清理用 |

| 场景 | 行为 | HTTP |
|---|---|---|
| 同 key + 同 `request_hash` + `succeeded` | 回放缓存响应，头 `Idempotent-Replayed: true` | 原状态码（通常 200/201） |
| 同 key + 同 `request_hash` + `in_flight` | 拒绝并发重复，`Retry-After: 2` | `409 conflict` |
| 同 key + 不同 `request_hash` | 拒绝（内容变了却想复用键） | `409 idempotency_conflict` |
| 同 key 但已过期 | 视为新请求（但写类操作仍受平台侧幂等/对账保护） | 正常执行 |

### 5.4 平台侧配合

| 平台能力 | 适配要求 |
|---|---|
| 平台支持外部请求号（`out_request_id`/`biz_no`） | adapter 必须透传 L3 键（截断到平台长度上限并记录映射） |
| 平台不支持 | 依赖 L3 + 写后核对：调用后 `GET` 现值确认；无法确认则置 `publish_unknown` 走对账 |
| 平台返回"重复请求" | 视为成功（幂等命中），不报错 |

### 5.5 消息去重（客服专用）

发送前 `SADD msg:out:{platform}:{conversation_id}` 存 `msg_key`（NX 语义），成功写 DB 后保留 24h；"发送中"状态占位（`message.status=sending`）防止双击与重复回调；重复发送请求直接返回首次结果（同 §5.3）。

## 6. A/B/C 分级与审批模型

### 6.1 分级定义（对齐总纲 §9.3）

| 级别 | 语义 | 可逆性 | 审批 | 回滚动作 | 允许的补救 |
|---|---|---|---|---|---|
| **A** | 可逆·低风险 | 覆盖写回可恢复 | 常规审批（可按策略自动批） | 写回快照原值（有前置校验，§11） | 覆盖写回 + 审计 |
| **B** | 不可逆·低危 | 不可回滚 | 人工审批 + 提示"提交后不可撤回" | **无回滚**，只有止损 | 补偿工单 + 止损动作 |
| **C** | 高危·不可逆 | 无损回滚不存在 | 红色警告 + 二次确认 + 影响面 + 建议窗口 + 双人（审批人 ≠ 执行人） | **无回滚**，只能先下架/退活动再改 | 补偿工单 + 止损 + 复盘 |

### 6.3 判定规则（在最坏情况下取最高级）

```
level(action, ctx) =
  base = registry[action].level
  // 逐条升级，取 max
  if ctx.listing_state == 'online'      → 至少 B
  if ctx.activity_hit == true           → 至少 C
  if ctx.touches_main_image == true     → C
  if ctx.touches_category_or_key_attr   → C
  if ctx.price_delta_ratio > 0.20       → C
  if ctx.affected_skus > 20             → 至少 B
  if ctx.affected_skus > 200            → C
  if ctx.irreversible_fields.length > 0 → C
  // 允许降级？仅一种：平台无历史状态可影响（首次发布且未上线）
  if ctx.first_publish && ctx.not_online && !ctx.activity_hit → 可降一级（C→B，不低于 B）
  return max(base, 所有命中项)
```

| 判定用例 | 输入 | 结果 |
|---|---|---|
| 未发布草稿改标题 | `online=false`，非主图 | A |
| 在售改标题 | `online=true` | B |
| 在售改价 5% | `online=true`，`delta=0.05` | C（在售改价本身 C） |
| 未上线改价 | `online=false`，`first_publish=true` | A |
| 批量改库存 15 个 SKU | 单次 ≤ 50 件 | A（数量 ≤ 20） |
| 批量改库存 300 个 SKU | `affected_skus=300` | C |
| 活动期改库存 | `activity_hit=true` | C |
| 首次上架（含主图） | `first_publish=true`，`not_online` | B（降一级，主图不降为 A） |

**批量规则**：一次批量请求的级别 = 所有子项级别的最大值；子项级别不一致时**禁止混批**（提示拆单）；C 级批量必须逐项二次确认（每项一个 confirm token），且单批 ≤ 10 项。

### 6.5 SLA、升级与代理

| 级别 | 响应 SLA（进入 pending → 有人认领） | 决策 SLA | 首次提醒 | 升级点 | 终升级 |
|---|---|---|---|---|---|
| C | 10 分钟 | 60 分钟 | SLA 50% | 100% → admin + 值班群 + 看板标红 | 200% → 负责人电话 + 暂停相关自动写 |
| B | 30 分钟 | 4 小时（工作时段） | SLA 50% | 100% → 负责人 | 200% → admin |
| A | 2 小时 | 8 小时（工作时段） | SLA 80% | 100% → 负责人 | 200% → 周报 |

工作时段：`09:00–21:00 Asia/Shanghai`；非工作时段 C 级仍计时（客服/上架值班制），A/B 顺延并在 UI 标注。

**代理审批**：
1. 代理关系由 admin 在设置里配（`delegate_from → delegate_to`，含生效窗口与可代理级别），写 `role.change`（C 级）审计；
2. 代理人决策记 `on_behalf_of`，UI 与审计都显示"张三（代李四）"；
3. 代理人不能是申请人本人（四眼原则），也不能代理自己无权批的级别；
4. C 级默认不可代理；紧急模式（admin 双人确认）下可代理，且必须 24h 内补书面说明。

**批量审批**：
1. 仅允许同 `action + level + platform`，且 `payload_hash` 各自独立；
2. 单批 ≤ 50 项（A/B），C 级 ≤ 10 且逐项确认；
3. 批量决策逐项落 `audit_log`（一项一条，`batch_id` 关联），失败项不阻塞其他项；
4. 批量拒绝必须填统一理由，可对单项覆盖；
5. 批量接口幂等键 = `batch_id`（§5.1）。

**内联审批（消息类 B 级）**：客服/询盘的 `message.send`、`message.send_template` 采取"人工确认即审批"——发送前确认条展示"发送后不可撤回"，发送人点击发送即视为 L3 决策；服务端在同一请求内落一条 `approval`（`requested_by=system`、`decided_by=发送人`、`level=B`、`decision=approve`、`decide_comment="inline confirm"`）并即时写审计。该模式**不适用于** C 级（`inquiry.quote` 仍需独立审批 + 双人 + 确认凭证），也**不适用于**批量发送。

**审批展示必备**（前端不可省略）：事实来源（含版本与时间）、与平台现值 diff、操作级别、影响面、风险点、建议执行窗口、审批有效期倒计时。

## 7. 写入门（唯一写入口）

### 7.1 调用时序（8 步，失败即停）

```
调用方（工作流/审批中心/客服台）
   │  POST /listings/publish | /replies/send | ...
   ▼
S1 身份与角色 ──► S2 approval 校验 ──► S3 快照 ──► S4 幂等检查
                                                       │
                                                       ▼
S8 审计 ◄── S7 结果分类 ◄── S6 平台调用 ◄── S5 kill switch + 限流 + 熔断 + 并发锁
   │
   ▼
S9 回写相位/状态 + 通知 + 指标
```

> 与总纲 §9.2 的差异说明：总纲列"幂等 → 快照"，本文把快照提前到幂等之前。理由：快照失败必须阻止一切写，且快照是幂等键中 `payload_hash` 的对照基准；两项都在"调用前"且互不依赖，顺序调整不改变语义。差异已记入 §13 对齐表。

### 7.2 逐步定义

| 步 | 名称 | 输入 | 校验/动作 | 失败返回 | 是否可跳过 |
|---|---|---|---|---|---|
| S1 | 身份与角色 | session、`request_id` | 认证；角色 ∈ {operator, admin}；`admin` 专属动作校验 | `401 unauthorized`、`403 forbidden` | 否 |
| S2 | approval 校验 | `approval_id`、当前 payload | ① 存在且 `status ∈ {pending, approved, scheduled}`；② `approved`/`scheduled` 未过期；③ 重算 `payload_hash` 与审批一致（**内容变即失效**）；④ `level` 与注册表一致；⑤ 四眼（`decided_by ≠ requested_by`，C 级另需 `second_confirm_by`）；⑥ 预约窗口内 | `approval_required`（缺失）/`approval_stale`（哈希或有效期不符）/`forbidden`（四眼不满足） | 否（A 级可按策略自动生成"系统审批"，仍需落 `approval` 行，`decided_by=system`，可审计） |
| S3 | 快照 | `listing_id`、`platform` | 读平台现值（只读接口）→ 写 `listing.published_snapshot`（含 `snapshot_hash`、`captured_at`、`capture_source`）；读失败按 `uncertain` 处理，**不写** | `upstream_5xx`（快照失败）/`conflict`（现值与审批 diff 基准不一致） | 否 |
| S4 | 幂等检查 | L3 `write_key` | 查 `idempotency_key`；`succeeded` → 回放；`in_flight` → 409；`hash` 不同 → 409 | `conflict` / `idempotency_conflict` | 否 |
| S5 | 守卫与限流 | `platform`、`task_type`、`listing_id` | ① kill switch 双检（§9）；② 令牌桶限流（平台级 + 动作级）；③ 熔断器（连续 5 次 5xx 打开 60s）；④ 并发锁 `lock:listing:{platform}:{listing_id}`（TTL 60s，防并发改同一商品）；⑤ 配额（批量/消息/素材） | `kill_switch_on` / `rate_limited` / `quota` | 否 |
| S6 | 平台调用 | 规范化 payload | 调 adapter → edge-proxy（如需）；携带 `request_id`、L3 键、签名；超时按类型（§4.2）；**只调用一次，不在本层重试** | 由 S7 分类 | 否（dry-run 模式仅演练，不落平台） |
| S7 | 结果分类 | 平台响应/异常 | 按 §4.1 分类 → `retryable/manual/permanent/uncertain/guard`；`uncertain` 立即触发对账；写后核对（若有 `GET` 接口） | — | 否 |
| S8 | 审计 | 全链路上下文 | 写 `audit_log`（含 `irreversible`、`level`、`payload_hash`、`approval_id`、`snapshot_ref`、`request_id`）；不可逆动作**同一事务**内建 `compensating_ticket`；写 `listing_write_log` | 审计失败 → 整笔回滚（`upstream_5xx`，绝不允许"写了但没审计"） | 否 |
| S9 | 回写与通知 | 结果 | 更新 `workflow_run.status/phase`、`listing.platform_state`、`sync_cursor`；发事件（SSE/看板/通知）；更新指标 | — | 否 |

### 7.3 时序约束（代码层强制）

| 约束 | 实现 |
|---|---|
| S2 必须在 S3 之前 | 写入门是单函数 `gateway.write(req)`，步骤顺序写死，不可由调用方重排 |
| S3 与 S6 之间必须有 `snapshot_ref` | 调用 adapter 时强制传 `snapshot_ref`，adapter 签名要求该参数 |
| S8 与 S6 同一数据库事务（审计不丢） | `runner` 用 outbox：平台调用成功后写 `audit_outbox`，事务提交后同步 flush；审计写失败则整笔标记 `audit_pending` 并阻断该 listing 后续写 |
| 不可逆写必须有补偿工单 | 应用层 `assertCompensation()` + DB 触发器双保险 |
| 同一 listing 并发写 | 分布式锁 + `listing.version` 乐观锁，双失败返回 `conflict` |

### 7.4 写入门返回结构

```json
{
  "request_id": "req_01J...",
  "data": {
    "write_id": "01J...",
    "approval_id": "01J...",
    "level": "C",
    "idempotent_replayed": false,
    "result": "success",
    "platform_response": { "listing_id": "PDD-8891", "audit_status": "pending" },
    "snapshot_ref": "01J...",
    "compensating_ticket_id": "01J...",
    "next_action": null
  }
}
```

失败时 `result=failed|uncertain` 且 `next_action ∈ {retry_later, fix_and_resubmit, create_compensation, contact_admin, none}`。

## 8. 补偿工单（`compensating_ticket`）

### 8.1 生命周期

| 状态 | 含义 | 进入条件 | 出向 |
|---|---|---|---|
| `open` | 已创建，待认领 | 不可逆写成功（B/C）或审计标 `irreversible` | `assigned`、`waived`（admin） |
| `assigned` | 已指派责任人 | 值班表匹配 | `mitigating`、`escalated` |
| `mitigating` | 止损动作执行中 | 首个止损动作已下发 | `mitigated`、`escalated` |
| `mitigated` | 止损动作已执行，待验证 | 平台确认或数据核对通过 | `verified` |
| `verified` | 复盘人确认影响已控制 | 第二名人员验证（≠ 执行人） | `closed` |
| `closed` | 关闭 | 证据齐全 + 24h 无新发事件 | — |
| `escalated` | 超时/失败升级 | SLA 超时或止损失败 | `mitigating`、`waived` |
| `waived` | 豁免（风险可接受） | admin 签署理由 + 复核人 | `closed` |

### 8.2 字段

`id, org_id, audit_log_id(FK, 唯一), run_id, level, action, platform, resource_type, resource_id, detected_at, impact_scope(jsonb: sku_ids, order_ids, amount_fen, customer_count), root_cause, mitigation_plan, mitigation_actions(jsonb[]), owner, sla_due_at, status, verified_by, verified_at, evidence_refs[], closed_at, waive_reason, request_id`。

### 8.3 SLA 与关闭判据

| 级别 | 认领 | 首个止损动作 | 验证 | 关闭 |
|---|---|---|---|---|
| C | 10 分钟 | 30 分钟 | 2 小时 | 24 小时（含复盘链接） |
| B | 30 分钟 | 2 小时 | 8 小时 | 72 小时 |

关闭判据（全部满足）：止损动作有平台/系统确认证据；影响面数据已核对（订单/客户/金额）；验证人 ≠ 执行人；复盘文档链接存在；24 小时内无新增同类事件。**不满足不得关闭**，只能 `waived`（需 admin + 理由 + 月报统计）。

## 9. kill switch

### 9.1 作用域与优先级

| 作用域 | `scope_type` | `scope_value` 示例 | 阻断粒度 |
|---|---|---|---|
| 全局 | `global` | `*` | 所有写 |
| 平台 | `platform` | `pdd` / `1688` | 该平台所有写 |
| 平台 × 任务类型 | `platform_task` | `pdd:publish`、`pdd:price`、`pdd:message` | 精准 |
| 类目 | `category` | `pdd:50012345`（叶子类目） | 该类目所有写 |
| 供应商 | `provider` | `img-provider-a` | 该供应商全部模型调用（素材） |
| 单商品 | `listing` | `pdd:8891` | 该 listing 全部写 |

任务类型枚举：`publish`（发布/上下架）、`price`、`stock`、`message`、`media`、`sync`（只读同步可不停）、`batch`。

**匹配优先级**：`listing > platform_task > category > platform > provider > global`；任一命中即阻断，**取最严**（`block` 优先于 `drain`）。

### 9.2 生效方式（必须可验证）

| 环节 | 实现 |
|---|---|
| 权威存储 | Postgres `kill_switch`（`status=on|off`，`expires_at` 可空=永久） |
| 快速读 | Redis `ks:v1:{scope_type}:{scope_value}`，值为 JSON，TTL = `min(expires, 300s)` 并每 60s 刷新 |
| 本地缓存 | 进程内 1 秒缓存；失效通过 Redis pub/sub `ks:invalidate` 广播（各实例订阅后清本地） |
| 检查点 | 写入门 S1.5（廉价预检）与 S5（权威，含 DB 回源）双检 |
| fail-closed | Redis 不可用且 DB 读超时 → **阻断所有写**，返回 `kill_switch_on` 且 `detail.guard="unavailable"`；读路径不受影响 |
| 撤销 | admin 关闭后 10 秒内全实例恢复；`drain` 模式允许在途写完，禁止新取任务 |

### 9.3 语义：`block` vs `drain`

| 模式 | 行为 | 适用 |
|---|---|---|
| `block` | 立即拒绝新写，在途写也中断（已发出的不撤回） | 平台风控、账号异常、批量事故 |
| `drain` | 停止取新任务，在途任务跑完 | 计划内变更、模型切换 |

### 9.4 演练与留痕

- **季度演练**：在沙箱平台（或 dry-run 模式）开 `platform_task=pdd:publish`，验证"开 → 生效 ≤ 10s → 写被拒 → 关 → 恢复"；记录到 `audit_log`（`action=kill_switch.drill`）与演练报告（交付物 `16`）。
- 所有开关动作（开/关/改作用域）都是**审计事件**，并由 SSE 广播到前端横幅（运营看板与上架页顶部常驻提示）。
- 开 kill switch 属 A 级（防护动作，立即生效），但**关闭**必须是 admin 且二次确认（误关会恢复自动写）。

## 10. 止损动作清单与执行时序

### 10.1 场景 → 止损动作

| 场景 | 首选止损 | 级别 | 审批 | 时限 | 成功判据 |
|---|---|---|---|---|---|
| 错价已生效（C） | 先退出活动 → 改回"标价"（作为**新写**，非回滚）或紧急下架 | C | 紧急模式：admin 一键 + 事后补审 | 30 分钟 | 平台价正确 + 无活动价残留 |
| 主图误换（C） | 下架 → 恢复原主图（新写）→ 重新上架 | C | 同上；须记录"未使用伪回滚" | 30 分钟 | 平台主图正确 + 重新审核通过 |
| 类目/关键属性误改（C） | 下架 → 提交资质/属性修复 → 重新提交审核 | C | 紧急模式 | 2 小时 | 审核通过或明确拒绝原因 |
| 批量误操作（C） | 立即 `kill_switch(batch, block)` → 逐项核对 → 差异项下架 | A（开关）+ 逐项 C | 开关即时；逐项补审 | 15 分钟（先止血） | 写入口零新增 + 差异清单闭合 |
| 客服消息误发（B） | 停止该会话自动回复 → 发补偿话术 → 建工单 → 视情况升级人工/主管 | B | 模板话术可预批（`compensation_script` 白名单） | 15 分钟 | 客户已收补偿 + 工单登记 |
| 报价错误（C） | 撤回/作废报价（平台支持则撤回）→ 重新报价 → 通知分销商 | C | 紧急模式 | 30 分钟 | 新报价生效 + 客户确认 |
| 平台驳回（B） | 按 `repair_hints` 修复 → 重新提交 | B | 重新审批（内容变） | 4 小时 | 重新发布成功 |
| 平台风控/限流 | `kill_switch(platform, block)` + 降速 + 告警 | A | 即时 | 5 分钟 | 写入口静默 + 限流恢复 |
| 素材问题（B/C） | 隔离素材 → 平台侧替换/下架 → 重新生成 | B | 按替换位置定级 | 1 小时 | 平台素材正确 + 抽检通过 |

### 10.2 执行时序（以 C 级事故为例）

| 时刻 | 动作 | 责任人 | 留痕 |
|---|---|---|---|
| T+0 | 告警触发（指标/人工） | 系统 | `audit_log` + SSE |
| T+1 min | 值班确认事故等级，拉群 | 值班 admin | 事件号 |
| T+2 min | `kill_switch` 阻断同源写（防扩大） | 值班 admin | `kill_switch` + 审计 |
| T+5 min | 判定止损路径（下架优先 vs 先退活动） | 值班 admin + 运营 | 决策记录 |
| T+10 min | 执行首个止损写（走写入门，紧急审批通道） | operator | 写入门审计 + 快照 |
| T+15 min | 平台侧确认（截图/接口回读） | 运营 | `evidence_refs` |
| T+20 min | 客服口径下发（补偿话术） | 客服主管 | 模板版本 |
| T+30 min | 补偿工单 `mitigated` → 通知客户 | 客服 | 工单 |
| T+2 h | 影响面核对（订单/金额/客户） | 运营 | 工单 `verified` |
| T+24 h | 复盘会 + 修复项进 backlog | 负责人 | 复盘文档 |
| T+72 h | 工单 `closed` | 负责人 | 关闭证据 |

**紧急审批通道**：仅 C 级事故可用；由 admin 发起，需 `second_confirm_by`（另一名 admin/负责人）+ 30 字理由；通道开启期间所有写仍走写入门与审计，只是把 SLA 从 60 分钟压到 5 分钟；通道 2 小时后自动关闭。

## 11. 禁止伪回滚：代码层约束

> 定义：**伪回滚** = 用旧快照覆盖写回，然后对外声称"已恢复原状"。平台侧不可逆（重新审核、权重、活动掉线、消息已达）使这个声明为假。

### 11.1 唯一判定源

```ts
// packages/core/src/action-registry.ts
export type Reversibility = 'reversible' | 'irreversible' | 'irreversible_high';
export const ACTION_REGISTRY = {
  'listing.update_stock':        { level: 'A', reversibility: 'reversible',         snapshot: ['stock'] },
  'listing.update_price':        { level: 'C', reversibility: 'irreversible_high',  snapshot: ['price_fen','activity_price_fen'] },
  'listing.replace_main_image':  { level: 'C', reversibility: 'irreversible_high',  snapshot: ['main_image_id'] },
  'message.send':                { level: 'B', reversibility: 'irreversible',       snapshot: [] },
  // ...
} as const satisfies Record<string, ActionMeta>;
```

### 11.2 具体阻止手段（逐层，缺一不可）

| # | 层 | 约束 | 违反后果 |
|---|---|---|---|
| 1 | 类型 | `rollback()` 只接受 `ReversibleAction`（branded type）；`irreversible*` 动作在类型层无法传入 | `tsc` 失败 |
| 2 | 运行时 | `assertReversible(action)`：registry 查表，非 `reversible` 立即抛 `IrreversibleActionError` | 500 → 映射 `irreversible` |
| 3 | API | `POST /listings/rollback` 对 B/C 动作返回 `409 irreversible` + `next_action=create_compensation`；请求体不接受 `force` | 调用被拒 |
| 4 | 前置校验 | A 级回滚必须：① 平台现值 == 该次写后哈希（`expected_current_hash`）；② 该上市品此后无依赖写（`listing_write_log` 链检查）；③ 在 24h 窗口内 | `409 conflict`，不做盲覆盖 |
| 5 | 写入门 | 回滚请求同样走 S1–S9，`action=listing.restore_snapshot`；`approval` 必须指明 `reason=reversible_restore` | 无法绕过 |
| 6 | DB CHECK | `listing_write_log`：`CHECK (level = 'A' OR restored_from_snapshot = false)`；`audit_log`：`irreversible=true` 时 `compensating_ticket_id` 非空（延迟约束 `DEFERRABLE INITIALLY DEFERRED`） | 插入失败 |
| 7 | DB 触发器 | `BEFORE UPDATE` 拦截 `restored_from_snapshot=true` 且 `level<>'A'`；`AFTER INSERT` 对 `audit_log(irreversible=true)` 自动建工单（兜底） | 事务回滚 |
| 8 | 依赖边界 | adapter 仅可被 `packages/write-gateway` import（`eslint-plugin-boundaries` + `dependency-cruiser` 规则） | CI 失败 |
| 9 | 契约测试 | 动作 × 可逆性矩阵：每个 B/C 动作断言"不存在可调用的回滚路径"；registry 改动未同步测试 → CI 失败 | CI 失败 |
| 10 | 文案 lint | 前端 i18n 文案黑名单：不可逆动作的结果页禁止出现"已回滚/已恢复/已还原"；允许"已止损/已登记/已补偿"（CI 扫描 `apps/web/messages/*.json`） | CI 失败 |
| 11 | 二次确认凭证 | C 级执行前需服务端签发 `confirm_token`：绑定 `payload_hash + user_id + 5 分钟 TTL`，一次性；不经服务端签发无法执行 | 无法伪造 |
| 12 | 指标告警 | 任何 `listing.restore_snapshot` 命中 B/C 字段（即使被拒）→ P0 告警 + 值班核查 | 事后追责 |

### 11.3 数据库约束（可直接落迁移）

```sql
-- 1) 不可逆写必须挂工单
ALTER TABLE audit_log ADD CONSTRAINT ck_irrev_ticket
  CHECK (NOT irreversible OR compensating_ticket_id IS NOT NULL)
  DEFERRABLE INITIALLY DEFERRED;

-- 2) 只有 A 级允许"覆盖写回快照"
ALTER TABLE listing_write_log ADD CONSTRAINT ck_restore_a_only
  CHECK (level = 'A' OR restored_from_snapshot = false);

-- 3) 相位与状态组合合法性（防"approve 了就直接 succeeded"）
ALTER TABLE workflow_run ADD CONSTRAINT ck_phase_status
  CHECK (
    NOT (phase = 'approved' AND status IN ('succeeded','compensated'))
  );

-- 4) B/C 动作不得有 restore 记录（触发器兜底）
CREATE OR REPLACE FUNCTION forbid_pseudo_rollback() RETURNS trigger AS $$
BEGIN
  IF NEW.restored_from_snapshot AND NEW.level <> 'A' THEN
    RAISE EXCEPTION 'pseudo-rollback forbidden for level %', NEW.level
      USING ERRCODE = '23514';
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_forbid_pseudo_rollback BEFORE INSERT OR UPDATE
  ON listing_write_log FOR EACH ROW EXECUTE FUNCTION forbid_pseudo_rollback();
```

### 11.4 回滚的正确表述（前端强制）

| 情况 | 允许文案 | 禁止文案 |
|---|---|---|
| A 级且校验通过 | "已恢复为变更前的值（可逆操作，已核对平台现值）" | "已回滚"（单独使用） |
| B/C 已执行 | "已登记不可逆操作，正在止损：{动作}" | "已回滚""已恢复""已还原" |
| 补偿完成 | "止损完成，影响面已核对" | "已恢复原状" |

## 13. 与总纲的对齐与差异

| 项 | 总纲 | 本文 | 说明 |
|---|---|---|---|
| 写入门步骤顺序 | approval → 幂等 → 快照 → 限流 → 调用 → 分类 → 审计 | approval → **快照** → 幂等 → 限流 → 调用 → 分类 → 审计 | 两项均在调用前、互不依赖；快照失败必须阻断（§7.1 说明） |
| `workflow_run` 状态 | 用一条业务链描述（`draft→…→archived`） | `status`（引擎）+ `phase`（业务）双轴 | 总纲示例链落在 `phase`（§3.3） |
| 回滚语义 | A 覆盖写回；B/C 只能止损 | 同，并给出 12 条代码级阻止手段 | 新增实现细节，不改结论 |
| 不可逆登记 | `audit_log.irreversible` + 补偿工单 | 同，加 DB CHECK/触发器强制 | 增强 |
| 死信 | 超时进死信并可重放 | 同，加重放 6 条前置条件与禁止清单 | 增强 |
