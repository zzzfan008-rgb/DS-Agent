## 8. t11 默认值修补（2026-10-20）

### 8.1 缺陷

QA 静态门禁发现：`workflow_run.state` 的 DEFAULT 写成了 `'queued'`，而 `docs/21` §2 的 7 态词表是
`pending | running | waiting_human | succeeded | failed_retryable | failed_permanent | cancelled`，
迁移里的 `ck_workflow_state` 只允许这 7 个值。后果：任何省略 `state` 的 INSERT 必然违反 CHECK（t2 一插入就炸）。

根因：t1 第一版 schema 沿用 `docs/06` §3.5 的旧状态机默认值（`queued`），按 `docs/21` 改 `state` 词表时只改了 CHECK，漏改 DEFAULT。

### 8.2 修改点

| 文件 | 行 | 修改前 | 修改后 |
|---|---|---|---|
| `packages/db/prisma/schema.prisma` | 776 | `state String @default("queued")` | `state String @default("pending")` |
| `packages/db/prisma/migrations/20261020142000_init/migration.sql` | 721 | `"state" TEXT NOT NULL DEFAULT 'queued'` | `"state" TEXT NOT NULL DEFAULT 'pending'` |

**为什么直接改原迁移而不新增 ALTER**：该迁移只在 t1 验收时的一次性 `pgvector/pgvector:pg16` 容器上执行过（容器已删除）；
本机 `localhost:5432` 的 Postgres 认证失败、并非本项目库；没有共享/开发库执行过本迁移。
因此直接改原文件，避免「迁移历史 + schema」两处不一致；若后续任一环境已执行过该迁移，应改为新增 `ALTER TABLE ... ALTER COLUMN ... SET DEFAULT`。

### 10.2 第 3 条为何用 CHECK + 触发器「双保险」

- **同行规则用 CHECK**：`status` 与 `platform_category_id` 的关系只涉及同一行，CHECK 可精确表达；它在语句层原子生效，对 Prisma、raw SQL、运维脚本等**全部写入方**一致生效，不受触发器触发时机/顺序影响，且应用层可用同一表达式预判并给出可读错误。
- **跨表规则留在触发器**：`platform_category.platform = listing.platform` 需要查另一张表，CHECK 无法表达，保留 `trg_listing_category_platform`。
- 两者互补：触发器覆盖 `platform`/`platform_category_id` 变更，CHECK 覆盖 `status` 进入 `publishing/published` 的变更；应用层校验只负责友好报错，不替代 DB。

## 11. size_chart 唯一索引修复（t17，2026-10-20）

### 11.1 缺陷

旧索引把「一个商品只能有一行 effective」当成约束，与「一尺码一行、一个版本多行」冲突：

```sql
-- 修复前（错误）
CREATE UNIQUE INDEX uq_size_chart_effective ON size_chart (product_id)
  WHERE status = 'effective' AND archived_at IS NULL;
```

后果：同一商品同一生效版本插入第 2 个尺码（M、L）即唯一冲突 → **多码商品无法创建**（t8 实测挂住）。
`docs/21` §6 的口径是版本内唯一（`product_id, version_no, size_code`）；旧实现与之矛盾。

### 11.2 修复（additive 迁移）

迁移：`prisma/migrations/20261020160000_size_chart_effective_fix/migration.sql`（39 行）+ `down.sql`（12 行）。
未改 t1/t12/t13 迁移，未改列语义。

```sql
-- 修复后
DROP INDEX IF EXISTS uq_size_chart_effective;          -- 删掉 (product_id) 唯一
CREATE EXTENSION IF NOT EXISTS btree_gist;             -- EXCLUDE 约束依赖

ALTER TABLE size_chart
  ADD CONSTRAINT ex_size_chart_one_effective_version
  EXCLUDE USING gist (product_id WITH =, version_no WITH <>)
  WHERE (status = 'effective' AND archived_at IS NULL);
```

**为什么没有采用任务书原定的 `UNIQUE (product_id, version_no) WHERE effective`**：同版本多码的
`product_id + version_no` 完全相同，该唯一索引会再次挡住 M/L/XL（行为验证 #1 会失败）。
`EXCLUDE` 的语义正好是「同一 product 下 version_no 必须相同」——即一个商品只能有一个 effective 版本，
而同一版本内允许多行（多码）。保留 `uq_size_chart (product_id, version_no, sku_size_code) WHERE archived_at IS NULL`
负责版本内尺码唯一。

触发器 `check_sku_size_exists()` **未改**：它查询「该 product 存在 `status='effective' AND archived_at IS NULL`
且 `sku_size_code = NEW.size_code` 的行」，在 EXCLUDE 约束保证唯一生效版本后语义正确；已用「SKU 尺码 S 不在
有效尺码表 → 23514」验证。

文档侧已由 captain 同步：`docs/06 §4.2.3`、`docs/06 §5.1 #6`、`docs/12 §9.2` 均改为
`ex_size_chart_one_effective_version`（exclude/gist）表述，并注明旧 `(product_id)` 唯一索引已删除。

**回填 SQL（18-1）**：

```sql
ALTER TABLE product_sku ADD COLUMN fabric_code TEXT;
UPDATE product_sku s
SET fabric_code = f.fabric_code
FROM fabric_composition f
WHERE f.id = s.fabric_id;
-- 断言：任何一行未回填则整笔迁移失败
ALTER TABLE product_sku ALTER COLUMN fabric_code SET NOT NULL;
```

**回填是否有歧义（captain 提问）**：没有。`fabric_id` 是 uuid 外键、指向 `fabric_composition` 的**唯一一行**，
`JOIN f.id = s.fabric_id` 是一对一取值，不存在「同 fabric_id 多行」的情况。所谓「同一面料多版本」是
**多行共享同一个 `fabric_code`、`version_no` 不同**；无论 SKU 原 `fabric_id` 指向哪一版，回填出的
`fabric_code` 都相同（这正是 §18-1 要的稳定身份）。迁移内另有 DO 断言：若出现 `fabric_code IS NULL`
（即 `fabric_id` 找不到 `fabric_composition` 行），迁移直接报错、整体回滚；原列 `NOT NULL + FK` 下正常不会发生。

### 17.3 kb_document.source_ref 结论：**确认无需新增列**

核对 schema：`kb_document` 已有 `source_type` / `source_id`（uuid, nullable）/ `uri`（text, nullable），**没有 `source_ref` 列**；`backend-api` 的知识库服务已按以下方式实现（`apps/api/src/knowledge/service.ts`）：

- 注释明确：「**不改 schema**：`source_ref` 存 `kb_document.uri`，并派生稳定 `source_id = uuidv5(source_ref)`」；
- 实际代码：`const sourceId = uuidv5('kb:' + sourceType + ':' + sourceRef)`（第 293 行），写库时 `uri: sourceRef`（第 421 行）；
- 唯一键（t19 已收紧）：
  - `uq_kb_doc (org_id, source_type, source_id, version_no) WHERE archived_at IS NULL AND source_id IS NOT NULL` —— 同一来源的版本唯一；
  - `uq_kb_doc_active (org_id, source_type, source_id) WHERE status='active' AND archived_at IS NULL AND source_id IS NOT NULL` —— 同一来源最多一个 active 版本。

为什么这满足「来源标识 + 版本」与幂等：

1. `source_ref` 是外部系统的**不透明字符串**；`uri` 原样保存它（可追溯、可人工核对），长度由服务层归一化/截断到 500 字符；
2. `uuidv5(sourceType + sourceRef)` 是**确定性**映射：同来源字符串永远得到同一 `source_id`，因此重复导入做的是同一 doc 的版本推进/active 切换，而不是新建重复文档；
3. 版本由 `version_no` 表达，`uq_kb_doc` 保证 `(来源, 版本)` 唯一；`uq_kb_doc_active` 保证同来源只有一条 active；`source_id IS NOT NULL` 条件让手工文档（无外部来源）不参与唯一（docs/21 §18-5）；
4. 若未来需要按 `source_ref` 原文前缀检索/展示，`uri` 已可查（无索引），无需为「唯一性/幂等」再加列；`source_ref` 列只会与 `uri` 重复存储。

**决定：不加 `source_ref` 列、不加索引。** 已在 docs/06 §4.9.1 的 `uri` 行注明「外部来源 `source_ref` 也存此列，`source_id=uuidv5(source_ref)` 由应用派生」。

已知边界：`source_id` 依赖 `source_ref` 字符串的稳定性；若外部系统改变引用格式（如加前缀/改大小写），会映射成新文档。该约定由知识库服务负责（sourceRef trim + 固定 namespace），不属 DB 约束能覆盖的范围。
