## 2. 同步游标（`sync_cursor`）

### 2.1 使用的列（docs/06 §4.5.2 / Prisma `SyncCursor`）

| 列 | 用途 |
|---|---|
| `platform` / `shop_id` / `resource` | 唯一键 `(org_id, platform, shop_id, resource)`；resource ∈ `products/orders/messages/after_sale/stock` |
| `cursor` | 平台游标（录制样本为 `ck-orders-1/2`，仅验证机制） |
| `watermark_at` | 已消费水位 |
| `last_run_at` / `last_success_at` | 运行/成功时间；`GET /sync/status` 的 `lag_seconds` 依据 |
| `consecutive_failures` / `status` / `error_code` | 连续失败 ≥5 → `status='error'`（docs/06 要求） |
| `lease_owner` / `lease_until` | 单实例消费（抢占式租约，防并发重复跑） |
| `stats` | `{pulled, created, updated, skipped}`；`orders` 有真实 sink，会填 created/updated/skipped；其余资源只填 `pulled` |
| `page_size` | 每页条数（默认 100） |

### 2.2 行为

- **断点续跑**：每读完一页立即 `checkpoint(cursor, watermark_at, stats)`；进程中断后下一次从 `cursor` 继续。
- **并发**：`tryAcquire` 用 `UPDATE ... WHERE lease_until IS NULL OR lease_until < now()` 抢占；拿不到租约返回 `409 conflict`（docs/12 §3.9）。
- **失败**：记录 `error_code`、`consecutive_failures+1`、释放租约；保留最后成功游标。
- **落库（t43）**：`orders` 资源接 `PrismaOrderSink`，逐页写 `orders` + `order_items`：
  - 幂等键 `(platform, platform_order_id)`（唯一索引 `uq_order_platform ... WHERE archived_at IS NULL`）；
  - 明细按 `(order_id, platform_sku_ref)` upsert（`uq_order_item`），**不删除**（平台可能漏传）；
  - `buyer_ref` 必须是 **sha256 hex（64 位小写）** —— DB 硬 `CHECK ck_order_buyer_ref_hash`，明文昵称/手机号会被 23514 拒绝，服务层先做一次校验给出 422 而不是 500；
  - 订单状态受 `ck_order_status` 约束（`pending/paid/shipped/delivered/completed/refunding/refunded/cancelled`），未知状态直接拒绝（不把平台新状态静默写坏）；
  - 响应 `dry_run`：有 sink → `false`（真实落库）；无 sink → `true`（只推进游标）。
- **`after_sale` 落库（t49）**：`PrismaAfterSaleSink` 写 `after_sale`，幂等 `(platform, platform_after_sale_id)`：
  - **t50**：`orders` 同步写入新订单后，会自动重放 pending 售后（不推进 after_sale 游标），见 §15；
  - 关联订单按 `(platform, platform_order_id)` 批量查（一次查询，无 N+1）；
  - **本地缺订单时 `order_id` 写不进去**（NOT NULL + FK RESTRICT，不改 schema 就无解）→ 计入
    `stats.pending` 与 `pending_reasons={order_missing:N}`，**不丢弃**；对账的 `after_sale_platform_only`
    继续把它报出来，等 `orders` 补齐后重跑即可落库；
  - `kind` 与 DB `ck_after_sale_kind` 对齐（未知值 422 而非 500）；`closed_at` 由状态推导，不编造时间。
- **其余资源只推进游标**：`products/messages/stock` 暂无 sink（表/契约未就绪），`dry_run=true`。
- **真实 reader 硬拒绝**：`RECONCILE_READER/SYNC_READER=adapter` 时抛 `publish_blocked`（409），detail 带 `reason=adapter_contract_unverified` 与 TODO 列表（1688：`TODO-1688-*`；PDD：`TODO-PDD-CONTRACT-VERIFY`）。

### 3.2 订单维度（5 类，t43）

本地表：`orders` + `order_items`（t37）；平台侧：快照 `orders[]`（含 `items[]`）。

| 类 | 判定 | 本地样例 | 平台样例 | 严重级 | `suggested_action` |
|---|---|---|---|---|---|
| `order_platform_only` | 平台有、本地无 | — | `ALI-ORDER-1003` shipped / 15800 分 | high | `{level:null, kind:manual}` |
| `order_local_only` | 本地有、平台无 | `ALI-ORDER-1002` paid / 9999 分 | 快照中不存在 | high | `{level:B, kind:manual}` |
| `order_amount_mismatch` | `total_cents` 或 `paid_cents` 不符 | `ALI-ORDER-1004` total/paid 31600 | total/paid 30000 | high | `{level:B, kind:manual}` |
| `order_status_mismatch` | 订单 `status` 不符，**或** 退款状态不符（两侧都非 null 才比） | `ALI-ORDER-1005` paid + refunding | refunded + refunded | high | `{level:B, kind:manual}` |
| `order_item_mismatch` | 明细按 `platform_sku_ref` 对齐后：缺失 / `qty` 不符 / `unit_price_cents` 不符 / `amount_cents` 不符 | `ALI-ORDER-1006` SKU-0001 qty 1 @31600 | qty 2 @15800 | medium | `{level:B, kind:manual}` |

口径说明：
- **金额**：`total_cents` 与 `paid_cents` **一起**比较（只看一个数字容易漏运费/优惠差异）；
- **退款状态**：本地侧由 `after_sale` 行推导（`refunded` > `refunding` > `none`），平台侧取快照 `refundStatus`；**任一侧为 `null` 不比较**（未知 ≠ 不一致）；
- **明细**：不删除、不新增；平台多出的 SKU 记"本地缺失"，本地多出的 SKU 记"平台不存在"，都归入 `order_item_mismatch`；
- **完整性保护**：`snapshot.ordersComplete === false` 时跳过 `order_local_only` 推断（样本不全不误报）。

### 3.3 售后维度（3 类，t43 + t48）

本地表：`after_sale`（t37）；平台侧：快照 `afterSales[]`。

| 类 | 判定 | 本地样例 | 平台样例 | 严重级 | `suggested_action` |
|---|---|---|---|---|---|
| `after_sale_amount_mismatch` | 两侧都有、`amount_cents` 不符 | `ALI-AS-9001` 4000 分 | 5000 分 | high | `{level:C, kind:manual}` |
| `after_sale_status_mismatch` | 两侧都有、`status` 不符；平台 `closed/cancelled` 而本地 `open` 时升 high | `ALI-AS-9002` open | closed | high | `{level:B, kind:manual}` |
| `after_sale_platform_only`（t48/D12） | 平台有、本地**完全没有**同 `platform_after_sale_id` 的记录 | — | `ALI-AS-9003`（订单 1003，refunding，15800 分） | high | `{level:B, kind:manual}` |

口径说明：
- 金额/状态差异只比对**两侧都存在**的售后单；
- **平台有、本地完全没有**必须报（t48 决策）：可能意味着同步失败，或**有人绕过系统退款**；
- 本地有同 id 时**不重复**报"本地无"（那是字段不一致，不是缺失）；本地有、平台无不在本轮范围；
- 退款金额涉及资金，主修复动作恒为 `manual`（**C 级**），代码里不存在任何自动退款/改金额路径。

### 3.4 修复建议的三档结构

每类差异都带完整 `suggestion{summary, actions[], doc_refs[], auto_fixable:false}`：

- `actions[].kind`：`read`（只读核对）/ `write`（走写入门，带 `level` 与 `requires_approval`）/ `manual`（人工处理）；
- `actions[].level`：`A|B|C|null`；`write` 动作用 A/B/C，纯只读/纯人工为 `null`；
- `suggested_action{level,kind}`：**从 `actions` 派生的主动作**（取级别最高的一条，同级取靠后的一条）——建议表约定"先只读核对、后写/人工处置"，所以后者才是真正要执行的；
- `auto_fixable` 恒为 `false`：**M8 只出清单，不改任何业务数据**。

## 4. 存储：`drift_log` 落库与 `drift_key` 规则（t43 已切换）

### 4.1 现状（t43：已切 postgres）

- `drift_log` 由 t37 迁移 `20261020250000_orders_drift_after_sale` 建表；`RECONCILE_STORE` 默认值在 t43 改为 **`postgres`**。
- `DriftStore` 端口三实现：
  - `PgDriftStore`：真实 SQL，`INSERT ... ON CONFLICT (platform, day, drift_key) WHERE archived_at IS NULL DO UPDATE`（部分唯一索引 `uq_drift_day` 的冲突目标）+ `xmax = 0` 区分 inserted/updated + `to_regclass` 探测；
  - `FileDriftStore`：`<RECONCILE_DIR>/<day>/<platform>.json`，原子写（tmp+rename），同 key 合并；保留给本地/测试与无库场景；
  - `auto`：探测 `drift_log`，有则 PG，无则文件，并在响应 `store_note` 说明原因。
- **不再依赖"库里没有表"这种环境事实**：测试对 `file` 与 `postgres` 各显式跑一遍，`auto` 单独断言"探测到表 → postgres"（纯函数 + 集成各一条）。
- **t37 实际表结构与本文件早期"建议 DDL"的差异**（实现按实际表走）：
  - 实际是**单 `detail` jsonb** 承载内容，没有 `subject/local_value/platform_value/detail(text)/suggestion/status/first_detected_at/last_detected_at/seen_count` 这些独立列；
  - 因此上述扩展字段统一打包进 `detail` jsonb，键约定见 §4.2；
  - 唯一索引是**部分唯一** `uq_drift_day (platform, day, drift_key) WHERE archived_at IS NULL`（不含 `org_id`，`org_id` 只做查询过滤）；
  - `drift_key` 长度约束是 `BETWEEN 1 AND 200`（不是 `= 35`），当前实际值仍是 35。

### 4.2 `detail` jsonb 键约定（t37 表结构下的实际写法）

| 键 | 类型 | 说明 |
|---|---|---|
| `text` | string | 人读的差异描述（原 `detail` 文本列） |
| `subject` | object | 差异主体（`type/listing_id/platform_item_id/sku_id/platform_sku_id/order_id/platform_order_id/order_item_id/platform_sku_ref/after_sale_id/platform_after_sale_id`） |
| `local` / `platform_value` | object \| null | 两侧取值快照；`null` = 该侧不存在 |
| `suggestion` | object | `{summary,actions[],doc_refs[],auto_fixable:false}` |
| `suggested_action` | object | `{level,kind}`；冗余存一份便于直接查表，**读取时仍以 `suggestion` 派生为准** |
| `status` | string | 恒 `open`（t43 未做关闭流程）；`ON CONFLICT` 时保留已有值 |
| `first_detected_at` / `last_detected_at` | string(ISO) | 首次/最近发现时间；重复对账只更新后者 |
| `seen_count` | number | 已见次数；重复对账 +1 |

### 4.3 `drift_key` 构造规则（**t43 起为 v2：含订单/售后维度**）

```
drift_key = 'dk_' + hex( sha256( platform + '|' + kind + '|' + listing_id + '|' + platform_item_id + '|'
                               + platform_sku_id + '|' + platform_order_id + '|' + platform_after_sale_id ) ).slice(0, 32)
```

- **参与字段（7 个，顺序固定）**：`platform`、`kind`、`listing_id`、`platform_item_id`、`platform_sku_id`、`platform_order_id`、`platform_after_sale_id`；
- **t43 变更**：在**末尾追加**订单号与售后单号两个字段。商品维度历史 key 的字段顺序语义不变，但**哈希值变化** —— 这是一次显式的键规则版本变更（v1 → v2），已在 §4.5 登记影响；
- **空值处理**：`null` / `undefined` 以**空串**参与，不做占位符；
- **不参与**：`day`（存储维度，唯一键里单列）、`org_id`（唯一键里单列，且不在 `uq_drift_day` 里）、`severity`、`detail`、价格/库存/金额取值；
  → 因此"价格从 14900 变 14950"、"金额从 30000 变 31000"仍是同一条差异（更新而非新增），这是刻意设计（差异是"某对象某类不一致"，不是"某次取值"）；
- **订单维度定位**：订单级差异用 `platform_order_id`；明细级差异再加 `platform_sku_ref`（进 `subject`，**不进** key —— 同一订单同一 SKU 的明细只有一条）；
- **售后维度定位**：用 `platform_after_sale_id`；订单号同时参与（便于按订单聚合，且避免跨订单售后单号碰撞）；
- **唯一作用域**：`(platform, day, drift_key) WHERE archived_at IS NULL`；同一对象同一类差异每天最多一行；
- **稳定性**：`kind` 或参与字段口径变更 = 键规则变更，必须升版本并在文档登记（否则历史去重语义断裂）；
- 当前长度固定 35（`dk_` + 32 hex），`CHECK` 允许 1–200。

### 4.4 `drift_key` 取值样例（真实输出，2026-10-20 / 1688）

```text
order_platform_only                ALI-ORDER-1003  dk_<32hex>
order_local_only                   ALI-ORDER-1002  dk_<32hex>
order_amount_mismatch              ALI-ORDER-1004  dk_<32hex>
order_status_mismatch              ALI-ORDER-1005  dk_<32hex>
order_item_mismatch                ALI-ORDER-1006 / ALI-SKU-0001  dk_<32hex>
after_sale_amount_mismatch         ALI-AS-9001（ALI-ORDER-1004）   dk_<32hex>
after_sale_status_mismatch         ALI-AS-9002（ALI-ORDER-1005）   dk_<32hex>
```

（实际 hex 值随 `platform|kind|id` 变化，测试里断言 `^dk_[0-9a-f]{32}$` 且 14 条互不相同。）

### 4.5 键规则 v1 → v2 的影响登记

| 项 | v1（t36） | v2（t43） | 影响 |
|---|---|---|---|
| 参与字段 | 5 个（商品维度） | 7 个（+ 订单号 + 售后单号） | 同一商品差异的 `drift_key` **哈希值会变** |
| 历史数据 | t36 期间落盘/落库的行 | 新 key 不再命中旧行 | 若跨版本同日重跑，同一条商品差异会**多出一行**（旧 key 一行 + 新 key 一行） |
| 处置 | — | ~~切换日按天清理/归档~~ → **t48 改为版本化统计（见 §11）**：`detail->>'key_version'` 只取当前版本，旧行保留不删、自然退出统计，**不需要任何人工清理** | 零风险；版本再变只需把 `CURRENT_DRIFT_KEY_VERSION` +1 |

## 10. D12：售后「平台有、本地无」差异（t48）

### 10.1 决策与理由

**决策：要报。** t46 当时以"避免重复退款误报"为由不报，队长指出这个规避方式的代价更大：
平台上有一笔退款、本地完全没有记录，是**最该报警**的一类 —— 它可能意味着
① 同步失败（游标丢/任务中断，本地漏拉），或 ② **有人绕过系统直接退款**（绕过审批与审计）。
漏报这两者中的任何一个，都比"多一条待核对清单"严重得多。

### 10.2 判定规则

| 情形 | 是否报 `after_sale_platform_only` | 说明 |
|---|---|---|
| 平台有、本地**完全没有**同 `platform_after_sale_id` 的记录 | **报**（`severity=high`） | 本轮新增 |
| 平台有、本地有同 id 但**金额不同** | 不报此类，只报 `after_sale_amount_mismatch` | 字段不一致 ≠ 记录缺失，避免重复 |
| 平台有、本地有同 id 但**状态不同** | 不报此类，只报 `after_sale_status_mismatch` | 同上 |
| 平台有、本地有且**完全一致** | 不报 | — |
| 本地有、平台无 | 不报（本轮范围外） | 本地多出来的售后单属于数据质量问题，交给 `after_sale` 同步/人工，不混进对账清单 |

实现位置：`apps/api/src/reconcile/engine.ts` `diffAfterSales()` —— 先判 `!local` 走 `after_sale_platform_only` 并 `continue`，
后续金额/状态比较只在"两侧都有"时执行，结构上保证不会重复报。

### 10.3 修复建议

`suggested_action = { level: 'B', kind: 'manual' }`，两条 actions：

1. `read` / `after_sale.detail`：先查 `sync_cursor` 的 `after_sale` 游标与 `last_success_at`，判断是否同步中断；
2. `manual` / `after_sale.adopt_or_ticket`（B 级，需审批）：同步失败 → 修游标后重跑；疑似绕过系统 → 建异常工单并人工补录。
   **禁止自动补单/自动退款**（`auto_fixable=false`）。

### 10.4 测试

`apps/api/test/reconcile.test.ts`：

- `售后差异：… / 平台有本地无（D12）3 类各一条`：断言 `after_sale_platform_only` 命中 `ALI-AS-9003`、
  `severity=high`、`local=null`、`suggested_action={B,manual}`、detail 含"没有任何记录"与"绕过系统退款"；
  并断言本地已有同 id 的 9001/9002 **不会**被重复报成"本地无"。
- `D12 三种情形：平台有本地无 → 报；平台有本地有但金额不同 → 只报金额；一致 → 不报`：
  ① 只报 9003；② 9001 只出 `after_sale_amount_mismatch` 一条；③ 三张售后单两侧全一致 → `[]`。

### 10.5 真实输出

录制样本新增 `ALI-AS-9003`（挂在 `ALI-ORDER-1003` 上 —— 该订单本地完全没有，售后自然也没有）：

```text

```

## 11. D13：`drift_key` 版本化统计（t48）

### 11.1 决策与做法

**决策：不靠"上线日清理"这种人工动作。** 版本写进 `drift_log.detail->>'key_version'`（**不加列、不改 schema**）：

- 写入：`PgDriftStore.detailPayload()` 写入 `key_version: 2`；`ON CONFLICT` 更新时也刷新该字段；
- 读取：`list()` / `count()` / `countByKind()` 一律 `AND COALESCE(detail->>'key_version','1') = $当前版本`；
- 老行（t43 之前没有该字段）视为 **v1**，**保留在表里不删**，自然退出统计；
- `ReconcileRunResult.key_version` 随响应返回，调用方一眼能看出当前口径。

于是版本切换**零风险**：不需要"记得清理"，不需要归档脚本，也不会因为忘清理而重复计数。

### 11.2 版本定义

| 版本 | 参与 `drift_key` 的字段 | 生效 |
|---|---|---|
| v1 | `platform \| kind \| listing_id \| platform_item_id \| platform_sku_id` | t36 |
| v2（当前） | v1 + `platform_order_id \| platform_after_sale_id` | t43/t46 起 |

常量：`apps/api/src/reconcile/types.ts` `CURRENT_DRIFT_KEY_VERSION = 2`。**下次改键规则只需 +1**，
旧行自动退出统计（不需要数据迁移）。

### 11.3 测试

- `PgDriftStore：…` 断言 `row.key_version === 2`（`detail->>key_version` 真的写进去了）；
- `D13：旧 key_version 行保留但不参与统计；切版本零风险（无需人工清理）`：
  写入 14 条 v2 → 统计 14；手工插一条无 `key_version` 的 v1 行 → **统计仍 14**、`countByKind` 不计它、
  `list` 不返回它；物理行数 = 15（**v1 行确实还在，不是被删掉**）；同日重跑 → `inserted=0`、行数仍 15、统计仍 14；
- `D13：内存/文件存储同样只统计当前 key_version`：`MemoryDriftStore` 与 `FileDriftStore` 混入 v1 记录后
  `count` 不变、`list` 全部是 v2 —— 三种存储口径一致。

### 11.4 真实输出（现场演示）

```console
$ # 造一条 v1 遗留行（detail 里没有 key_version）
$ psql -c "INSERT INTO drift_log ... '{\"text\":\"v1 遗留行（切换前）\",...}'"
物理行数(v1+v2): 1   当前版本统计: 0
```

即：v1 行**在表里**（1 行），但当前版本统计为 **0** —— 旧行不删、不计，正是设计意图。

同日对账两次（`RECONCILE_STORE=postgres`）：

```text
[daily] reconcile 1688: total=14 … persisted(inserted=14,updated=0,unchanged=0) store=postgres
[daily] reconcile 1688: total=14 … persisted(inserted=0,updated=14,unchanged=0) store=postgres
```

`drift_log` 直查 14 行，**全部 `detail->>'key_version' = 2`**。

## 13. t49：after_sale 同步 sink + 关键差异告警

> 背景：t48 报出「`after_sale` 只推游标、没有 sink」，意味着本地售后记录全靠人工/脚本，
> 而 `after_sale_platform_only` 是发现"平台有退款、本地零记录"的唯一手段 —— 如果它也不告警，
> 这个风险敞口就完全没人看着。t49 同时补上两端。

### 13.1 `after_sale` 同步 sink（`apps/api/src/sync/after-sale-sink.ts`）

`syncAfterSale` 从"只推游标"升级为真实写 `after_sale`：

| 项 | 实现 |
|---|---|
| 幂等键 | `(platform, platform_after_sale_id)`（唯一索引 `uq_after_sale ... WHERE archived_at IS NULL`） |
| 写入字段 | `platform / platform_after_sale_id / order_id / kind / status / amount_cents / reason / opened_at / closed_at / raw_object_key` |
| 订单关联 | 先按 `(platform, platform_order_id)` 在本地 `orders` 批量查（一次查询，无 N+1） |
| 缺订单 | **不写库、不丢弃**：计入 `stats.pending` + `pending_reasons={order_missing:N}`；对账的 `after_sale_platform_only` 继续把它报出来 |
| `kind` 校验 | 与 DB `ck_after_sale_kind` 对齐（`refund_only / return_refund / exchange`），未知值 422 而不是 500 |
| `closed_at` | 平台给了就用；状态是 `closed/cancelled` 但没给时间时用 `opened_at` 兜底（**不编造"现在"**） |
| 删除 | 不删除任何行（对账/审计依赖历史） |

**为什么缺订单不能写空 `order_id`**：DB 里 `after_sale.order_id` 是 **NOT NULL + FK RESTRICT**。
任务书允许"`order_id` 为空或先落 pending 关联"，但改空需要改 schema（明确禁止），
所以选择 **pending 语义**：数据不丢、原因可查、对账仍报。`orders` 同步补齐后重跑即可落库。

`dry_run` 语义随之更新：`orders` 与 `after_sale` 都是 `false`（真实落库），`products/messages/stock` 仍是 `true`。

### 13.2 关键差异告警

`drift_by_kind` 本来就支持按类型设阈值（`value > threshold` 触发，`threshold=0` 即"出现即告警"），
t49 补的是**让它配了不会白配、不配会被点名**：

1. **拼错 kind 直接报错**：`drift_by_kind` 的 key 必须是 `DRIFT_KINDS` 里的已知值。
   此前 `{"after_sale_platform_onyl":0}` 会被静默接受 —— 等于这条差异永远不告警，比配置报错危险得多。
   现在启动/脚本入口即 `ConfigError`，错误信息列出全部合法值。
2. **日报显式回报配置状态**：`GET /api/dashboard/daily` 新增
   `critical_thresholds[{kind,configured,threshold,recommended,reason}]` 与 `critical_thresholds_missing`。
3. **每日脚本打 WARNING**：未配置时输出
   `WARNING: after_sale_platform_only 未配置告警阈值 … 风险敞口无人看着`，并给出可直接粘贴的配置片段。
4. **`.env.example` 给推荐配置**，并标注这条必须配。

未配置阈值时仍然是"只报事实、不告警"（原行为不变）——只是不再**默默**不告警。

## 14. 告警配置建议（**`after_sale_platform_only` 必须配**）

### 14.1 推荐配置

```bash
DAILY_ALERT_THRESHOLDS='{
  "drift_by_kind": {
    "after_sale_platform_only": 0,
    "price_mismatch": 1,
    "state_mismatch": 1,
    "order_amount_mismatch": 1
  },
  "drift_total": 50,
  "approvals_pending": 20
}'
```

`.env.example` 已带这条（可直接抄）。规则：`value > threshold` 触发，`threshold=0` 表示出现即告警。

### 14.2 为什么 `after_sale_platform_only` 必须配

| 理由 | 说明 |
|---|---|
| 它是唯一的兜底信号 | `after_sale` 的同步频率取决于调度；平台侧新开退款而本地还没拉到时，只有这条差异能发现 |
| 漏报 = 可能掩盖绕过系统退款 | 平台有退款、本地零记录，意味着要么同步失败，要么有人绕过审批与审计直接退了钱 |
| 误报成本很低 | 每条都要人工核对，但核对一条差异远比事后发现一笔无记录退款便宜 |
| 阈值必须是 0 | 这条差异不存在"可接受的数量"，出现一条就该看 |

### 14.3 其他建议

- `price_mismatch` / `state_mismatch` / `order_amount_mismatch` 建议 `1`（金额与在架状态直接涉及钱和合规）；
- `stock_mismatch` 是 A 级可逆写，可给较大阈值（如 `20`）避免噪声；
- `drift_total` 给一个上限（如 `50`）兜底"某类没单独配但整体爆量"；
- 改了阈值要重启 api / 重跑 `daily:report` 才生效（配置在启动时解析，非法配置 fail fast）。

## 15. t50：orders 同步成功后自动重放 pending 售后

> 背景：t49 把缺订单的售后记成 `pending`，但补跑靠"人工记得" —— 这类"等别人记得"的机制，
> 在事故时最容易忘，等于没有机制。t50 把它变成同步链路里的自动动作。

### 15.1 方案（不改 schema）

**pending 清单不持久化。** 它的唯一事实源是"平台侧这笔售后挂在哪张订单上"，
持久化一份就是第二份真相，会和平台漂移。**派生状态不落库。**

触发链：

```
POST /sync/:platform {resource:'orders'}
  → PrismaOrderSink 落库 orders + order_items
  → totals.created + totals.updated > 0 ？
      是 → replayPendingAfterOrders(platform)
             → 用 after_sale reader 从 cursor=null 读全量
             → PrismaAfterSaleSink.apply() 重新关联（命中订单的落库，未命中的继续 pending）
             → **不调用 checkpoint，不推进 after_sale 游标**
      否 → 跳过（没有新订单可命中，省一次全量读）
```

三个关键决定：

| 决定 | 理由 |
|---|---|
| **不用 `events_outbox`** | 项目里 `events_outbox.published_at` 无人回写，没有消费者在跑。用一个没有消费者的队列，等于给自己"看起来异步了"的假象 |
| **不推进 after_sale 游标** | 这是"重放关联"，不是"再同步一遍"；推进游标会让后续增量漏数据 |
| **重放失败不回滚 orders 同步** | 订单已经落库成功，一次重放异常不能把"订单同步成功"误报成失败；只在 `after_sale_retry.error` 里记 |

### 15.2 上限与降级

`AFTER_SALE_RETRY_MAX_ITEMS`（默认 **5000**）：大店量级下 orders 是高频操作，每次全量读 `after_sale`
会放大延迟。超过上限时只处理前 N 条、`degraded=true`，并由路由打 WARNING 让人知道降级了。

### 15.3 响应

`POST /api/sync/:platform` 的响应新增 `after_sale_retry`（仅 `resource='orders'` 且真的写入新订单时出现）：

```json
{
  "after_sale_retry": { "created": 2, "updated": 0, "skipped": 0, "pending": 1, "degraded": false }
}
```

审计 `sync.run` 的 `after.after_sale_retry` 同步记录 —— 调用方一眼看到"这次订单同步顺带救回了几笔"，不用翻日志。

### 15.4 三种时序的真实输出

`apps/api/test/t50-evidence.ts`（内存 sink，纯本地）：

```text
① 售后先到 : {"pulled":3,"created":0,"pending":3,"reasons":{"order_missing":3}}
② 订单后到 : {"created":2,"updated":0,"skipped":0,"pending":1,"degraded":false}
   落库售后 : 1688|ALI-AS-9001, 1688|ALI-AS-9002
③ 重复触发 : created=0 retry=undefined replayCalls=1
   强制再放 : {"created":0,"skipped":2,"pending":1}
④ 超上限   : {"created":0,"updated":0,"skipped":0,"pending":2,"degraded":true,"scanned":3}
```

读法：

- **①** 售后先到、本地无订单 → 3 笔全部 `pending`，一笔都落不了库；
- **②** 订单后到 → **自动**重放救回 9001/9002（`created=2`），9004 的订单仍不存在 → `pending=1`；
- **③** 再同步一次 orders：游标已到末尾、`created=0` → **不触发重放**（`retry=undefined`，`replayCalls` 仍是 1）；
  即使强制再放一次，也只是 `skipped=2`（靠 `(platform, platform_after_sale_id)` 幂等）；
- **④** 上限设 2 → `degraded=true`、只处理前 2 条。

### 15.5 测试

`apps/api/test/reconcile.test.ts` 新增 5 条（reconcile 39 → 44）：

| 用例 | 断言 |
|---|---|
| ① 售后先到、订单后到 | 首次 after_sale 全 pending；orders 同步后 `after_sale_retry.created=2`、`pending=1`；sink 里只有 9001/9002 |
| ② 售后先到、订单永不到 | `pending` 保持 1；`diffAfterSales` 仍报 `after_sale_platform_only`（9004），severity=high |
| ③ 重复触发幂等 | 第二次 orders 同步 `created=0` → 不触发重放；强制重放 `created=0/skipped=2/pending=1`，行数不变 |
| 上限降级 | `maxItems=2` → `degraded=true`、`scanned=3`、只落 2 条 |
| 重放失败不回滚 | 回调抛错 → 同步仍 `succeeded`、`stats.created=5`、`after_sale_retry.error` 含原因 |

集成侧 `POST /api/sync/pdd after_sale` 已改写为真实时序（先清 pdd 的售后/订单/游标）：
第一次 after_sale → `created=0/pending=3`；随后 orders → `after_sale_retry.created=2/pending=1`。
