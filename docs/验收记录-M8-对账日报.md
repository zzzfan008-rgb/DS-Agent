## 2. 同步游标（`sync_cursor`）

### 2.1 使用的列（docs/06 §4.5.2 / Prisma `SyncCursor`）

| 列 | 用途 |
|---|---|
| `platform` / `shop_id` / `resource` | 唯一键 `(org_id, platform, shop_id, resource)`；resource ∈ `products/orders/messages/after_sale/stock` |
| `cursor` | 平台游标（录制样本为 `ck-orders-1/2`，仅验证机制） |
| `watermark_at` | 已消费水位 |
| `last_run_at` / `last_success_at` | 运行/成功时间；`GET /sync/status` 的 `lag_seconds` 依据 |
| `consecutive_failures` / `status` / `error_code` | 连续失败 ≥5 → `status='error'`（docs/06 要求） |
| `lease_owner` / `lease_until` | 单实例消费（抢占式租约，防并发重复跑） |
| `stats` | `{pulled, created, updated, skipped}`；`orders` 有真实 sink，会填 created/updated/skipped；其余资源只填 `pulled` |
| `page_size` | 每页条数（默认 100） |

### 2.2 行为

- **断点续跑**：每读完一页立即 `checkpoint(cursor, watermark_at, stats)`；进程中断后下一次从 `cursor` 继续。
- **并发**：`tryAcquire` 用 `UPDATE ... WHERE lease_until IS NULL OR lease_until < now()` 抢占；拿不到租约返回 `409 conflict`（docs/12 §3.9）。
- **失败**：记录 `error_code`、`consecutive_failures+1`、释放租约；保留最后成功游标。
- **落库（t43）**：`orders` 资源接 `PrismaOrderSink`，逐页写 `orders` + `order_items`：
  - 幂等键 `(platform, platform_order_id)`（唯一索引 `uq_order_platform ... WHERE archived_at IS NULL`）；
  - 明细按 `(order_id, platform_sku_ref)` upsert（`uq_order_item`），**不删除**（平台可能漏传）；
  - `buyer_ref` 必须是 **sha256 hex（64 位小写）** —— DB 硬 `CHECK ck_order_buyer_ref_hash`，明文昵称/手机号会被 23514 拒绝，服务层先做一次校验给出 422 而不是 500；
  - 订单状态受 `ck_order_status` 约束（`pending/paid/shipped/delivered/completed/refunding/refunded/cancelled`），未知状态直接拒绝（不把平台新状态静默写坏）；
  - 响应 `dry_run`：有 sink → `false`（真实落库）；无 sink → `true`（只推进游标）。
- **其余资源只推进游标**：`products/messages/after_sale/stock` 暂无 sink（表/契约未就绪），`dry_run=true`。
- **真实 reader 硬拒绝**：`RECONCILE_READER/SYNC_READER=adapter` 时抛 `publish_blocked`（409），detail 带 `reason=adapter_contract_unverified` 与 TODO 列表（1688：`TODO-1688-*`；PDD：`TODO-PDD-CONTRACT-VERIFY`）。

### 2.3 验证输出（测试节选）

`apps/api/test/reconcile.test.ts` 中断言：
- 第一轮 `pages=1, pulled=2, cursor=ck-orders-1`；
- 第二轮 `resumed_from=ck-orders-1, pulled=1, cursor=ck-orders-2`；
- 第三轮 `pulled=0`（已到末尾，不重复拉取）；
- 并发跑第二次 → `ApiError('conflict')`；

## 3. 对账差异（13 类：商品 6 + 订单 5 + 售后 2，录制样本）

平台快照：`recorded-samples.ts`（`verified:false`, `complete:true`, `ordersComplete:true`, `afterSalesComplete:true`，note 明确"合成样本，非 1688 真实报文"）。
本地种子（`apps/api/test/reconcile.test.ts`）：6 个 1688 listing（`ALI-2026-0001…0007`，0001 为基线）+ 5 个订单（1001/1002/1004/1005/1006）+ 2 个售后（9001/9002）。

### 3.1 商品/上架维度（6 类，t36）

| 类 | 本地 | 平台 | 严重级 | `suggested_action` | 修复建议（节选） |
|---|---|---|---|---|---|
| `platform_only_listing` | 无 listing | `ALI-2026-0006` online | medium | `{level:null, kind:manual}` | 只读核对 → 人工建档并绑定 `platform_item_id`（不自动发布） |
| `local_published_missing_platform` | `ALI-2026-0007` published | 快照中不存在 | high | `{level:B, kind:write}` | 核对平台是否删除 → `POST /api/listings/stop-loss`（B 级，需审批） |
| `local_published_platform_offline` | `ALI-2026-0004` published | `offline` | medium | `{level:B, kind:write}` | 查下架原因 → 重新上架（B 级，需审批）或止损 |
| `price_mismatch` | `ALI-SKU-0002` 15800 分 | 14900 分 | medium | `{level:C, kind:write}` | 写前拉现价 → 改价 `listing.update_price`（**C 级**，审批 + confirm_token + 低峰窗口） |
| `stock_mismatch` | `ALI-SKU-0003` 88 | 0 | low | `{level:A, kind:write}` | `stock.query` 核对 → `listing.update_stock`（A 级，覆盖写 + 快照） |
| `state_mismatch` | `ALI-2026-0005` published | `violation_offline` | high | `{level:B, kind:write}` | 读驳回原因 → 止损（B 级）→ 修复后重提 |

### 3.2 订单维度（5 类，t43）

本地表：`orders` + `order_items`（t37）；平台侧：快照 `orders[]`（含 `items[]`）。

| 类 | 判定 | 本地样例 | 平台样例 | 严重级 | `suggested_action` |
|---|---|---|---|---|---|
| `order_platform_only` | 平台有、本地无 | — | `ALI-ORDER-1003` shipped / 15800 分 | high | `{level:null, kind:manual}` |
| `order_local_only` | 本地有、平台无 | `ALI-ORDER-1002` paid / 9999 分 | 快照中不存在 | high | `{level:B, kind:manual}` |
| `order_amount_mismatch` | `total_cents` 或 `paid_cents` 不符 | `ALI-ORDER-1004` total/paid 31600 | total/paid 30000 | high | `{level:B, kind:manual}` |
| `order_status_mismatch` | 订单 `status` 不符，**或** 退款状态不符（两侧都非 null 才比） | `ALI-ORDER-1005` paid + refunding | refunded + refunded | high | `{level:B, kind:manual}` |
| `order_item_mismatch` | 明细按 `platform_sku_ref` 对齐后：缺失 / `qty` 不符 / `unit_price_cents` 不符 / `amount_cents` 不符 | `ALI-ORDER-1006` SKU-0001 qty 1 @31600 | qty 2 @15800 | medium | `{level:B, kind:manual}` |

口径说明：
- **金额**：`total_cents` 与 `paid_cents` **一起**比较（只看一个数字容易漏运费/优惠差异）；
- **退款状态**：本地侧由 `after_sale` 行推导（`refunded` > `refunding` > `none`），平台侧取快照 `refundStatus`；**任一侧为 `null` 不比较**（未知 ≠ 不一致）；
- **明细**：不删除、不新增；平台多出的 SKU 记"本地缺失"，本地多出的 SKU 记"平台不存在"，都归入 `order_item_mismatch`；
- **完整性保护**：`snapshot.ordersComplete === false` 时跳过 `order_local_only` 推断（样本不全不误报）。

### 3.3 售后维度（2 类，t43）

本地表：`after_sale`（t37）；平台侧：快照 `afterSales[]`。

| 类 | 判定 | 本地样例 | 平台样例 | 严重级 | `suggested_action` |
|---|---|---|---|---|---|
| `after_sale_amount_mismatch` | `amount_cents` 不符 | `ALI-AS-9001` 4000 分 | 5000 分 | high | `{level:C, kind:manual}` |
| `after_sale_status_mismatch` | `status` 不符；平台 `closed/cancelled` 而本地 `open` 时升 high | `ALI-AS-9002` open | closed | high | `{level:B, kind:manual}` |

口径说明：
- 只比对**两侧都存在**的售后单（平台独有/本地独有的售后单本轮不报，避免"重复退款"类误报）；
- 退款金额涉及资金，主修复动作恒为 `manual`（**C 级**），代码里不存在任何自动退款/改金额路径。

### 3.4 修复建议的三档结构

每类差异都带完整 `suggestion{summary, actions[], doc_refs[], auto_fixable:false}`：

- `actions[].kind`：`read`（只读核对）/ `write`（走写入门，带 `level` 与 `requires_approval`）/ `manual`（人工处理）；
- `actions[].level`：`A|B|C|null`；`write` 动作用 A/B/C，纯只读/纯人工为 `null`；
- `suggested_action{level,kind}`：**从 `actions` 派生的主动作**（取级别最高的一条，同级取靠后的一条）——建议表约定"先只读核对、后写/人工处置"，所以后者才是真正要执行的；
- `auto_fixable` 恒为 `false`：**M8 只出清单，不改任何业务数据**。

## 4. 存储：`drift_log` 落库与 `drift_key` 规则（t43 已切换）

### 4.1 现状（t43：已切 postgres）

- `drift_log` 由 t37 迁移 `20261020250000_orders_drift_after_sale` 建表；`RECONCILE_STORE` 默认值在 t43 改为 **`postgres`**。
- `DriftStore` 端口三实现：
  - `PgDriftStore`：真实 SQL，`INSERT ... ON CONFLICT (platform, day, drift_key) WHERE archived_at IS NULL DO UPDATE`（部分唯一索引 `uq_drift_day` 的冲突目标）+ `xmax = 0` 区分 inserted/updated + `to_regclass` 探测；
  - `FileDriftStore`：`<RECONCILE_DIR>/<day>/<platform>.json`，原子写（tmp+rename），同 key 合并；保留给本地/测试与无库场景；
  - `auto`：探测 `drift_log`，有则 PG，无则文件，并在响应 `store_note` 说明原因。
- **不再依赖"库里没有表"这种环境事实**：测试对 `file` 与 `postgres` 各显式跑一遍，`auto` 单独断言"探测到表 → postgres"（纯函数 + 集成各一条）。
- **t37 实际表结构与本文件早期"建议 DDL"的差异**（实现按实际表走）：
  - 实际是**单 `detail` jsonb** 承载内容，没有 `subject/local_value/platform_value/detail(text)/suggestion/status/first_detected_at/last_detected_at/seen_count` 这些独立列；
  - 因此上述扩展字段统一打包进 `detail` jsonb，键约定见 §4.2；
  - 唯一索引是**部分唯一** `uq_drift_day (platform, day, drift_key) WHERE archived_at IS NULL`（不含 `org_id`，`org_id` 只做查询过滤）；
  - `drift_key` 长度约束是 `BETWEEN 1 AND 200`（不是 `= 35`），当前实际值仍是 35。

### 4.2 `detail` jsonb 键约定（t37 表结构下的实际写法）

| 键 | 类型 | 说明 |
|---|---|---|
| `text` | string | 人读的差异描述（原 `detail` 文本列） |
| `subject` | object | 差异主体（`type/listing_id/platform_item_id/sku_id/platform_sku_id/order_id/platform_order_id/order_item_id/platform_sku_ref/after_sale_id/platform_after_sale_id`） |
| `local` / `platform_value` | object \| null | 两侧取值快照；`null` = 该侧不存在 |
| `suggestion` | object | `{summary,actions[],doc_refs[],auto_fixable:false}` |
| `suggested_action` | object | `{level,kind}`；冗余存一份便于直接查表，**读取时仍以 `suggestion` 派生为准** |
| `status` | string | 恒 `open`（t43 未做关闭流程）；`ON CONFLICT` 时保留已有值 |
| `first_detected_at` / `last_detected_at` | string(ISO) | 首次/最近发现时间；重复对账只更新后者 |
| `seen_count` | number | 已见次数；重复对账 +1 |

### 4.3 `drift_key` 构造规则（**t43 起为 v2：含订单/售后维度**）

```
drift_key = 'dk_' + hex( sha256( platform + '|' + kind + '|' + listing_id + '|' + platform_item_id + '|'
                               + platform_sku_id + '|' + platform_order_id + '|' + platform_after_sale_id ) ).slice(0, 32)
```

- **参与字段（7 个，顺序固定）**：`platform`、`kind`、`listing_id`、`platform_item_id`、`platform_sku_id`、`platform_order_id`、`platform_after_sale_id`；
- **t43 变更**：在**末尾追加**订单号与售后单号两个字段。商品维度历史 key 的字段顺序语义不变，但**哈希值变化** —— 这是一次显式的键规则版本变更（v1 → v2），已在 §4.5 登记影响；
- **空值处理**：`null` / `undefined` 以**空串**参与，不做占位符；
- **不参与**：`day`（存储维度，唯一键里单列）、`org_id`（唯一键里单列，且不在 `uq_drift_day` 里）、`severity`、`detail`、价格/库存/金额取值；
  → 因此"价格从 14900 变 14950"、"金额从 30000 变 31000"仍是同一条差异（更新而非新增），这是刻意设计（差异是"某对象某类不一致"，不是"某次取值"）；
- **订单维度定位**：订单级差异用 `platform_order_id`；明细级差异再加 `platform_sku_ref`（进 `subject`，**不进** key —— 同一订单同一 SKU 的明细只有一条）；
- **售后维度定位**：用 `platform_after_sale_id`；订单号同时参与（便于按订单聚合，且避免跨订单售后单号碰撞）；
- **唯一作用域**：`(platform, day, drift_key) WHERE archived_at IS NULL`；同一对象同一类差异每天最多一行；
- **稳定性**：`kind` 或参与字段口径变更 = 键规则变更，必须升版本并在文档登记（否则历史去重语义断裂）；
- 当前长度固定 35（`dk_` + 32 hex），`CHECK` 允许 1–200。

### 4.4 `drift_key` 取值样例（真实输出，2026-10-20 / 1688）

```text
order_platform_only                ALI-ORDER-1003  dk_<32hex>
order_local_only                   ALI-ORDER-1002  dk_<32hex>
order_amount_mismatch              ALI-ORDER-1004  dk_<32hex>
order_status_mismatch              ALI-ORDER-1005  dk_<32hex>
order_item_mismatch                ALI-ORDER-1006 / ALI-SKU-0001  dk_<32hex>
after_sale_amount_mismatch         ALI-AS-9001（ALI-ORDER-1004）   dk_<32hex>
after_sale_status_mismatch         ALI-AS-9002（ALI-ORDER-1005）   dk_<32hex>
```

（实际 hex 值随 `platform|kind|id` 变化，测试里断言 `^dk_[0-9a-f]{32}$` 且 13 条互不相同。）

### 4.5 键规则 v1 → v2 的影响登记

| 项 | v1（t36） | v2（t43） | 影响 |
|---|---|---|---|
| 参与字段 | 5 个（商品维度） | 7 个（+ 订单号 + 售后单号） | 同一商品差异的 `drift_key` **哈希值会变** |
| 历史数据 | t36 期间落盘/落库的行 | 新 key 不再命中旧行 | 若跨版本同日重跑，同一条商品差异会**多出一行**（旧 key 一行 + 新 key 一行） |
| 处置 | — | 切换当天的 `drift_log` 按天清理/重跑（`DELETE ... WHERE day = <切换日>`），或人工把旧 key 行 `archived_at` 置位 | 仅影响切换日；之后稳定 |
