## 3. 强类型校验与拒绝策略（docs/19 §10 L0/L1）

- **色卡**：`bk0101` → `BK-0101`；拒绝 Hex、未知色系、无 4 位序号；展示名不参与判断。
- **尺码**：`2XL→XXL`、`3XL→XXXL`、`均码/FREE→ONE`；词表外（如 `6XL`）拒绝；`one_size` 仅 1 行。
- **尺码表**：ajv 校验 `SizeChartV1` + 业务规则——测量值 0.5 步进/≤250、12 部位词表、按 `category_code` 必测部位（上装胸围+衣长等）、建议区间成对/`max>min`/按 size_order 严格递增/空档 ≤2/覆盖 ≥20cm、≥15kg；失败返回 `422 validation_failed` + `{code,field,message}`（如 `SCHEMA-003`、`BIZ-SIZE-002`、`BIZ-SIZE-003`）。
- **成分**：纤维标准词表（`涤纶→聚酯纤维`）→ 1–8 条、整数 1–100、降序、合计必须 100；99/101 直接拒绝（`SCHEMA-004`）。
- **平台属性映射**：`internal_field` 四表白名单（防属性外渗）、enum 必须有 `platform_value_id`、range 必须有 `extra.min/max`、类目必须叶子且平台一致。
- **事实信封**：结构校验 + `facts_hash` 复算；判断前与当前主数据重建的 facts 比对，不一致 `422 invalid_fact`。
- **事务性**：CSV 任一行非法 → 整批不写；尺码表/成分非法 → 不产生新版本（测试断言行数不变）。

## 4. 判断层

### 4.1 L1（规则引擎，纯函数）

- 规则集 `rules@1.0.0`，词表 `lexicon@1.0.0`；20 条：
  - 词面/结构：LEX-001/002/003/005/006/007、TXT-001/002；
  - 硬事实：PRC-001/003、STK-001、CMP-001/002、SIZE-001/002/004、POL-001；
  - 客服：REP-001/002。
- 每条命中：`rule_id + severity + field='text' + span（映射回原文偏移） + matched + suggestion`；
- `l1_result={rule_set_version,lexicon_version,evaluated,skipped,hits,errors,duration_ms,blocked}`；`l1_hit_rule_ids` 单列；
- 规则内部异常记录到 `errors`，编排层 escalate（不允许规则崩了放行）；
- blocker 命中即 `reject` 短路，不调 L2（成本 0）。

### 4.2 L2（LLM 裁决）

- 输入：`judge@1.0.0` 六段提示词（角色/输入/证据要求/标准/输出契约/示例）+ facts + l1_hits + evidence；
- 输出 Schema `JudgmentV1`（verdict/severity/reason/repair_hint/evidence_refs/claims/confidence）；
- 后置校验：JSON Schema → 证据白名单（chunk/doc/doc_version）→ 引用逐字子串 → `reject/needs_revision` 必须有引用 → `pass` 只能 info/low → `confidence<0.6` 升级；
- 无证据：**不调用 L2**，直接 `escalate(no_evidence_available)`；Schema/缺证据失败先修复重试 1 次，仍失败 `escalate`；
- 合并：L1 blocker→reject；L1 high/medium 不能被 L2 降为 pass；L2 escalate 永远优先；最终 severity 取最大；
- 模型调用走 t7 的 `purpose=judge` 路由（配额/熔断/计量/`model_call_log` 一致）。

### 4.3 判定记录与申诉

- `judgment` 落库：status/verdict/severity/l1_result/l1_hit_rule_ids/l2_result/evidence_refs/reason/repair_hint/model_call_id/rule_set_version/lexicon_version/prompt_version/facts_hash/cost_cents/latency_ms/escalated；
- 草稿判定后回写 `content_draft.status/judge_id/risk_flags/fact_check`；
- 申诉：24h 内 1 次，blocker 不可申诉；admin 复核 upheld/overridden，改判写 `final_verdict` 与 status；全部写 audit。

## 7. 阻断与偏差

### B1（阻断，schema）：size_chart effective 唯一索引错误
- 现状：`uq_size_chart_effective ON size_chart (product_id) WHERE status='effective' AND archived_at IS NULL`（t1 migration:1476）。一码一行时，同一商品第二个码（M/L）插入即唯一冲突；
- docs/21 §6 要求 `(product_id, version_no, size_code)`；docs/06 文字为“一尺码一行”，但索引行同样写错；
- 影响：多码商品无法创建/导入；t9 上架取多码尺码表必撞；
- 建议：db-infra 补 additive 迁移
  `DROP INDEX uq_size_chart_effective; CREATE UNIQUE INDEX uq_size_chart_effective ON size_chart (product_id, version_no) WHERE status='effective' AND archived_at IS NULL;`
  并同步修 docs/06 §4.2.3/索引表；
- 本任务未自行改 schema；t8 验收用单码路径，代码按正确语义写 `status='effective'`，迁移落地后多码自动可用。

### B2（契约补充）：SKU 插入前必须有 effective 尺码表
- DB 触发器 `check_sku_size_exists`（t1）要求 SKU `size_code` 已存在于该商品 effective size_chart；
- docs/12 `POST /products` 原字段没有尺码表，但同请求要建 SKU，存在顺序矛盾；
- 本实现给 `POST /products`/CSV 增加 `size_chart`（CSV 增加 `measurements` 列）作为契约补充；建议 docs/12 收录，或改成“先建商品+尺码表，再建 SKU”的两步流程。

## 10. t28 补充：商品聚合 / 审批内容失效 / 内容专用审批动作（2026-10-20）

### 10.1 商品列表聚合（G1）

`GET /api/products` 现在返回：

```json
{
  "platform_states": {
    "pdd":  { "status": "published|publishing|rejected|draft|archived|not_listed", "platform_state": null, "last_write_at": "..." },
    "1688": { "status": "not_listed", "platform_state": null, "last_write_at": null }
  },
  "missing_fields": ["missing_size_chart", "missing_fabric", "missing_qualification", "missing_platform_category"]
}
```

- `platform` 过滤：先批量取该平台 listing 的 productId（1 条 distinct 查询），再筛商品；`missing_fields=1` 在聚合结果上按 code 过滤。
- 聚合为 **5 条批量 SQL**（product + SKU + size_chart + fabric + listing），无逐商品 N+1；游标仍按 `spu_code` 升序稳定分页。
- 实测（测试库，1000 条商品，`missing_fields=true, limit=20`）：**44.5ms**，见 `apps/api/test/last-run-t28.log` 的 `[t28] 1000 products aggregate`。
- 说明：当前为“取筛选集合后内存过滤 missing_fields”，1000 条实测满足；10 万级建议改 SQL EXISTS/物化聚合（登记后续）。

### 10.2 审批内容失效（G3）

- `POST /api/approvals` 创建时把 `target_payload` 存入 `approval.diff.target_payload`；`decide` 对 `subject_type=content_draft`（及 `action=publish_content`）用 **core `canonicalHash`** 重算 `contentDraftTargetHash`，与 `approval.target_hash` 不一致 → **428 `approval_stale`**，`error.next_action='resubmit'`。
- `PUT /api/content/drafts/:id`：编辑正文后重新装配主数据 facts、更新 `word_count/status`，返回新的 `facts_hash` + `target_hash`；旧 pending 审批标 `invalidated`（保留记录，不删除），旧审批 decision 仍因 hash 不符返回 428；重新提交新审批可正常批。
- **t35 阻断（已报队长）**：DB `uq_approval_open` 仍是全量唯一 `(subject_type,subject_id,action)`，非 pending-only；编辑草稿时本实现先把旧 pending 标 `invalidated` 才能创建新审批。t35 落地后需补“驳回/已批准后重新提交”的回归；届时可移除该临时失效动作（或保留为产品语义）。

### 10.3 内容专用审批动作（G13）

- 新增动作 `approval.action='publish_content'`（B 级，action code `content.publish`，`approvalAction=publish_content`），不再复用 `listing.create`；`ActionMeta` 中 `content.publish` 定级 B，`computeLevel` 已单测。
- **t32 阻断（已报队长）**：DB `ck_approval_action` 尚未包含 `publish_content`，迁移落地前 `POST /approvals` 该动作会被 DB CHECK 拒绝；迁移 SQL 已提交队长，落地后建议补 201 + admin 审批用例。
- 服务端 level 判定与 `listing.create` 共用同一套 `computeLevel`，不会因为动作名不同漂移。
