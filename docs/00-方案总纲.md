# 服装电商双平台运营系统 · 方案总纲

| 项 | 内容 |
|---|---|
| 版本 | 1.0（第一版，方案基线） |
| 日期 | 2026-10-20 |
| 状态 | 待批准；批准后按第十五节里程碑施工 |
| 业务场景 | 自有服装货品，在**拼多多（零售）+ 1688（批发/代发）**双平台销售 |

| 代码根目录 | `D:\DSSAAS` |

---

## 一、目标与成功标准

### 1.1 目标

把服装电商的**内容生产、客服应答、商品上架、素材制作、经营对账**五件事，从"人工逐条做"变成"系统生成 + 人审批 + 系统执行"，并用一套可审计的边界保证不出事故。

### 1.2 成功标准（全部可测）

1. 一个新品从拿到资料到双平台上架，人工只需**校对与审批**，不再逐字写文案、不再手工填平台表单。
2. 客服消息到达后**秒级**进入工作台，草稿 5 秒内可用或自动降级为话术模板，人工一键确认发送。
3. 所有对平台与对外消息的写操作**100% 经过审批与审计**，可追溯到"谁、何时、基于什么事实"。
4. 平台驳回后能给出可执行的修复项并重新提交；不可逆操作有明确的止损路径。
5. 商品的价格、库存、成分、尺码、政策**全部来自主数据**，不出现模型编造的事实。
6. 系统整体可在单机房（或单机 + 云主机）部署，备份、恢复、演练有记录，DSH 升级不会让业务停摆。

### 1.3 非目标

不做对外 SaaS、多租户、计费与配额售卖；不做企业级 SSO-SCIM；不做浏览器自动化（Playwright / DOM 注入 / 按键模拟）发布或回复；不自研 ERP、n8n、Dify 等价物；不用 AI 图替代实拍主图；不做未经人工审批的自动改价与自动回复。

## 二、场景与范围

### 2.1 业务范围

| 域 | 内容 |
|---|---|
| 商品 | 主数据（SPU/SKU）、尺码表、面料成分、类目与资质、平台属性映射 |
| 内容 | 标题、卖点、详情页、FAQ、场景与季节文案、种草短文案 |
| 客服 | 拼多多消费者会话（售前/售后/退换/物流）、1688 询盘与报价（分销商/批发） |
| 上架 | 双平台商品发布、上下架、改价、库存同步、批量操作、驳回回写 |
| 素材 | 实拍图管理、AI 场景图/背景/模特替换、尺码表图渲染、商品视频上传、短视频样片 |
| 经营 | 会话与订单同步、对账、日报告警、成本归集、审批积压 |
| 治理 | 审批流、审计、判断层、kill switch、补偿工单 |

### 2.2 平台能力差异（必须分别实现）

| 维度 | 拼多多（C2C 零售） | 1688（B2B 批发） |
|---|---|---|
| 价格模型 | 单一售价 + 促销价 | 起批价 + 规格阶梯价 + 区间价 |
| 商品结构 | 颜色/尺码 SKU + SKU 图 | 规格组合 + 起批量 + 代发 |
| 消息通道 | 飞鸽/商家客服（消费者） | 旺旺询盘（分销商/批发商） |
| 主要交互 | 售前售后、退换、评价 | 询盘、报价、账期、代发、下单 |
| 内容重点 | 主图、详情、短视频、转化导向 | 参数、起批说明、代发能力、货源可信 |
| 核心指标 | 转化率、客单价、退款率 | 询盘量、报价成交率、起批达成率 |
| 审批规则 | 价格与主图最敏感 | 报价与起批条件最敏感 |

结论：**两套 adapter、两套模板、两套指标、两套审批策略**；共用主数据、模型网关、素材管线、写入门与审计。

## 三、总体架构

```
                         ┌───────────────────────────────┐
   运营/客服（浏览器）→  │  apps/web  Next.js（唯一业务入口）│
                         └───────────────┬───────────────┘
                                         │ HTTP / SSE
                         ┌───────────────▼───────────────┐
                         │  apps/api  Fastify + TS        │
                         │  API / 编排 / 写入门 / 模型网关 │
                         │  平台适配 / 身份 / 审计         │
                         └───┬─────────┬─────────┬───────┘
                     ┌───────▼──┐  ┌───▼────┐  ┌─▼──────────┐
                     │ Postgres │  │ Redis  │  │  MinIO     │
                     │ pgvector │  │ BullMQ │  │  素材/视频  │
                     └──────────┘  └───┬────┘  └────────────┘
                                       │
                         ┌─────────────▼──────────────┐
                         │ apps/worker（同镜像另进程） │
                         │ 媒体/同步/对账/批处理       │
                         └───────┬───────────┬────────┘
                                 │           │
                    ┌────────────▼──┐   ┌────▼─────────────────┐
                    │ 中心 DSH Host │   │ edge-proxy（按需）    │
                    │ agent 内核    │   │ 指定机房薄代理+签名    │
                    └───────────────┘   └────┬─────────────────┘
                                             │
                                   拼多多 / 1688 开放平台
```

### 3.1 组件职责

| 组件 | 职责 | 边界 |
|---|---|---|
| `apps/web` | 12 个业务页面，所有业务操作的唯一入口 | 不直连模型、不直连平台 |
| `apps/api` | 业务 API、工作流编排、写入门、模型网关、平台适配、身份、审计 | 唯一写平台的地方 |
| `apps/worker` | 媒体任务、平台同步、对账、通知、批处理任务 | 不对外提供 API |
| `apps/analytics`（可选） | 经营报表、图像批处理（Python FastAPI） | 只读数据、只产出报表 |
| 中心 DSH Host | agent 内核：多步工具调用、长上下文、追问、skill 与 MCP 编排 | 只做有界任务，**不直写平台** |
| `edge-proxy`（按需） | 平台要求指定机房时，做转发 + 签名 + 防重放 + 报文留档 | 只转发，不做业务判断 |
| Postgres | 业务唯一事实源 | 页面与接口只读它 |
| MinIO | 素材、视频、导出包 | 版本化 |

### 3.2 DSH 的定位与复用边界

DSH 作为 **agent 内核**接入，不作为业务系统、不作为唯一入口。

| 需求 | 复用 DSH 组件 | 说明 |
|---|---|---|
| 文本模型多供应商路由 | `dsh-llm-pi-ai` | 一份配置路由多提供方/兼容网关；profile 与凭据按请求解析，改配置下个请求生效，无需重启 |
| 供应商密钥存储 | `dsh-credentials` | 密钥只存一次、按名引用；界面只报"是否已配置"，从不返回值 |
| 内部 RPC 与授权 | `dsh-api-gateway` + `dsh-api-remote-access` | 流式 Remote（`mode:'stream'`）、`AbortSignal` 取消、peer principal 决定 role × resource |
| 沙箱与审批档位 | `dsh-permission-presets` + `dsh-user-approval` | 运营/客服/只读三档；敏感操作一次性决定并留审计 |
| Skill / MCP | `dsh-skill-filesystem`、`dsh-mcp-client`、`dsh-mcp-resources` | 品牌语气/尺码/洗护/退换货 4 个 skill；ERP 与平台只读 MCP |
| Agent 工作台打包 | `dsh-agent-preset` | 一个"服装电商运营" preset，内含四组工具与技能 |
| 平台回调触发 | `dsh-webhook` | 订单/消息/售后回调触发对应工作流 |
| 批处理 / 定时 / CI | `dsh-headless` | 一次性任务模式（`--json` 事件流、`--session-id` 续接），无 GUI、不常驻 |
| 会话留痕 | `dsh-session-persistence-jsonl` | agent 思考过程黑匣子，仅供调试 |

**不使用的**：`dsh-storage-json` 不承载业务数据（其 `root` 必填、目录以 `0o700` 创建，官方明示更大或高并发数据应选 SQLite）；`dsh-workflow` 是给模型用的 agent 扇出编排（JS 脚本 + `agent()/parallel()/pipeline()`，由调用方提供执行引擎），**不是**带持久化状态、人工节点、幂等与回滚的业务流程引擎——业务流程状态机用 BullMQ + Postgres 自建。

## 四、技术选型与关键决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 后端框架 | **TypeScript + Fastify 为主线**；Python 仅做可选的分析/图像 worker（FastAPI） | DSH 扩展面（MCP client、skill、preset、bundle、Typert RPC）全为 TS；模型协议与工具 schema 只维护一份 |
| 业务工作流 | **BullMQ + Postgres 状态机** | 需要持久化、幂等、可恢复、人工节点、回滚——DSH 的 workflow 不含这些 |
| 数据库 | Postgres 16 + pgvector | 业务事实源与向量检索同库，减少一套运维 |
| 队列 | Redis + BullMQ | 与 Node 生态一致，重试/死信/延时开箱可用 |
| 对象存储 | MinIO | 自托管、S3 兼容、版本化 |
| 前端 | Next.js（App Router） | SSR 与流式渲染，适合工作台类界面 |
| 身份 | 自建轻量账号层（口令 + TOTP） | DSH 无企业身份源；预留 LDAP/企业微信/钉钉适配口 |
| 平台接入 | 官方开放平台 API 优先，导入包兜底 | 不碰浏览器自动化，规避账号风控 |
| 知识库 | pgvector + 混合召回 + 引用溯源 | DSH 无 embedding/vector 包，需自建 |
| 部署 | Docker Compose（可平滑迁 K8s） | 单机房可运维优先 |

## 五、交互入口与 Agent 驱动

### 5.1 唯一业务入口 = `apps/web`

运营与客服**不安装、不接触 DSH**。他们在网页里点按钮或提诉求，由 `apps/api` 驱动中心 DSH Host 执行，SSE 流式回显。

- 中心 DSH Host 常驻，对外只暴露一个 Typert Remote service（`@Remote({ mode:'stream' })`），支持流式输出与 `AbortSignal` 取消。
- `apps/api` 以 Client 身份调用，peer principal 决定权限，前端按 `dsh-api-remote-access` 的决策自动隐藏无权入口。
- DSH 原生 Web/Desktop 界面**仅供管理员**调试 preset、skill 与观察 agent 行为，不进业务流程。
- `dsh-headless` **不作交互通道**（每次调用跑一个任务即退出），只用于批处理、CI、定时任务。

### 5.2 场景分工

| 场景 | 入口 | 理由 |
|---|---|---|
| 文案生成/改写、详情产出 | 网页按钮 → api → agent | 业务人员要的是结果，不是对话 |
| 客服回复、询盘报价 | 网页（会话 + 草稿 + 发送） | 同上 |
| 商品资料问答、多轮澄清 | 网页内嵌对话（同一 Remote service） | 需要追问但仍留在业务上下文 |
| 调参、调试 preset/skill | DSH Web（仅管理员） | 开发者工具 |
| 批量、定时、CI | worker → `dsh-headless` | 无 GUI 需求 |

## 六、身份、权限与审计

### 6.1 角色

三档角色，最小权限：

| 角色 | 权限 |
|---|---|
| `viewer` | 只读：商品、会话、审批列表、报表 |
| `operator` | 生成草稿、上传素材、提交审批、发送已批准消息 |
| `admin` | 供应商与模型配置、路由、审批终审、kill switch、备份与账号管理 |

### 6.2 审计

- `audit_log` 追加写、不更新：谁、何时、动作、资源、before/after、request_id。
- 写入门每笔落审计；不可逆动作额外标记 `irreversible=true` 并关联补偿工单。
- 模型调用落 `model_call_log`：模型、token、耗时、成本、产出摘要。
- 审批记录包含事实来源快照（引用了哪些主数据/知识库片段）。

## 七、模型与供应商管理

### 7.1 三层模型

| 层 | 表 | 关键字段 |
|---|---|---|
| Provider（供应商账号） | `provider` | kind(text/image/video/embedding)、base_url、auth_ref（指向 DSH 凭据）、status、连通性、余额 |
| Model（模型与参数价格） | `model` | provider_id、external_model_id、display_name、capability、params_schema、price、rate_limit、status、published_at |
| Route（默认与降级） | `model_route` | scope(org/role/user)、purpose(copy/judge/image/video/embed/rerank)、model_id、fallback_ids、priority、配额 |

### 7.2 可见性与生效规则

前台只显示**同时满足**以下条件的模型：

1. `provider.auth_ref` 已配置且连通性测试通过；
2. `model.status = published` 且 `params_schema` 合法；
3. `route` 命中当前用户 scope，且角色未被禁；
4. 用户有权使用（角色 × 用途矩阵）。

管理员改配置后**下个请求即生效**，不重启服务。每次调用记录真实使用的 model_id、参数与成本；超配额拒绝或按 route 降级。

### 7.3 供应商与模型清单

首批接入文本、图片、视频三类供应商；图片侧至少包含用户指定的四个模型（模型 ID 以其控制台实际可用值为准，命名映射登记在 `model.external_model_id`）。视频与文本推理各自独立供应商，彼此不耦合。

### 7.4 图片/视频的工程约束

- 图片多为同步或短轮询；视频多为"提交任务 → 轮询 → 取回 URL"的异步链路 → 走 `media_job` + 队列 + MinIO。
- DSH 不处理音视频（`dsh-attachment` 明示"音频和视频暂无专门处理"）→ 转码、抽帧、分片上传全部自建。

## 八、平台适配层

### 8.1 接入路径

| 路径 | 适用 | 说明 |
|---|---|---|
| 官方开放平台 API | 已获权限、接口满足需求 | 写入门调用，走签名与限流 |
| 上架包（CSV/Excel）+ 后台导入 | 接口未获批或不支持字段 | 系统产出符合平台模板的上架包 |
| 工作台人工执行 | 消息、询盘等无法 API 化的场景 | 网页内处理 + 剪贴板助手 |
| 只读同步（订单/商品） | 可获取数据即可 | 用于对账与展示 |

### 8.2 接入侦察（施工第一件事）

每个平台产出一份《平台接入侦察报告》，内容固定六项：

1. **账号与资质**：开发者认证、应用创建、类目资质要求与申请周期；
2. **接口清单**：商品发布/上下架/改价、库存、订单、消息/客服、素材（图片/视频）上传——逐条记录接口名、是否需审核、限流、沙箱可用性；
3. **部署与网络约束**：逐接口标注"公网直连 / IP 白名单 / 强制指定机房或云内网 / 需专线或隧道"；
4. **规则与处罚**：自动上架与自动回复是否允许、风控触发条件、处罚类型；
5. **考核口径**：回复时效、服务分等平台规则的准确表述（以平台文档为准）；
6. **契约漂移应对**：公告订阅 → 变更工单 → adapter 回归 → 灰度发布。

### 8.3 部署与网络约束

平台可能要求部分接口在指定云环境内调用。应对方式：

- adapter 拆两层：`adapters-pdd` / `adapters-1688`（中心侧：业务逻辑、幂等、快照、审计）+ `edge-proxy`（部署在满足要求的机房，只做转发、请求签名、时间戳防重放、报文留档）。
- 中心 ↔ edge：HTTPS + 双向证书 + HMAC 签名 + 时间窗防重放；不使用 SSH 隧道。
- 若某接口要求特定机房且不采购云主机：该接口进入"未自动化接口清单"，走导入包/人工路径，其余模块照常交付。

## 九、工作流与写入门

### 9.1 工作流

- BullMQ + Postgres 状态机（`workflow_run`），每步带 `idempotency_key`。
- 失败分类：可重试 / 需人工 / 永久失败；断点续跑；超时进死信并可重放。
- 示例（上架）：`draft → fact_checked → judged → media_ready → approved → publishing → published / rejected → (stop_loss | rollback) → archived`。

### 9.2 写入门（唯一写入口）

硬规则：

1. 必须携带 `approval_id`；审批对象与目标资源哈希绑定，内容变更即失效；
2. 幂等键 = `hash(platform + action + payload)`，重复提交不产生第二次写；
3. 写前快照原始值（`listing.published_snapshot`）；
4. 对齐平台限流，失败退避；
5. 失败分类回写工作台，给出可执行下一步；
6. 全量审计。

### 9.3 写操作分级与回滚语义

平台的线上状态不是幂等可逆的：改价、换主图、改类目可能触发重新审核、搜索降权或活动中掉线；客服消息发出后没有撤回接口。

| 级别 | 典型操作 | 可逆性 | 审批要求 | 回滚动作 |
|---|---|---|---|---|
| **A 可逆** | 库存微调、未发布内容改动、内部标签 | 可逆 | 常规审批 | 覆盖写回快照原值 |
| **B 不可逆·低危** | 新增 SKU、发送客服消息、替换非主图素材 | 不可回滚 | 提示"提交/发出后不可撤回" | 只能止损：紧急下架、补偿话术、人工工单 |
| **C 高危·不可逆** | 在售改价、换主图、改类目或关键属性、触碰活动字段 | 无损回滚不存在 | 红色警告 + 二次确认 + 影响面提示 + 建议执行窗口 | 先下架或先退出活动再改，不做覆盖写回 |

配套：

- **执行时机建议**：C 级操作先查活动状态，命中活动期则转"预约低峰窗口"或"先下架再改"，并记录决策。
- **禁止伪回滚**：不得用旧快照覆盖写回并宣称已恢复；不可逆动作必须登记并生成补偿工单。
- **消息去重**：发送前按 `platform + conversation_id + outbound_idempotency_key` 去重，"发送中"状态占位，防重复回调与双击。
- **kill switch**：按平台/类目/任务类型一键停用自动写；支持批量下架与批量改价；演练留档。

### 9.4 审批

- 队列 + SLA（超时升级）+ 积压告警 + 责任表（谁审上架、改价、回复、值班）。
- 审批项展示：事实来源、风险点、与平台现值的 diff、操作级别、预计影响。
- 支持"批准并执行 / 修改后执行 / 拒绝 / 预约执行"。

## 十、判断层

三段闸门，硬事实与语义判断分离：

| 层 | 内容 | 判定 | 成本 | 留存 |
|---|---|---|---|---|
| L1 规则 | 禁限词、品牌语气、成分/尺码字段完整、价格与库存一致性、退换政策适用范围、类目资质必填 | 确定性 pass/fail + 命中项 | 近 0 | 规则 ID |
| L2 LLM 裁决 | 语义灰区：夸大宣传、场景与季节匹配、尺码推荐话术、售后承诺越界 | 固定 JSON Schema：`verdict / severity / reason / evidence_refs / repair_hint` | 低（低价档 + 限流 + 预算上限） | 完整落库，可申诉 |
| L3 人工 | 一切平台写操作 | 批准/驳回/编辑后批准/预约 | 人工工时 | 审批人、时间、diff |

原则：

- **价格、库存、成分、尺码、政策等硬事实不许模型生成**，只能从主数据与知识库取。
- 模型只判语义，且永不单独放行写操作。
- L2 的输出必须带证据引用；无引用不进入判断，直接升级到 L3。

## 十一、知识库与向量检索

- **文档源**：商品主数据、面料成分与洗护、尺码表、退换政策、常见问答、平台规则摘要、历史优质文案。
- **流水线**：解析 → 语义切片（按 SKU / 小节，保留来源与版本）→ 嵌入（`model` 表 `purpose=embed`）→ pgvector（HNSW，cosine）→ upsert 与版本留痕。
- **检索**：混合召回（向量 + 关键词/BM25）→ top-k → 可选重排 → 输出必须带引用（文档 id + 切片 + 版本）。
- **降级**：向量不可用 → 纯关键词 + "低置信"提示 → 判断层升级为人工。
- **权限**：按角色分域；`kb_query_log` 记录查询与命中，便于复盘。
- **一致性**：尺码表既是知识（客服口径）也是结构化数据（平台上传），同源同版本。

## 十二、素材与媒体管线

| 素材 | 方式 | 合规要点 | 自动化 |
|---|---|---|---|
| 主图/白底/尺码/面料细节 | 实拍；尺码表图由结构化数据渲染 | 符合类目图片规范 | 素材库 + 规范检查 |
| 场景图/背景/构图变体 | AI 生成，多模型可选 | 标注 AIGC；不替代实拍主图 | 全自动 + 抽检 |
| 模特图 | AI 替换（授权模特）+ 人审 | 肖像授权，不使用名人 | 自动生成 + 人工审 |
| 商品视频（实拍） | 拍摄 + 剪辑 | 平台视频接口上传（分片） | 审批后自动上传 |
| 短视频（种草） | AI 生成或模板合成 | 成本高、质量波动 → 先出 5 条样片再决定是否建流水线 | 人工决策后建流程 |
| 概念稿 | AI 生成 | 仅内部使用 | 自动 |

管线：`media_job`（提交 → 轮询 → 取回）→ MinIO → 变体（尺寸/裁剪/水印/AIGC 标识）→ 关联 SKU → 成本统计 → 人工抽检 → 进入上架草稿。按 `model_route.purpose` 设配额，超限拒绝或切低价模型。

### 13.2 服装类目的强类型字段

服装是 SKU 最复杂的类目，以下字段必须结构化存储并做 JSON Schema 校验，不允许塞进自由文本：

**尺码表**（`size_chart`，一尺码一行，多版本带生效日期）：

```json
{
  "size_code": "2XL",
  "measurements": { "衣长": 68, "胸围": 104, "肩宽": 46, "袖长": 61, "腰围": 84, "臀围": 98, "下摆": 92 },
  "recommend_height_min": 165,
  "recommend_height_max": 172,
  "recommend_weight_min": 65,
  "recommend_weight_max": 72
}
```

**面料成分**（`fabric_composition`）：`[{ "material": "聚酯纤维", "percent": 62, "note": "主料" }]`，百分比为整数且合计 100，用于满足平台资质与合规要求。

**平台属性映射**（`platform_attribute_mapping`）：`{ platform, attr_path, internal_value, platform_value_id, extra }`，例如拼多多标准色卡 ID、1688 尺码与建议体重区间。

**SKU 主键**：内部统一色卡 `color_id` + `size_code` + `fabric_id`；"卡其色/2XL"这类展示名不参与业务判断。

**尺码表图**：由结构化数据经模板渲染生成，与数据同版本，避免图文不一致。

## 十七、测试与质量门

- **契约测试**：对平台接口录制回放 + 沙箱验证；接口变更即跑回归。
- **故障注入**：超时、5xx、限流、部分成功、重复回调、平台字段变更。
- **黄金集**：至少 50 条真实 SKU × 两平台 × 文案 / 图片 / 尺码表。
- **安全测试**：注入、SSRF、越权、密钥泄漏、沙箱逃逸、MCP 工具越权。
- **专项测试**：不可逆动作的二次确认与登记、消息去重与并发、剪贴板助手不越界（无 DOM 注入、无按键模拟）、幂等与止损演练、账实对账。
- **静态规则**：业务代码禁止引用 `.jsonl` 与 DSH 存储根目录；`packages/db` 之外不得出现业务数据读路径。
- **CI 门禁**：lint + typecheck + 单测 + 迁移校验 + 契约回归 + 幂等回归 + 漂移检查。

| 风险 | 触发信号 | 影响 | 缓解 |

| 数据 | 位置 | 业务代码可否读 |
|---|---|---|
| 业务状态（商品、内容、审批、上架、会话、知识库、审计） | Postgres | 可，唯一事实源 |
| 素材与视频 | MinIO | 可 |
| Agent 会话黑匣子（`.jsonl`） | DSH 工作目录（持久卷 `dsh-data`） | 不可，仅调试工具 |
| DSH 凭据 | DSH 工作目录（`0o700`） | 不可，业务只持引用 |
| DSH 原生存储（storage-json root） | DSH 工作目录 | 不可，不承载业务数据 |

要求：DSH 工作目录在 Compose 中显式挂载为持久卷；禁止多容器各写本地文件；业务页面禁止用 `.jsonl` 拼装数据。

### 19.2 备份矩阵

| 对象 | 方式 | 频率 | 验证 |
|---|---|---|---|
| Postgres | 每日全备 + WAL 归档 | 每日 | 季度恢复演练 |
| MinIO | 版本化 + 对象备份 | 每日 | 半年演练 |
| DSH 目录（配置 + 黑匣子） | 随卷备份，短保留期 | 每日 | 季度抽查 |
| DSH 凭据 | 先确认落盘是否加密；未加密则**不进普通备份**，改为加密导出 + 轮换预案 | 每日/按导出 | 恢复与轮换演练 |

凭据不进 Git、不进镜像、不进普通备份介质；泄露预案为立即轮换 + 撤销 + 审计。

### 19.3 可观测与成本

- 每请求 `request_id` 贯穿 api、worker、平台调用与模型调用。
- 指标：QPS、错误率、平台调用 P95、队列深度、审批积压、媒体成本、草稿降级率。
- 成本按任务、模型、SKU 归集；每日报表；配额与熔断。
- 应急开关：kill switch（平台 × 类目 × 任务类型）、批量下架/改价、模型降级链、写入门熔断。

### 19.4 DSH 版本与升级

当前内核版本为预发布通道（`0.2.1-rc.2`），发布节奏快，必须制度化：

- 版本锁：lockfile 提交 + `resolutions` 固定，CI 校验未漂移；
- 只用公共扩展点：MCP server、skill、agent preset、plugin bundle；不 fork 内部包、不 import 未公开路径；
- 月度升级窗口 + 固定回归清单（preset 加载、skill 发现、MCP 工具、Host 常驻与流式调用、存储读写、Typert 调用与取消）；
- 停更兜底：核心链路不依赖 agent loop，可降级为直调模型 + 自建 MCP。
