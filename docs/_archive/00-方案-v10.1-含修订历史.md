**判决：v9 不可开工（它交付的是另一个东西）；v10/v10.1 是用户要求的那个东西的完整交付方案。**

## 二、用户问过但上一版没答的四个问题（正式答复）

### 2.1 后端框架：Fastify 还是 FastAPI？

**决策：主线 TypeScript + Fastify；Python 仅在媒体/数据 worker 侧用 FastAPI，且是可选组件。**

- DSH 生态全是 TS：MCP client、skill、agent preset、plugin bundle、Typert RPC（`dsh-api-gateway`）官方实现与示例均为 TS；Python 主线等于把模型协议、工具 schema、错误码维护两遍。
- 多供应商模型网关要接 `dsh-llm-pi-ai`（一份配置路由多提供方/网关，profile 与凭据按请求解析、下个请求即生效、无需重启）——TS 主线直接复用。
- Python 的真实优势（图像处理、ffmpeg、pandas 报表）只出现在**边缘层**，用独立进程 + 队列解耦即可。

例外：ERP 数据加工/经营报表若是重头且团队 Python 更强，可独立成 `apps/analytics`，与主线只通过 API / Parquet 交换。**不建议全 Python。**

### 2.2 判断层要不要 LLM？——要，但只能当"灰区裁决"，不能当唯一闸门

1. **规则闸（确定性，免费）**：禁限词、成分/尺码字段完整性、价格与库存一致性、退换政策适用范围、类目资质必填项。
2. **LLM 裁决（仅规则无法判定时）**：输入 = 草稿 + 事实片段 + 规则命中项；输出 = 固定 JSON Schema（`verdict / severity / reason / evidence_refs / repair_hint`）；走网关**低价档**；全量落库可申诉。
3. **人工（写入门强制）**：任何平台写操作仍需 `approval_id`，LLM 不能代替人放行。

**硬事实（价格、成分、尺码、政策）不许 LLM 生成**，只能从主数据与知识库取。

### 2.4 DSH 的更新频率与风险（实测 + 应对）

事实：`@deepseek-ai/dsh` 最新版 **0.2.1-rc.2（预发布）**，累计 36 个版本；2026-10-09 → 10-17 **9 天内 5 个 alpha/rc**；Desktop app 2.0.18。

- **版本锁**：pnpm lockfile 提交 + `resolutions` 固定 `@deepseek-ai/dsh*` 到 `0.2.1-rc.2`，CI 校验 lockfile 未漂移。
- **只用公共缝**：MCP server、skill、agent preset、plugin bundle；不 fork 内部包、不 import 未公开路径。
- **月度升级窗口**：不在业务周升级；升级前跑固定回归清单（preset 加载 / skill 热发现 / MCP 工具可用 / workflow 工具 / Host 常驻与流式调用 / 存储读写 / Typert 调用与取消）。

### 4.1 复用 DSH 的什么（实测可用）

| 需求 | 复用的 DSH 包 | 复用方式 |
|---|---|---|
| 文本/多供应商模型路由 | `dsh-llm-pi-ai` | 模型网关文本侧直接挂；图片/视频侧自建 adapter，共用同一注册表 |
| 供应商密钥 | `dsh-credentials` | `provider.auth_ref` 指向其记录；"后台配好才前台可见"用它的"已配置"语义。**注意：官方未承诺静态加密，见第十八节备份矩阵** |
| 写入门 / 审批的 RPC 与授权 | `dsh-api-gateway`（Typert RPC，流式 + AbortSignal + peer principal）+ `dsh-api-remote-access`（role × resource 授权，Client 侧自动隐藏无权入口） | 写入门做成 Host 侧 Remote service；**同时用作网页驱动 agent 的通道（P1）** |
| 沙箱与审批档位 | `dsh-permission-presets` + `dsh-user-approval`（敏感工具一次性决定，全程审计） | 运营/客服/只读三档预设随角色下发 |
| 平台回调 | `dsh-webhook`（受信任规则注册表，内置动作=创建根会话） | 订单/消息/售后回调 → 触发工作流会话 |
| 批处理/定时/CI | `dsh-headless`（**一次性任务模式：每次调用跑一个任务即退出，无 GUI、无服务器**；`--json` 事件流；`--session-id` 续接会话） | 仅用于批处理/定时/CI；**不用作交互通道**（P1） |
| 员工 agent 工作台 | `dsh-agent-preset`（YAML 定义 preset） | 打包"服装电商运营 preset"（文案/客服/选品/素材） |
| Skill / MCP | `dsh-skill-filesystem`（目录 bundle，热监视）+ `dsh-mcp-client` | 品牌语气/尺码/洗护/退换货 4 个 skill；ERP/平台只读 MCP |
| 会话持久化 | `dsh-session-persistence-jsonl` | agent 会话留痕（黑匣子），**业务代码不读**（P6） |
| 原生存储 | `dsh-storage-json` | **不用于业务数据**：其 `root` 必填、目录以 `0o700` 创建，官方明示"更大或高并发数据用 SQLite" → 业务状态只认 Postgres（P6） |

**明确不误用的**：`dsh-workflow` 是**给模型用的 agent 扇出编排**（JS 脚本 + `agent()/parallel()/pipeline()`，由调用方提供执行引擎），**不是**带持久化状态、人工节点、幂等、回滚的业务流程引擎；业务流程状态机用 BullMQ + Postgres 自建，两者不重复。

## 五、身份、权限、审计与**唯一交互入口**（补丁 P1 重写）

### 5.0 唯一业务入口 = apps/web（Next.js）

- 业务人员（运营/客服）**不安装、不接触 DSH**。他们在 apps/web 的 12 个页面里点按钮或提诉求，由 `apps/api` 驱动**中心常驻 DSH Host** 执行，SSE 流式回显到网页。
- **中心 DSH Host**：常驻进程，对外只暴露一个 Typert Remote service（`@Remote({ mode: 'stream' })`），支持流式输出与 `AbortSignal` 取消；`apps/api` 作为 Client（`@deepseek-ai/dsh-api-gateway/client` 的 `ctx.remote`）调用；peer principal 决定权限，复用 `dsh-api-remote-access` 的 role × resource 决策，前端自动隐藏无权入口。
- **DSH 原生 Web/Desktop 界面仅管理员使用**（调试 preset、skill、观察 agent 行为），不进业务流程。
- **`dsh-headless` 不作交互通道**：它每次调用跑一个任务即退出，没有常驻服务与多轮交互（实测："每次调用只运行一个任务，没有交互式后续"）。仅用于批处理、CI、定时任务。
- 附带收益：常驻 Host 避免 headless 每次起进程（插件加载 + 会话准备）的秒级开销。

### 5.1 身份与角色

- DSH 现状（实测）：有 Host 内 role/资源授权与沙箱/审批档位，但**没有企业身份源、SSO/OIDC/SCIM、多租户、按用户的配额与计费**。
- 自建轻量身份层：`users / roles / memberships`，口令 + TOTP；三档角色 `viewer`（只读）/ `operator`（草稿+素材）/ `admin`（供应商配置、发布审批、kill switch）；预留 LDAP/企业微信/钉钉 OAuth 适配口。

### 5.2 部署形态

中心 Host（`dsh --profile web` 或自有 profile，可绑定内网 IP、支持自签 TLS、启动打印带 token 的 URL）+ 中心 `apps/api`/`apps/worker` + 员工浏览器。理由：审计、成本归集、密钥、离职交接必须在中心；交互体验在浏览器。

### 5.3 审计

`audit_log` 追加写（谁、何时、动作、资源、before/after），永不更新；写入门每笔落审计（不可逆动作额外标记 `irreversible=true`，见 8.2）；模型调用落 `model_call_log`（模型、token、耗时、成本、产出摘要）。

### 5.4 场景分工：什么放网页、什么放 DSH

| 场景 | 入口 | 理由 |
|---|---|---|
| 文案生成/改写、详情页产出 | 网页按钮 → api → agent（同一 Remote service） | 业务人员要的是结果不是对话 |
| 客服回复、询盘报价 | 网页（会话列表 + 草稿 + 发送） | 同上 |
| 商品资料问答/多轮澄清 | 网页内嵌对话（走同一 Remote service，流式） | 需要追问但要留在业务上下文中 |
| 调参、调试 preset/skill、观察 agent 行为 | DSH Web（仅管理员） | 开发者工具，不进流程 |
| 批量、CI、定时任务 | worker → `dsh-headless`（`--json --session-id`） | 无 GUI 需求 |

## 六、模型与供应商管理（核心需求）

三层实体 + 状态机：

| 层 | 表 | 关键字段 |
|---|---|---|
| Provider（供应商账号） | `provider` | kind(text/image/video/embedding)、base_url、auth_ref→DSH 凭据、status、连通性测试结果、余额 |
| Model（能力/模型/参数/价格） | `model` | provider_id、external_model_id、display_name、capability、params_schema、price、rate_limit、status、published_at |
| Route（默认与降级） | `model_route` | scope(org/role/user)、purpose(copy/judge/image/video/embed/rerank)、model_id、fallback_ids、priority、配额 |

**"后台配好，前台才显示"的确切规则**：
1. `provider.auth_ref` 已配置且连通性测试通过（`dsh-credentials` 报"已设置"）；
2. `model.status=published` 且 `params_schema` 校验通过；
3. `route` 命中当前用户 scope 且角色未被禁；
4. `/api/models?capability=&purpose=` 只返回同时满足 1–3 且用户有权使用的模型；
5. 管理员改配置 → 下个请求即生效（`dsh-llm-pi-ai` 的 profile/凭据按请求解析语义），**不重启**；
6. 每次调用记录真实 model_id + 成本，超配额拒绝或降级。

**用户给的模型名需核对**：gpt-image-2.5 / nanobanana2.1 / qwen-image-3 / seedream5.0 与公开常见命名不一致，M0 以账号内实际可用的 model id 建档，映射表落在 `model.external_model_id`。

**图片/视频工程约束**：视频多为"提交→轮询→取回"异步链路 → 队列 + `media_job` + MinIO；DSH 明写"音频和视频暂无专门处理" → 转码与分片上传自建。

### 7.2 平台接入侦察（M0 第一件事）

现状（实测 2026-10-20）：PDD 开放平台 API 文档需登录开发者账号；公开公告 412 条，接口与规则持续变更（10-17 订单接口新增保密发货标签、10-14 商品资质合规要求升级、09-29 订单换 SKU + 消息推送、**09-28 新增商品视频分片上传接口**、09-21 多多云 DB 容量超限）。1688 未取得可核实的公开 API 文档（尝试路径 404/需登录），**必须在 M0 用开发者账号核对**。

M0 产出物（每平台一份《平台接入侦察报告》）：
1. 账号与资质：开发者认证 / 应用创建 / 类目资质要求（服装类目注意 10-14 资质升级公告）→ 记录申请周期；
2. 接口清单：商品发布/上下架/改价、库存、订单、消息/客服、素材（图片/视频）上传 → 逐条记录"接口名 + 是否需审核 + 限流 + 沙箱可用性"；
3. 规则与处罚：自动上架/自动回复是否被允许、风控触发条件、处罚类型；
4. 消息推送：订单/消息推送能否拿到 → 决定自动回复与自动上下架可行度；
5. 平台考核口径（如回复时效/服务分规则）→ 决定客服 SLA 目标（**须以平台规则为准，不采信未核实的数字**）；
6. **契约漂移策略**：订阅公告 → 变更工单 → adapter 回归 → 灰度；
7. **兜底路径（默认启用）**：商品走"上架包（CSV/Excel）+ 后台批量导入"；客服消息走工作台人工发送 + 剪贴板助手；1688 同理 + 询盘人工处理。**兜底路径是交付的一部分，不算失败**。

### 7.3 平台部署与网络约束（补丁 P2）

事实：PDD 开放平台存在"多多云"体系（公告含 2026-09-21「多多云数据库存储容量超限常态化处理机制的说明」）。**是否强制在多多云 VPC 内部署、是否需 IP 白名单、哪些接口允许公网直连，逐接口不同且未核实**——因此 M0 必须逐接口核验，不得假设。

M0 核验表（每个在用接口一行）：

| 接口 | 公网直连 | IP 白名单 | 强制多多云/指定机房 | 需专线/隧道 | 需商家授权与审核 | 限流 | 备注 |

架构准备（不预设结论，但保证不被卡死）：
- adapter 拆两层：`adapters-pdd` / `adapters-1688`（中心侧：业务逻辑、幂等、快照、审计）+ `edge-proxy`（部署在满足平台要求的机房的**薄代理**：只做转发、请求签名、时间戳防重放、原始报文与响应留档）。
- 中心 ↔ edge 通信：HTTPS + 双向证书 + HMAC 请求签名 + 时间窗防重放；**不使用 SSH 隧道**（运维脆弱、易随重启断链）。
- 若核验结果要求特定机房而你不愿意购买云主机 → 该接口走兜底路径（导入 + 人工），其余模块照常交付；**M0 报告必须给出"该接口能否自动化"的明确结论与代价**。
- 1688 一并核验（阿里云侧同类要求）。

## 八、工作流与写入门

### 8.1 编排与硬规则

- BullMQ + Postgres 状态机（`workflow_run`），每步 `idempotency_key`；失败分类（可重试/需人工/永久失败）；断点续跑；超时与死信。
- 状态机样例（PDD 上架）：`draft → fact_checked → judged → media_ready → approved → publishing → published / rejected → (rollback|stop_loss) → archived`。
- 写入门硬规则：必须带 `approval_id`（内容变更即失效）· 幂等键 `hash(platform+action+payload)` · 写前快照原始值（`listing.published_snapshot`）· 限流退避 · 失败分类回写并给可执行下一步 · 全量审计。
- 审批：队列 + SLA（超时升级）+ 积压告警 + 责任表；审批项展示事实来源、风险点、与平台现值的 diff。
- kill switch：按平台/类目/任务类型一键停用；批量下架/批量改价；回滚演练留档。

### 8.2 写操作分级与"非对称可逆性"（补丁 P4）

平台线上状态**不是幂等可逆的**：改价、换主图、改类目可能触发重新审核、搜索降权、活动中掉线；客服消息发出后**没有撤回 API**。因此回滚语义必须分级：

| 级别 | 典型操作 | 可逆性 | 审批 UI | 系统回滚动作 |
|---|---|---|---|---|
| **A 可逆** | 库存微调（±）、未发布内容改动、内部标签/备注 | 可逆 | 常规审批 | 覆盖写回快照原值 |
| **B 不可逆·低危** | 新增 SKU、发送客服消息、上传/替换非主图素材 | **不可回滚** | 明确提示"发出/提交后不可撤回" | 只能止损：紧急下架 / 转人工售后工单 / 补偿话术 |
| **C 高危·不可逆** | 在售商品改价、换主图、改类目/关键属性、触碰活动（百亿补贴/万人团）字段 | **无损回滚不存在** | 红色警告 + 二次确认 + 影响面提示 + 建议执行窗口 | 不做"覆盖写回"，改为**先下架或先退出活动再改** |

配套规则（补丁 P7、P8）：
- **执行时机建议**：C 级操作先查活动状态；命中活动期 → 审批通过后转为"预约到低峰窗口"或"先下架再改"，并记录决策。
- **禁止伪回滚**：系统不得用旧快照覆盖写回并宣称"已恢复"；不可逆动作在 `audit_log` 标记 `irreversible=true` 并强制生成补偿工单引用。
- **消息发送去重与并发**：发送前按 `platform + conversation_id + outbound_idempotency_key` 去重；"发送中"状态占位，防平台重复回调与客服双击导致重复发送。
- **活动与价格保护**：涉及活动/价格的字段变更在审批阶段即提示"可能影响活动权重"。

### 8.3 客服实时性与降级链（补丁 P3）

链路：`平台回调 → api → Postgres → SSE/WebSocket 推送到已打开的工作台（秒级提醒）→ agent 生成草稿（5 秒硬超时）→ 审批 → 发送`。

- **秒级提醒**：消息入站先落库并立刻推送，不等 agent、不等模型。
- **5 秒硬超时**：草稿生成超时/失败 → 直接返回高频话术模板库 Top-N（可一键采用），不让客服等模型。
- **三条发送通道并行可用**：
  1. 官方消息 API（若已获批）→ 写入门发送；
  2. 网页内发送（仅需展示与留痕时）；
  3. **本地剪贴板助手**：审批通过瞬间由 api 把话术推送到员工本机的小工具，自动写入**系统剪贴板**并提示，客服在飞鸽/旺旺 `Ctrl+V` 发送。
    - **边界（风控红线）**：助手**只写系统剪贴板**，不注入 DOM、不模拟按键、不识别窗口、不做任何浏览器自动化。
- 口径说明：拼多多"回复时效/服务分"等考核规则**未核实**，M0 以平台规则为准；设计上按最严（秒级提醒 + 5 秒降级 + 模板兜底）执行，不依赖任何未证实的时限数字。

## 十、知识库与向量检索

- DSH 现状（实测）：**无 vector / embedding / RAG 包**；`dsh-storage` 只有 json 后端 + 领域层 → 向量与业务库自建（Postgres + pgvector）。
- 文档源：商品主数据、面料成分与洗护、尺码表、退换政策、常见问答、平台规则摘要、历史优质文案。
- 流水线：解析 → 语义切片（按 SKU/小节切，保留来源与版本）→ 嵌入（`model` 表 purpose=embed）→ pgvector HNSW（cosine）→ upsert + 版本留痕。
- 检索：混合召回（向量 + 关键词/BM25）→ top-k → 重排（可选）→ **输出必带引用**（`evidence_refs`：文档 id + 切片 + 版本），无引用不进 L2 判断。
- 降级：向量不可用 → 纯关键词 + "低置信"提示 → 判断层升级为 L3 人工。
- 权限：按角色分域；`kb_query_log` 记录查询与命中。
- 尺码表既是知识也是结构化数据（第十二节）→ 同一份数据同时供 RAG 引用与平台上传。

## 十一、媒体与素材管线

| 素材类型 | 方式 | 平台与合规 | 自动化程度 |
|---|---|---|---|
| 主图/白底/尺码/面料细节 | **实拍**（尺码表图由结构化数据模板渲染产出） | 符合类目图片规范；不做 AI 替代 | 素材库管理 + 规范检查 |
| 场景图/背景/构图变体 | AI 生成（多模型可选） | 标注 AIGC；不触碰"主图必须实拍"红线 | 全自动 + 抽检 |
| 模特图 | AI 替换（授权模特）+ 人审 | 肖像授权、不做名人 | 自动生成 + 人工审 |
| 商品视频（实拍） | 拍摄 + 剪辑 | PDD 2026-09-28 已支持商品视频分片上传 → 上传通路存在 | 自动上传（审批后） |
| 短视频（种草） | AI 生成或模板合成 | 成本高、质量不稳 → **先出 5 条样片再决策** | 人工决策后建流程 |
| 概念稿/设计灵感 | AI 生成 | 仅内部 | 自动 |

管线：`media_job`（提交→轮询→取回）→ MinIO → 变体（尺寸/裁剪/水印/AIGC 标识）→ 关联 SKU → 成本统计 → 人工抽检 → 进入上架草稿。成本上限与降级按 `model_route.purpose=image/video` 配额。

## 十二、数据模型（Postgres）——含服装类目强类型字段（补丁 P5）

### 12.1 核心表

`provider`、`model`、`model_route`、`credential_ref`（只存 ref）、`product`、`product_sku`、`size_chart`、`fabric_composition`、`platform_attribute_mapping`、`platform_category`、`listing`（含 `published_snapshot`）、`content_draft`、`judgment`、`media_asset`、`media_job`、`conversation`、`message`、`approval`、`workflow_run`、`audit_log`（含 `irreversible`）、`kb_document`(+`kb_chunk`+`kb_query_log`)、`sync_cursor`、`kill_switch`、`model_call_log`、`compensating_ticket`（不可逆动作补偿工单）。

公共字段：`id`(uuid)、`org_id`（默认 1，留边界）、`created_at/updated_at`、`created_by`、`version`(乐观锁)、软删 `archived_at`。索引：平台+状态、`workflow_run(state)`、`approval(status, sla_due_at)`、`media_job(status, poll_after)`、向量列 HNSW。

### 12.2 服装类目的一等公民字段（JSON Schema 强校验，不塞 description）

- `size_chart`（一尺码一行一版本，带 `effective_from`）：
  ```json
  { "size_code": "2XL",
    "measurements": { "衣长": 68, "胸围": 104, "肩宽": 46, "袖长": 61, "腰围": 84, "臀围": 98, "下摆": 92 },
    "recommend_height_min": 165, "recommend_height_max": 172,
    "recommend_weight_min": 65,  "recommend_weight_max": 72 }
  ```
  单位与字段名在 schema 内固定；尺码表随季节改版 → 多版本 + 生效日期。
- `fabric_composition`：`[{ "material": "聚酯纤维", "percent": 62, "note": "主料" }, ...]`，**百分比精确到整数且合计 = 100**（应对 2026-10-14 商品资质合规要求升级）。
- `platform_attribute_mapping`：`{ "platform": "pdd", "attr_path": "sku.color_id", "internal_value": "khaki", "platform_value_id": "…", "extra": {} }` —— PDD 标准色卡 ID、1688 尺码 + 建议体重区间等平台私有字典的映射。
- `product_sku`：`color_id`（内部统一色卡）+ `size_code` + `fabric_id` + `attributes`（平台无关的结构化属性）+ 内部名称（"卡其色/2XL"）仅作展示。
- **写入即校验**：所有 JSON 字段入库前用 JSON Schema 校验，不合法直接拒绝并给出字段级错误；平台发布前再做一次平台字典存在性检查。
- **尺码表图片 = 结构化数据的模板渲染产物**：同一份数据两用（平台上传图 + 客服/RAG 检索），避免图文不一致。

## 十八、可运维性、成本、存储边界与备份矩阵（补丁 P6 重写）

### 18.1 存储边界（硬规则）

| 数据 | 位置 | 业务代码可否读 | 说明 |
|---|---|---|---|
| 业务状态（草稿/审批/商品/尺码表/成分/审计/listing/会话/知识库/补偿工单） | **Postgres** | ✅ 唯一事实源 | 所有页面与接口只读这里 |
| 素材与视频 | MinIO | ✅ | 版本化 |
| Agent 会话黑匣子（`.jsonl`） | DSH 目录（卷 `dsh-data`） | ❌ 仅 debug 工具可读 | 保留期短（调试窗口），不进业务视图 |
| DSH 凭据存储 | DSH 目录（卷 `dsh-data`，目录 `0o700`） | ❌ 业务代码只持 ref | 见 18.3 |
| DSH storage-json `root` | DSH 目录（卷 `dsh-data`） | ❌ 业务状态不用它 | 官方明示"更大或高并发数据用 SQLite"，故不用作业务库 |

依据：`dsh-storage-json` 的 `root` 必填、目录按需以 `0o700` 创建（实测），`dsh-storage` 的内置后端只有 json + 领域层 → **业务数据进 Postgres，DSH 目录只放 DSH 自己的东西**。

### 18.2 部署与双写分裂防护

- docker-compose 显式挂载 DSH 工作目录为持久卷 `dsh-data`（api/worker/DSH Host 共享同一卷），禁止多容器各写本地 JSON。
- 边界规则写进工程规范与代码评审清单；CI 静态检查：`packages/db` 之外出现 `.jsonl` 或 DSH storage root 的读路径 → 失败。
- **禁止反向拼装**：业务页面禁止用 `.jsonl` 里的 agent 输出组装业务数据；agent 产出必须经写入门/草稿表落 Postgres 后才可见。

### 18.3 凭据与备份矩阵

| 备份对象 | 方式 | 频率 | 恢复验证 |
|---|---|---|---|
| Postgres | 每日全备 + WAL 归档 | 每日 | 季度恢复演练 |
| MinIO | 版本化 + 对象备份 | 每日 | 半年演练 |
| DSH 目录（配置 + `.jsonl` 黑匣子） | 随卷备份，**短保留期** | 每日 | 季度抽查可读 |
| **DSH 凭据** | **先确认落盘形态**：`dsh-credentials` 官方只承诺"只报是否已设置、不返回值"，**未声明静态加密** → M1 必须实测；<br>若非静态加密：凭据**不进普通备份**，改为**加密导出**（导出件用 KMS/环境变量注入的密钥加密）+ 轮换预案；<br>若为静态加密：随 DSH 目录备份，恢复时校验可解密 | 每日/按导出 | 恢复演练 + 轮换演练 |

- 凭据**不进 Git、不进镜像、不进普通备份介质**；泄露应急预案 = 立即轮换（`dsh-credentials` 轮换下次请求即生效）+ 撤销 + 审计。
- 备份脚本统一由 `scripts/backup.ps1` 执行，产出备份矩阵报告（哪些被备份、哪些被排除、原因）。

### 18.4 其他运维项

- 观测：每请求 `request_id` 贯穿 api/worker/平台调用/模型调用；Prometheus 指标（QPS/错误率/P95 平台调用/队列深度/审批积压/媒体成本/草稿超时降级率）。
- 成本：按任务、按模型、按 SKU 归集；每日成本报表；配额与熔断。
- 应急开关：`kill_switch`（平台 × 类目 × 任务类型）、批量下架/改价、模型降级链、写入门熔断、止损动作。
- 升级流程：DSH 月度窗口 + 平台公告 24h 响应 + adapter 契约回归。
